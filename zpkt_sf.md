# Implementation plan for `zpkt/sf` and `libZpkt_sf`

Author **hrogers-kaldron** · 2026-11-26

Build one optional Linux raw Ethernet plugin against AMD's public **`ef_vi`** API. Applications select `libZpkt_sf.so` through `Zpkt::Env`. The device remains a `Zpkt::Nif` with an ordinary Ethernet peer, one Rx owner and one Tx owner. The unit of support is an allocated virtual interface (VI) with a usable receive, transmit, steering and wake configuration. Negotiate those capabilities and record the resulting mode. A product name alone cannot determine the packet path, particularly on an X4 adapter with Enterprise and Express datapaths. [Mellanox plan](zpkt_mlx.md) · [Zpkt interface contract](zpkt/INTERFACE.md) · [AMD ef_vi User Guide](https://docs.amd.com/api/khub/documents/PhDqWIW_vwYMa_9U3H35kQ/content)

## 1. Build the module and open the named interface

Add `zpkt/sf/Makefile.am` and backend-private factory, configuration, Nif, queue and buffer-pool files. Add a Linux-only, opt-in `--with-sf` to `configure.ac` and expose it in `z.config`. Register the source include alias and generated Makefile. Build the plugin after `zpkt/src` and before its tests, independently of DPDK. Install `libZpkt_sf.la` as an unversioned libtool module (`-module -avoid-version`). Export the existing C-linkage `ZpktPlugin` entry point. Applications link common Zpkt. [Build conventions](docs/BUILD.md) · [Module traversal](zpkt/Makefile.am) · [Loadable backend example](zpkt/afp/Makefile.am)

AMD distributes the public `etherfabric/` headers and the user-level library with Onload. For the documented static-library build, probe the matching headers and `libciul1.a`. **Link a tiny shared module** that exercises real VI allocation and registration symbols. This catches missing dependencies and archive objects unsuitable for a shared library that an executable-only probe would miss. Hide provider symbols in the plugin, expose SDK path overrides for source installations, and exercise the installed module through Env. Record the SDK release, driver version and their supported combination. [AMD compiling and linking, §6.2](https://docs.amd.com/api/khub/documents/PhDqWIW_vwYMa_9U3H35kQ/content) · [AMD development packages](https://docs.amd.com/r/en-US/ug1586-onload-user/Packaging-Changes)

Parse and own the typed `interfaces` map at factory construction. On a cache miss, use the host-supplied ifindex for `ef_pd_alloc()` after opening the driver handle. Retain the protection domain (PD) on the Nif. Use the host MAC and MTU, report one logical Rx queue, and retain Env's default host lookup and loopback policies. Return a stopped, unallocated device. Include the interface, operation and native error on failure. Query available datapaths by ifindex before allocating the PD. Default to the native datapath selected by the SDK and expose an optional Express request on hardware with multiple datapaths. An explicit request must succeed or return a configuration error. Probe capabilities against that PD, then verify resources actually allocated. Guard release-specific SDK features with configure probes and document the oldest header/library combination exercised by CI. AMD's `eflatency` example uses `EF_VI_CAP_RX_REF` to distinguish provider-managed receive from application-posted buffers. [Env contract](zpkt/INTERFACE.md#construction-and-env-ownership) · [AMD capability API](https://github.com/Xilinx-CNS/onload/blob/master/src/include/etherfabric/capabilities.h) · [AMD example](https://github.com/Xilinx-CNS/onload/blob/master/src/tests/ef_vi/eflatency.c)

## 2. Receive all packets on the named interface

Acquire the shared socket-owned nftables netdev guard at named open using the resolved ifindex. Retain it across stop, failed starts and retries until successful finalization. This suppresses Linux protocol delivery while the VI is dormant and when hardware makes a host copy. Require `CAP_NET_ADMIN` for the guard. A failed claim rolls back the open. [Shared netdev guard](zpkt/src/ZpktIngress.cc)

```text
module libZpkt_sf.so
interfaces {
  enp65s0f0 { rxDepth 512 }
}
```

The receive contract covers every inbound Ethernet frame delivered to the selected interface, across EtherTypes, destination addresses and VLANs. After preparing the VI, buffers and notification queues, first try separate all-unicast and all-multicast filter specifications (`ef_filter_spec_set_unicast_all()` and `ef_filter_spec_set_multicast_all()`). Install both with `ef_vi_filter_add()`. Qualify the combination for broadcast and traffic already matched by other filters. On a datapath that supports promiscuous port sniff, an alternative is a single Rx `ef_filter_spec_set_port_sniff(&spec, 1)` filter on the dedicated VI. Sniff makes a copy, which is why the host ingress guard remains necessary. Admit sniff only when its capture domain is exactly the selected Nif. Where supported, a separate `ef_filter_spec_set_block_kernel()` filter can suppress earlier host delivery if the validated combination still supplies all frames to the VI. [AMD filter API and semantics](https://github.com/Xilinx-CNS/onload/blob/master/src/include/etherfabric/vi.h)

Retain each installed cookie. Remove partial filters before trying another mode. Keep failed removals and the guard for retry. Publish readiness only after one complete mode succeeds. For X3522, X4 and other shared-queue datapaths, establish complete coverage of the named function and exclude other functions' frames. Fail activation when only narrower filters are available. Report the effective intercept or guarded-copy mode. Size the receive descriptors or provider capture space and event queue for `rxDepth`, accounting for refill granularity, and verify actual usable depth before start. Measure backlog exhaustion separately from malformed frames, event loss and software discards. [AMD shared receive queues](https://docs.amd.com/r/en-US/ug1586-onload-user/Controlling-Access-to-RX-Queues-on-X3522) · [X4 filters](https://docs.amd.com/r/en-US/ug1586-onload-user/X4-Filters)

## 3. Allocate stable pools and select the receive model

Provision the common Rx pool, distinct TxTCP/TxUDP pools, and any transport reserves as a transaction. Precompute slot identity, upper wire bounds and request-ID tables. Preserve logical size, small control pools, headroom, tailroom, alignment, and interior-pointer lookup/return. Register DMA backing with `ef_memreg_alloc()`. Derive addresses using `ef_memreg_dma_addr()` at each required offset. The API guarantees continuity within each 4 KiB block. Fit posted receive extents inside a valid DMA span, and split transmit extents into supported vector segments where needed. Check arithmetic and frame/descriptor limits up front. Publish only when all pool backing and metadata are ready. Repeating `alloc()` with the identical set reuses it. Reject conflicting sets and unwind a partial registration before retry. [Pool contract](zpkt/INTERFACE.md#shared-allocation) · [Registration API](https://github.com/Xilinx-CNS/onload/blob/master/src/include/etherfabric/memreg.h)

| Effective Rx mode | Packet delivery | Return and restart |
| --- | --- | --- |
| Application-posted buffers, as on SFN8000, X2 and X4 Enterprise | Post a free registered Rx slot with its request ID. Query the VI's receive prefix and required DMA extent. Place the Ethernet start at the aligned canonical packet base. Validate the event length after accounting for the prefix. | Transfer the slot to the callback. Repost only after its final pool return, which may occur on another thread. |
| X4 compatibility mode | The SDK copies provider-owned frames into application-posted buffers and translates events to ordinary Rx events. Use the posted-buffer interface and report the receive copy. | Preserve the application slot until final return. Test this mode independently of true posted-buffer DMA. |
| Provider-managed references, as on X3522 or X4 Express | On `RX_REF`, obtain the pointer with `efct_vi_rxpkt_get()`, copy the validated frame into an available Zpkt slot, and call `efct_vi_rxpkt_release()` before invoking the callback. On discard or pool exhaustion, release the reference exactly once. | The application owns a writable Zpkt slot. Returning it after stop or on another thread never calls into a retired VI. Count drops caused by pool exhaustion. |

X2 and X4 Enterprise can use DMA transmit. X3522 and native X4 Express use cut-through programmed I/O (CTPIO). X4 compatibility can implement a DMA-style call with CTPIO. Choose the operations once during setup and report the effective Rx/Tx modes, including SDK copies. Keep one implementation of slot accounting and shutdown across these modes. [AMD X4 architecture and compatibility](https://docs.amd.com/api/khub/documents/YUDpjop2UySM2YKb5ryPcA/content)

Resolve geometry that depends on the VI **before publishing pools**. Allocate a dormant VI to inspect its receive prefix, buffer length and queue limits where needed. At each activation validate the negotiated mode and extents against the retained allocation. If incompatible, fail that start while preserving outstanding buffers. Inject a restart layout change and verify both address and bytes of a previously retained packet. Keep private prefixes and registration padding outside caller capacity. Validate the largest frame the configured MTU and tag policy allow. For the initial implementation accept geometry that yields one complete contiguous frame. Refuse an unsupported MTU before installing any filter. Add bounded assembly only with a fixture that establishes fragment ordering, discard behavior and effective copy mode. [Receive API](https://github.com/Xilinx-CNS/onload/blob/master/src/include/etherfabric/ef_vi.h) · [AMD reference-based receive](https://docs.amd.com/r/en-US/ug1523-x3522-user/Software-Migration)

## 4. Service receive, transmit and wake

Allocate one Rx-only and one Tx-only VI with separate event queues in the first implementation. Each Z service owner is then the sole consumer of its queue. Check allocation results and record actual depths. Report an actionable setup error if a compatible pair cannot be allocated. Consider a shared software event queue only if a supported configuration needs it and a test can prove independent Tx progress when Rx is idle or stopped. Hardware Rx queue sharing for steering is a separate property. [VI allocation API](https://github.com/Xilinx-CNS/onload/blob/master/src/include/etherfabric/vi.h) · [Zpkt owner contract](zpkt/src/Zpkt.hh)

**Rx and wake.** Prime posted-buffer receive with `ef_vi_receive_init()` and `ef_vi_receive_push()`, sized to the actual ring. Decode the event types enabled for this VI, including discards. Check length, prefix and fragment flags. Where the VI publishes descriptors in groups of eight, size the ring and pool to allow a group, track staged descriptors separately, and keep the return wake armed until enough free slots arrive to publish. Test startup and recovery with one through seven staged descriptors. Bound callback work by the Rx quantum while polling with at least the SDK's minimum event array size. Keep any pending suffix in preallocated storage and preserve event order. Use `ZiRxBurst` for a group and a null burst for a singleton. After a bounded idle spin, publish the wait, call `ef_vi_prime()` with the current event cursor, recheck events, returned frames and public wakes, then wait on the driver fd and Z's eventfd. Request hardware wake support on filters where required. Use a bounded eventfd wait with repoll on paths without a suitable hardware wake, and document the effective wait mode. Pool return should kick a parked owner that can replenish its queue. An incoming public wake interrupts idle or busy receive even under continuous traffic. [Common wake protocol](zpkt/src/Zpkt.cc) · [AMD event API](https://github.com/Xilinx-CNS/onload/blob/master/src/include/etherfabric/ef_vi.h)

**Tx and completion.** Use the public DMA send operation where available and the documented cut-through transmit path on VIs that require it. Distinguish native DMA from emulation that copies data or computes checksums. Select a mode that preserves exact caller and wire bytes, including raw non-IP frames. Where the provider could write the source, use preallocated private Tx backing and send from there if the selected mode can preserve the required wire semantics. Account for cut-through acceptance and any required fallback/completion as one submission. Report pressure before issuing an irreversible send. On a CTPIO-only VI, check byte capacity and use the SDK's request-ID-bearing fallback operation to associate a unique outstanding ID with the send. Without that operation, X3 and X4 Express can return the same provider ID for every send. Qualify the request-ID path for the initial implementation. Test both fallback and failure paths. For X4 compatibility mode an init call can transmit immediately, so complete admission and acquire the lease first. Start with caller-computed checksums, request `EF_VI_TX_IP_CSUM_DIS` and `EF_VI_TX_TCPUDP_CSUM_DIS` on paths with default offloads, and report `tcpChksumOffload() == false`. [AMD X4 migration guide](https://docs.amd.com/api/khub/documents/YUDpjop2UySM2YKb5ryPcA/content) · [Cut-through transmit contract](https://docs.amd.com/r/en-US/ug1586-onload-user/Using-CTPIO-with-ef_vi)

Scalar `send()` publishes frame one immediately. The vector overload returns exactly the accepted leading prefix up to `MaxTxBatch`. A refused entry takes no submission lease. `txReady()` observes the existing lease before a retained frame is edited. Maintain the caller's allocation and the device submission independently even on a copying path. In `pollTx()`, expand bundled completions with `ef_vi_transmit_unbundle()` when the event type supports it, map each request ID back to its slot and count each retirement once. Preserve progress for the final submission followed by idle. Report `zeroCopy()` only when both active directions preserve direct packet backing. Record the effective Rx/Tx modes separately in `status()` and expose callback-scoped queue statistics in `allQueues()`. Count delivered frames/bytes, pool starvation, software discards, Tx accepted/retired/pending and VI errors. Include the queue depths, effective steering and fallback reason in diagnostics. [Packet service and ownership](zpkt/INTERFACE.md#packet-service)

## 5. Stop, recover and finalize

With the scheduler running, close admission, withdraw filters, interrupt and quiesce Rx, release each pending provider reference, and drain Tx on its owner. Fence off-owner wake writers before closing descriptors. Treat lost events, including `EF_EVENT_TYPE_OFLOW`, as a failed run. Track accepted slots in a bounded ledger. A successful `ef_vi_flush()` is the documented boundary after which pushed buffers can be reused. After that boundary, retire any still outstanding device leases exactly once, account for unresolved wire outcome separately, and run `txStopped` on the Tx owner. If flush fails, use only a documented equivalent quiescence guarantee. Otherwise retain the VI, registered backing and ledger. Surface the native failure through `Nif::error()` and the Env finalization result. Refuse restart while ownership remains unresolved. Repeated stop/final attempts must reuse the same recovery state without accumulating resources or releasing a lease twice. [Flush contract](https://github.com/Xilinx-CNS/onload/blob/master/src/include/etherfabric/vi.h) · [Zpkt stop and finalization](zpkt/INTERFACE.md#stop-and-finalization)

Destroy run resources in dependency order and discard stale events before creating a fresh run. A caller-held packet keeps its address and bytes across stop, failed start and restart. At finalization require returned buffers, free registrations before backing, release the PD and driver handles, close the ingress guard, then retire the child from Env. Exercise finalization before allocation, after allocation without a start, after a partial start, and after repeated runs.

## Alternatives and scope

Using the existing DPDK plugin with a suitable driver is the comparison point for deployment and performance. The reason to build `libZpkt_sf` is direct use of AMD's packet API within the existing Zpkt ownership model. Passing vendor receive references directly to applications would violate the writable-buffer contract on Express. A preallocated copy has a measurable cost and bounds the provider's buffer lifetime independently of the application. Keep per-socket steering updates, shared event-queue handoff, explicit multi-queue scheduling, advanced Tx modes and checksum-offload negotiation as separate decisions after the first verified implementation. To switch backends, drain service, return buffers, finalize the old Env, and open the replacement through its configured module path.
