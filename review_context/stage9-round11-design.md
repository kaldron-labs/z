# Zutcp: user-mode TCP over AF_XDP

* **Author:** hrogers-kaldron
* **Status:** Final candidate — implementation decisions resolved; confirmatory readiness review in progress
* **Date:** 2026-11-10
* **Predecessor:** [Concepts brief](./concepts_brief.md)

## Overview

Introduce `zutcp`, a user-mode TCP implementation derived from `zquic`, for short FIX order, execution, and market-data messages. Zutcp implements the existing `ZiMxPlugin` interface and is registered with `ZiMultiplex` while stopped, before start and I/O use. Applications continue to use `ztcp` and `ztls` through ZiMultiplex; those modules are not modified for this work. An installed Zutcp plugin supplies user-mode transport, while an mx without that plugin retains its regular kernel transport. This supersedes the earlier Hub::utcp proposal; backend selection remains fixed for the active mx lifetime.

The starting point is a verbatim copy of `zquic` into `zutcp`, followed by global renaming of identifiers and names with case preserved. Remove encryption, the TLS handshake, connection migration, and multiple-stream facilities from the renamed copy; exclude QIR integration from Zutcp. Retain one bidirectional stream per connection and the existing link/stream application model. TLS remains available through `ztls` above the selected TCP backend.

QIR means the open-source [QUIC Interop Runner](https://github.com/quic-interop/quic-interop-runner). The Zquic integration lives in [zhttp/interop](./zhttp/interop/README.md), with integration coverage in zhttp/itest, because its HTTP/3 (H3) tests require Zhttp. QIR is external test infrastructure, not a QUIC transport mechanism to delete from the copied runtime. Existing Zhttp QIR facilities remain; Zutcp will use TCP-specific testing instead.

Create and independently test `zxdp` to encapsulate AF_XDP packet I/O. It supplies Rx and Tx ring abstractions and integrates reception with `ZmScheduler`. Its configuration follows `ZmRing_::Params`, including low-latency spinning. The packet-I/O boundary must accommodate future backends without making their implementation part of this work.

Preserve Zquic's dedicated Rx/Tx roles and thread-exclusive state. As a ZiMxPlugin, Zutcp runs directly on the multiplexer's Rx and Tx threads from the first working phase, configured exclusively through ZiMxParams. It has no separate protocol threads or thread selectors. Threads serve multiple connections, not one thread pair per connection.

The first Zutcp deliverable is a working client and server exchanging application bytes through `veth` and `zxdp` on one host, after copying, renaming, and removing excluded features. There are no TCP-specific protocol modifications in this milestone: it deliberately implements an intermediate protocol that is neither QUIC nor TCP. Incrementally convert that working client/server to TCP, verifying communication throughout the conversion.

## The Problem

The target workload sends streams of short FIX messages, each individually small enough to fit in one Ethernet packet. The current kernel TCP path incurs syscall and network-stack work. The motivating hypothesis is that a user-mode implementation can reduce that work and improve both message latency and throughput for this workload. The benefit must be demonstrated against the kernel path under comparable traffic and resource conditions; the design does not assume a measured improvement in advance.

Applications need to retain ordinary address resolution, address types, and host networking while selecting a different TCP data path. `ZiResolver`, `ZiIP`, and the kernel network stack continue to serve their existing roles. Packet steering and host-stack coexistence still need explicit design; ordinary address resolution alone does not settle them.

A conversion directly from copied QUIC code to interoperable TCP would change packet I/O and transport behavior at once. The intermediate client/server milestone establishes a working packet path and retained transport behavior before TCP-specific changes, so each subsequent change can be checked against an executable baseline.

## Goals

* Request zero-copy packet I/O from the kernel and preserve an implementation that does not obstruct it: register application Zi::IOBuf backing for NIC use and avoid userspace payload staging or configuration that prevents supported zero-copy operation. Actual kernel-side copying and capability selection are the responsibility of the kernel/NIC driver and outside this work's scope.
* Independently demonstrate `zxdp` packet exchange, ring ownership, scheduler wakeups, and clean shutdown before Zutcp integration.
* Deliver the first Zutcp client/server over single-host `veth`/`zxdp` using the copied protocol after excluded-feature removal, without requiring TCP interoperability or introducing TCP-specific mechanisms.
* Preserve a working client/server as the implementation is converted incrementally to TCP.
* Implement SACK, timestamps with PAWS, window scaling, DSACK, RACK-TLP, ECN, and TCP Fast Open. Decide separately which extensions peers must negotiate.
* Establish eventual interoperability against the independent kernel TCP stack over single-host veth loopback, including reliable ordered byte delivery, connection lifecycle, flow control, and recovery from loss and reordering.
* Support both single-host `veth` testing and two hosts connected over Ethernet. Use physical-host measurements to evaluate the hardware packet path.
* Implement Zutcp as a ZiMxPlugin registered on mx before start, preserving the existing Ztcp/Ztls-facing contracts without modifying those modules.
* Preserve the Zquic application model: application-created accepted links, one automatically created bidirectional stream per connection, `streamed(...)` notification, and stream-level `process(RxStream &)`. Accepted Fast Open data may be delivered before `connected()`; that callback signals completed establishment.
* Follow repository shard ownership, retained-buffer lifetime, bounded-memory, and asynchronous teardown rules. Avoid input rejection solely for conformance policing while retaining checks needed for message integrity and safe protocol operation.
* Preserve the copied transport's dedicated Rx/Tx thread model, functionality placement, and thread-exclusive data ownership through every intermediate protocol. Port TCP mechanisms into that model using explicit owner-directed handoffs.
* Evaluate latency and throughput for the target short-message workload against the kernel backend using Clang release builds and author/agent optimization guided by -pg profiles. Record measurements without imposing hard CPU budgets, throughput targets, or latency-percentile acceptance thresholds at this stage.

## Non-Goals

* MPTCP, TCP-MD5, and TCP-AO.
* Encryption or a TLS handshake inside Zutcp; this does not exclude TLS through `ztls`.
* Connection migration, multiple streams per connection, or QIR in Zutcp.
* Switching backends during the active mx lifetime.
* Modifying ztcp or ztls, adding Hub::utcp, or introducing a second backend interface alongside ZiMxPlugin.
* Implementing DPDK or vendor-specific packet-I/O backends in the initial delivery.
* TCP or QUIC wire interoperability for the first intermediate-protocol milestone.
* Preserving message boundaries through TCP: applications must continue to frame FIX messages across arbitrary receive-buffer boundaries.

## Technical Plan (Architecture)

### Preserve the Zquic Rx/Tx ownership model

Preserve the copied association between Rx/Tx functionality and thread-exclusive state, including applicable cache-line separation. Zutcp protocol and packet I/O run directly on mx's Rx/Tx owners from phase 1 onward, configured through ZiMxParams. Remove copied HubParams rxThread/txThread selectors during initial adaptation after the mandatory mechanical copy/rename. Control/startup and logging do not become protocol-data owners.

The starting ownership map comes from the copied implementation, including the explicit Rx/Tx sections and assertions in [ZquicStream.hh](./zquic/src/ZquicStream.hh) and [ZquicLink.hh](./zquic/src/ZquicLink.hh). Adapt protocol semantics within those ownership boundaries. Do not consolidate the connection into a shared mutable TCP control block accessed from either thread.

The ownership table applies in every phase. Packet I/O and Zutcp share the corresponding mx owner. Keep the Rx-to-Tx and Tx-to-Rx handoffs required by state ownership; introduce no independent Zutcp worker pair or packet-I/O-to-protocol queue.

| Owner | Functionality and exclusively owned state to preserve or adapt |
| --- | --- |
| Rx thread | Packet reception/parsing, receive sequence/reassembly state, receive credit and application delivery, incoming connection acceptance, and receive-side lifecycle. Own AF_XDP RX consumption and FILL publication. |
| Tx thread | Application transmit processing, packet construction/submission, retained sent data, sender acknowledgment/SACK processing, retransmission/loss timers, RTT estimation, congestion control/pacing, peer-advertised send credit, and transmit-side lifecycle. Own AF_XDP TX publication and COMPLETION consumption. |

Receiving an ACK on Rx does not move sender recovery to Rx. Parse and capture its bounded evidence, then post processing to Tx, which updates its own sent-data, recovery, RTT, and congestion state. Similarly, Rx owns receive-window/reassembly state and hands the information needed to advertise a window or send an ACK to Tx; Tx does not inspect Rx-owned structures while constructing a packet. Hand off peer window updates to the Tx owner of send credit. Tx completion/close events affecting Rx are posted back to Rx rather than mutating receive state directly.

Keep cross-thread entry points as thin dispatchers, with owner-only implementations and thread assertions, following [IO.md](./docs/IO.md). Transfer original buffer references and fixed metadata; use destination-owned storage/handles for larger handoffs. A retained packet can cross threads without copying payload, but a reference does not grant concurrent mutation of its metadata, headers, or protocol state. Maintain explicit ownership and in-flight retirement rules. The selected contended allocator free slists are a deliberate cross-thread reclamation mechanism; they do not authorize cross-thread ring or connection-state access.

Keep protocol timer callbacks and telemetry observation consistent with the same ownership map: execute mutable work on its owner and observe through the established snapshots/enumeration contracts. Preserve the Rx-drain then Tx-drain shutdown sequence. Do not introduce connection locks, shared mutable queues, or arbitrary atomics as substitutes for the copied shard boundaries.

For every conversion slice, record the source QUIC function/state owner, its TCP counterpart, and required handoffs. Verify owner assertions while the actual client/server runs under bidirectional traffic, ACK/loss processing, timer expiry, backpressure, observation, and teardown. This makes preservation of the thread model part of each phase's exit evidence, rather than a later optimization. Evaluate the resulting latency under OQ-7; thread isolation is a design commitment, not evidence of a performance result by itself.

### OQ-1: Establishment after deleting encryption and TLS

Deleting TLS does not delete the transport's need to identify a connection, learn its peer's receive limits, and determine whether the peer received its response. The natural remainder is an Initial/response/ACK exchange using the copied transport mechanisms. It does not require a second, independently designed hello protocol or TCP SYN semantics. This is a proposed derivation for the intermediate milestone, not a claim that standard QUIC supports an unencrypted mode.

#### What is already independent of TLS

* [ClientBootstrap](./zquic/src/Zquic.hh) creates initial destination and source connection IDs.
* The server routes an unknown Initial to `App::accepted(...)`, obtains the application's link, and retains it; see the server's `routeLong_()` and `accept_()` in [Zquic.hh](./zquic/src/Zquic.hh).
* [ServerBootstrap](./zquic/src/Zquic.cc) records the client's source ID and original destination ID, chooses a server source ID, and supplies bootstrap metadata. Its current reset-token generation and other excluded-feature dependencies must be removed along with those features; transport identity does not require them.
* Packet numbers, ACK ranges, retained control output, loss recovery, and PTO provide transport delivery evidence and recovery independently of TLS message contents.
* The lifecycle already separates Starting, Handshaking, and Established in [ZquicLink.hh](./zquic/src/ZquicLink.hh). A pending setup state can remain after the TLS machinery is deleted.

The current coupling is explicit: `readyToEstablish_()` requires `oneRTTReady()` and installed transmit/receive AppData secrets. Peer parameters also live behind `m_crypto.peerParams()`, and client startup emits TLS output to cause the first Initial. Removing the cryptographic code without replacing those dependencies leaves a silent client or a connection that never becomes established.

Transport parameter serialization itself is reusable: `Crypto::encodeParams()` and `decodeParams()` merely delegate to `TransportParams::encode()` and `decode()`. Preserve the required transport values and codec outside the deleted Crypto object. Standard QUIC carries those values in TLS; their new placement is an intermediate-protocol decision. [QUIC transport handshake](https://www.rfc-editor.org/rfc/rfc9000.html#section-7), [TLS integration](https://www.rfc-editor.org/rfc/rfc9001.html#section-8.2).

#### Natural packet exchange

```text
Client                                                   Server
  |                                                         |
  | Initial: original DCID, client SCID,                     |
  |          ack-eliciting setup content ------------------->| accept link
  |                                                         | choose server SCID
  |<---------------- Initial response: DCID = client SCID,   |
  |                  SCID = server SCID, ACK of client setup,|
  |                  ack-eliciting setup content             |
  |                                                         |
  | ACK of server setup response -------------------------->| setup confirmed
  |       (may be carried with first stream data)            |
  |                                                         |
  |<============ retained single-stream protocol ===========>|
```

The server retains the mapping from the client's original destination ID so retransmitted client Initial packets reach the same pending link. The client adopts the server's source ID for subsequent destination addressing. Bind the connection to its peer tuple; keeping bootstrap IDs at this milestone does not retain connection migration.

Proposed completion semantics are asymmetric, as in many transport exchanges: the client has peer-response evidence when it receives the server's setup response; the server has response-receipt evidence when its setup output is acknowledged. These become establishment events in place of TLS completion. Prepare the sole stream and preserve the native link/stream callbacks while mapping the plugin path onto the existing ZiConnection callback contract described in OQ-5. Exact internal publication sequencing belongs in implementation planning, not a new Ztcp/Ztls API. Initial-stage application early data is not required by this proposal; the previously accepted TCP Fast Open behavior applies when Fast Open is implemented later.

Do not require an acknowledgment of the final pure ACK. If that ACK is lost, the server's outstanding ack-eliciting response drives recovery, and the client acknowledges the repeated setup output. Retransmissions use the copied packet-number/recovery conventions, with new packet numbers for retransmitted content. A duplicate Initial, response, or confirmation must not recreate the link, reset parameters, recreate the stream, or repeat `connected()`. Apply setup deadlines and drain pending output on failure.

Packet receipt is transport delivery evidence, not cryptographic peer authentication. With protection removed, define the plaintext packet layout without header-protection sampling or AEAD tag assumptions and retain accidental-corruption detection covering setup metadata and application bytes. An AF_XDP transport constructs and checks its packet integrity explicitly; packet I/O alone does not replace the deleted authentication tag.

#### Selected policy: OQ-1.A, plaintext transport parameters

The author selected OQ-1.A. Both endpoints exchange the surviving encoded TransportParams directly in plaintext Initial payloads, install peer limits before allowing dependent transmission, and use the existing ACK/recovery mechanisms to complete setup. The fixed-profile option below is retained only as a considered alternative.

| Option | Mechanism | Trade-off and failure condition |
| --- | --- | --- |
| **OQ-1.A — Retain parameter exchange** | Put the surviving encoded TransportParams directly in a bounded, explicitly identified plaintext Initial payload. Initial packet context distinguishes this from normal frame payload; no TLS records or CRYPTO byte stream remain. Both parameter-bearing setup packets elicit ACKs. | Preserves independent endpoint settings and tests receive-credit initialization. Requires a small temporary payload-format change and recovery retention for those values. Fails if the server assumes receipt of a header means the parameter payload was processed, or if bounds/credits are installed after application transmission begins. |
| **OQ-1.B — Fixed initial profile** | Configure an explicitly matching initial profile for the paired test applications. Send existing PING frames in the Initial and its ACK-bearing response to make setup ack-eliciting. No parameter payload is needed. | Uses existing frame types and minimizes the intermediate wire change. Cannot negotiate independently configured receive limits; it fails when peer profiles differ or when bootstrap defaults leave zero transmit credit. Document and test the shared profile rather than assuming equality. |

OQ-1.A preserves the mandatory copy/rename/delete sequence and contains no TCP-specific modifications. Establishment follows the existing Initial and ACK machinery; the transport-parameter exchange replaces its TLS carrier.

Acceptance tests must cover normal setup, loss of each flight, duplicate setup packets, a lost final ACK, setup timeout, consistent connection-ID routing, exactly-once callbacks, differing receive limits, and data exchange on the sole stream. No kernel TCP or standard QUIC interoperability is expected at this stage.

### OQ-2: Kernel coexistence following Yasukata's work

The author selected alignment with Yasukata's implementation. Follow the same-NIC coexistence mechanism in [bench-iip](https://github.com/yasukata/bench-iip/blob/master/README.md#optional-sharing-a-network-interface-with-the-kernel-space-network-stack), together with [iip-af_xdp](https://github.com/yasukata/iip-af_xdp/blob/master/main.c), rather than requiring a separately addressed or dedicated NIC.

#### Source mechanisms to preserve

* Keep the interface configured through the kernel. Yasukata's backend obtains the interface MAC and IPv4 address using a control socket and `SIOCGIFHWADDR`/`SIOCGIFADDR`. Continue to use the framework's existing address and resolution facilities; this observation does not require duplicating those facilities or ioctl wrappers where Z already supplies them.
* Load a custom XDP classifier. The documented sharing example matches a TCP destination port, redirects matching traffic through the XSK map, and returns `XDP_PASS` for other traffic. This keeps other host services and kernel network functions available on the same interface.
* Preserve explicit classifier ownership: Yasukata's library-based example uses `XSK_LIBBPF_FLAGS__INHIBIT_PROG_LOAD` and registers the created sockets in the selected XSK map. The selected direct AF_XDP/BPF implementation performs that map registration itself and must not replace an existing classifier implicitly.
* Keep the mapping from receive queue to AF_XDP socket explicit. Yasukata's benchmark configures queue count to match its packet worker count; adapt queue ownership to the Z scheduler shards rather than copying its private thread implementation.

For the first Zutcp milestone, classify the intermediate protocol's actual traffic, including its UDP-shaped envelope if retained, rather than matching TCP before TCP exists. At the eventual TCP stage, classify server listener endpoints and client return traffic. Continue ordinary `ZiResolver`/`ZiIP` use on the control path. No userspace replacement for DNS is needed.

#### Details to finish within this selected model

The referenced coexistence example is a server demonstration with a fixed destination port and fixed IPv4 offsets. It establishes the architectural direction; it does not settle active-client endpoint allocation, all packet forms, or shutdown races. Complete those mechanisms explicitly:

* Extend packet selection to configured local addresses/listener ports and active-client endpoints, with bounded parsing of actual header lengths and supported address families. Do not redirect all traffic on a queue merely because an XSK exists.
* Define exclusive ownership of selected endpoints against kernel sockets. The reference's port filter is not itself a kernel port reservation. Select the concrete enforcement mechanism during interface planning.
* Inspect and specify the neighbor/next-hop path for active opens and any reply path not covered by receive-side addressing. The backend's local interface-address queries do not constitute route lookup or neighbor resolution; the sharing example passes nonselected discovery traffic to the kernel. Do not claim that a new kernel-neighbor cache integration already exists in the reference.
* Install socket/map and selection state before exposing an endpoint or sending its first packet. Define how late packets are handled during close and after socket failure, avoiding unintended kernel TCP responses for connections still owned by Zutcp. Yasukata's sample passes on an unavailable XSK entry; evaluate that fallback against live-connection ownership rather than adopting it silently.
* Attach/detach only the program and map state owned by this backend, preserving unrelated interface users.

#### Selected shutdown contract: Z framework I/O teardown

Follow [IO.md: Teardown](./docs/IO.md#teardown) and [FRAMEWORK.md: Timer Teardown](./docs/FRAMEWORK.md#timer-teardown). The author explicitly selected this contract; it is not an architectural alternative.

1. Prevent new application submissions, connection admission, ingress dispatch, and timer/I/O work for the stopping owner. Cancel its timers with `ZmScheduler::del`, guard late callbacks, and wake any polling or blocked worker. Quiesce selection of further packets into the retiring runtime without prematurely returning still-owned connections to kernel TCP. Post a continuation to the Rx owner to drain previously admitted work.
2. In the Rx continuation, finish or cancel pending receive processing and arrange retirement of retained receive buffers through their owning return paths. Drain late timer callbacks on their execution shards. Post the teardown continuation to the Tx owner; do not inspect or mutate Tx-owned state from Rx.
3. In the Tx continuation, drain or cancel pending sends and complete the backend's kernel/DMA retirement protocol before releasing packet backing. Complete teardown and release object ownership only when callbacks, queued work, and dependent resources can no longer reference the retiring objects. Use further asynchronous continuations where hardware retirement or buffer returns are still pending; do not block a shard waiting for them.

Keep the scheduler and required wake mechanisms operational through these continuations. Unregister wake functions only after their consumers are quiescent. Release XSKs, maps, ring mappings, and UMEM in an order that prevents kernel or queued userspace access to released storage. A connection teardown must not destroy packet resources still shared by other connections; final backend teardown owns that release. Do not keep owners alive by adding reference counts to populous buffers or timer callbacks where the framework requires drained raw back-pointers. Only main-thread callers may block waiting for overall completion.

The three phases settle shutdown organization. OQ-2.4.A selects endpoint-level exclusion around that sequence. Normal TCP close/TIME-WAIT behavior must remain distinct from destruction of the packet-I/O backend.

#### Considered alternatives and selected answers

The table preserves the considered alternatives within Yasukata's selected shared-interface model. The selected answers are OQ-2.1.B, OQ-2.2.B, OQ-2.3.A, and OQ-2.4.A; the other alternatives are not part of the plan.

| Stable ID | Option A | Option B |
| --- | --- | --- |
| **OQ-2.1 — Local endpoint ownership** | Hold a kernel socket bound to each claimed local address/port, without performing kernel TCP connect/listen for user-mode traffic. Use the appropriate protocol socket for the intermediate UDP envelope and eventual TCP. Keep it through endpoint retirement. This uses kernel allocation to detect conflicts but costs descriptors and needs explicit bind/reuse/wildcard tests; the bound socket does not itself suppress kernel replies to leaked packets. | Allocate user-mode client ports from an operator-reserved range and explicitly assign server ports. Exclude the range from kernel automatic assignment and enforce exclusive use operationally. This reduces control sockets but adds deployment policy. `ip_local_reserved_ports` does not prevent explicit binds, so it alone cannot guarantee exclusivity. |
| **OQ-2.2 — Active-open neighbor resolution** | Use kernel route/neighbor control APIs to find the outgoing interface, next hop, and MAC, request resolution when missing, and receive asynchronous updates. Keep ARP/ND packets on the kernel path. This preserves ordinary networking but requires a control-plane adapter and bounded waiting when discovery fails. | Supply static neighbor entries through normal kernel configuration for the directly connected host/veth topology, then read them for initial transmission. This simplifies the first deliverable but requires operator/test setup and fails when neighbor addresses change without configuration updates. It is not a complete dynamic-neighbor solution for eventual general deployment. |
| **OQ-2.3 — Classifier granularity** | Redirect selected local address/protocol/port endpoints and demultiplex connections in Zutcp. This closely follows Yasukata's port-based sample and keeps BPF state proportional to endpoints. It cannot divide ownership among kernel and user-mode peers sharing the same endpoint. | Redirect server listener matches plus exact active-client/established flow matches, with explicit precedence. This narrows capture but adds per-flow map lifecycle and races to test. Initial server traffic must still match a listener before a flow exists. |
| **OQ-2.4 — Late packets and unavailable XSKs** | Keep endpoint-level selection active with a quiesced discard action while its userspace owner drains; retire the exclusion only when endpoint/transport lifetime permits reuse. This is simple for exclusively owned ports but can temporarily prevent reuse of the whole endpoint. | Replace retiring flow entries with bounded per-flow discard tombstones while retaining listener and endpoint ownership separately. This allows finer reuse but adds retirement state and must handle late Initial/SYN packets as well as established traffic. |

**OQ-2.1 resolved: Option B.** Configure explicit user-mode server ports and a user-mode client-port range. Operators exclude those ports from kernel automatic allocation using `ip_local_reserved_ports`, preserving existing reservations when applying configuration. Zutcp allocates client ports within its configured range and detects exhaustion without unbounded searching or allocation. Deployment policy prohibits explicit kernel binds and overlapping assignments by independently managed user-mode instances to these ports. The sysctl alone does not enforce those prohibitions. Do not create placeholder bound sockets as the reservation mechanism. Document the reservation scope and verify it in deployment/test setup; active opens require an explicitly configured reserved client-port range. Use an Rx-owned bounded occupancy bitmap/cursor scan and fail once on exhaustion. Operators assign non-overlapping ranges/ports to independently managed instances.

**OQ-2.2 resolved: Option B.** Configure static kernel neighbor entries for the veth or directly connected Ethernet peers and read them to obtain the next-hop MAC before active transmission. Retain ordinary kernel-configured interfaces, routes, ZiResolver, and ZiIP. The test fixture installs its own entries; physical-host deployment supplies the corresponding entries. Missing or unusable entries produce an actionable connection/setup failure rather than an implicit dynamic-neighbor fallback. The deployment must update entries when link-layer addresses change. Dynamic neighbor discovery by Zutcp is outside this selected configuration.

**OQ-2.3 resolved: Option A.** Match configured local address, IP protocol, and reserved server/client ports in the XDP classifier. Redirect matching traffic to the appropriate queue's XSK and demultiplex connections inside Zutcp. BPF selection state is endpoint-based, not per connection. Unselected traffic passes to the kernel. Match the intermediate protocol's actual envelope in the first milestone and TCP only after wire conversion.

**OQ-2.4 resolved: Option A.** Retain endpoint-level exclusion during owner shutdown. Quiesce owned endpoints to discard further packets before draining their runtime, retaining the exclusion until endpoint/transport retirement permits reuse. XSK unavailability for an owned endpoint must not cause fallback to kernel TCP. Apply this fence to the stopping endpoint owner, not to unrelated live connections using the same backend. Individual connection closes still use the transport's close and late-packet rules while their endpoint remains active. Do not add per-connection BPF tombstones as the shutdown mechanism.

Unrelated traffic continues through the kernel. Retirement follows explicit transport/owner events and any required protocol deadlines, not periodic background garbage-collection scans. Specify the exact retirement event in implementation planning rather than inventing an arbitrary timeout.

Yasukata's [iip implementation](https://github.com/yasukata/iip/blob/master/main.c) supplies another useful distinction for OQ-2.2: passive-open code extracts the received Ethernet source address, and active-open APIs accept link-layer addresses. That explains how server replies can work without a generic route/neighbor adapter; it does not solve the first outgoing packet for our active client. Preserve that distinction when adapting the design. The kernel's [neighbor `use`/`managed` controls](https://man7.org/linux/man-pages/man8/ip-neighbour.8.html) provide concrete mechanisms to investigate for Option A. [IP socket binding](https://man7.org/linux/man-pages/man7/ip.7.html) and [reserved-port semantics](https://docs.kernel.org/networking/ip-sysctl.html#ip-variables) support the OQ-2.1 alternatives.

Attach/detach only backend-owned programs and map entries, preserving unrelated users of the interface; this is a requirement common to the options. The library/program-loading mechanism remains part of OQ-3, not a second competing OQ-2 decision.

Verify owned user-mode traffic alongside an unrelated kernel service on the same interface, with both incoming server connections and outgoing client connections. Include configured/missing static neighbors, reserved-port allocation and exhaustion, endpoint classification, map/socket unavailability, duplicate or late packets, and stop/restart. Verify three-phase teardown both while idle and with retained buffers, pending Tx, timers, and queued continuations outstanding.

### OQ-3: Proposed packet-I/O interface and execution model

This design follows Yasukata's separation of packet I/O from the transport, while retaining Z framework buffer, shard, and scheduler contracts. OQ-3's architectural decisions are resolved. The API details below are aligned with the ZiIOBuf and ZiMultiplex source inspected on 2026-11-09; remaining concrete declarations belong in Detailed Implementation.

**OQ-3.3 resolved: Option B.** Use direct kernel BPF syscalls to create and populate maps and load the endpoint classifier, rather than a libbpf loader dependency or external program provisioning as the runtime setup mechanism. Implement attachment and detachment through the kernel interfaces and track backend-owned resources explicitly. Preserve existing interface users and the selected OQ-2 endpoint/quiescing policy. #### Proposed normalized API

Expose a device/queue binding and packet operations, without TCP connection state. The following operation names describe responsibilities; final declarations belong in Detailed Implementation.

* **Configuration:** require the application's `mx` and use its scheduler and configured Rx/Tx slots. Reuse existing compile-time IOBuf payload geometry and cumulative layer framing requirements; obtain each pool's requested buffer count from the `count` argument to mx's allocator factory, forwarded to ZiMxPlugin::allocator. Device/queue binding, descriptor-ring capacity mapping, waiting controls, and required copy/zero-copy capabilities complete backend configuration. Do not introduce a parallel payload-geometry or reserve-count configuration scheme. Resolve and validate all immutable resources before starting packet service.
* **Receive:** acquire a bounded batch of packet references and metadata, then release descriptor slots independently of retained packet backing. Provide lengths and packet metadata needed by the copied transport without exposing libxdp descriptors.
* **Transmit:** allocate application output from registered Tx backing with cumulative layer headroom/tailroom, construct the application payload once in that backing, add protocol framing in its reserved space, and submit the same backing in a bounded batch on Tx. Do not gather application bytes into a second packet buffer. Report accepted versus backpressured work without hidden unbounded queuing. The transport retains responsibility for retransmission bytes and peer acknowledgments.
* **Completion and recycling:** retire kernel-held transmit frames on Tx; return received-frame ownership to Rx only after final reference release. Provide counters for pool depletion, full rings, drops, invalid descriptors, driver wakeups, and outstanding kernel/application ownership.
* **Lifecycle:** asynchronous init/start/stop/final responsibilities with the selected three-phase teardown and explicit completion. Endpoint registration and quiescing implement OQ-2's selection policy; Zxdp does not parse TCP connection state to decide when a connection is established.

Reuse `Zi::IOBuf` and the existing `Zi::IOBufPluginAllocator` adapter directly for retained packets and ranges. Its capacity, data pointer, offset, length, allocator, and owner fields already supply the required per-buffer metadata; do not introduce a duplicate packet-metadata wrapper or treat metadata placement as an open architectural question. Implement the backing provider through `Zi::IOBufPlugin`. It derives frame identity from the backing address and registered layout and owns reserve/free-frame accounting. Do not keep a naked span after retiring its frame or copy received payload into a staging array just to cross shards. Final releases return frames through the existing allocator callbacks; they do not keep the connection alive by adding references contrary to framework lifetime rules. See [ZiIOBuf.hh](./zi/src/ZiIOBuf.hh).

#### Registered backing, Rx stubs and heap framing

Use the updated Zi contracts. Zi::IOBuf::Registered and registered() identify registered backing; Initial/initial() are obsolete buffer API names. Preserve QUIC's unrelated Initial packet terminology in the intermediate protocol.

| Interface | Required contract | Zutcp/Zxdp use |
| --- | --- | --- |
| Zi::IOBufAllocator__ | alloc(unsigned size, bool registered=false) and free(ptr, size, bool registered=false) | Registered backing is supplied/recycled by the owning UMEM region; unregistered Rx allocations use ZmVHeap. |
| Zi::IOBufAllocator | allocBuf(bool registered=true, void *owner=nullptr, uint32_t length=0) returns ZmRef<IOBuf> | Registered Tx requests acquire actual fixed backing; registered Rx context requests return a metadata-only stub. |
| Zi::IOBufPlugin | alloc(uint32_t, bool registered) / free(uint8_t *, uint32_t, bool registered) | Reuse the base/derived allocator hierarchy and intrusive slists. A buffer's current registered() flag selects registered recycling versus heap release. |
| Zi::IOBufPluginAllocator | Preserve supplied buffer type/owner, explicit registered flag and truthful runtime capacity | Support non-null registered Rx stubs without treating their intentionally absent storage as allocation failure. A stub has size/skip/length zero and no builtin array. |
| ZiMxPlugin::recv(ZiConnection *) | Rx-owned notification that the connection's receive context has been updated | Zutcp inspects the connection's current context rather than caching a potentially replaced stub. A rearm notification alone is not received data. |

For registered Rx context requests, create the expected ZiIOBuf-derived metadata object without acquiring a UMEM slot. Keep its requested allocator/owner; do not expose the template Size as writable capacity while data_() is null. A callback is invoked for received data only after backing/view fields have been installed. For registered=false framing allocations, allocate heap backing from the outset and construct a non-builtin, unregistered object; the heap block must reach the provider's registered=false free path. Generic constructor flag inference must not mistake externally allocated heap storage for an inline builtin array.

**Allocation result contract.** allocBuf(registered=false, ...) returns a heap-backed ZiIOBuf and cannot return nullptr for heap exhaustion. ZmHeap/ZmVHeap handle out-of-memory through ZmHeapFail; dependents do not add null checks, retry loops or alternate allocation paths for this case. Callers need a null-result check only if they may request registered=true. In Zutcp's registered Rx case the result is a valid metadata-only stub; intentionally absent backing is not an empty ZmRef. Keep this object-allocation contract separate from ensure's status/overflow checks and the fatal attempt to grow an existing fixed registered Tx buffer.

For registered Tx requests, initial UMEM depletion still returns an empty reference promptly and ZiTxStream retains its existing writer-failure semantics. Growing an existing registered non-Rx buffer remains fatal before requesting replacement backing. The author's current Ztcp allocTxBuf_ and Ztls rxTxBuf/allocTxBuf/txBuf now guard empty allocation results; consume those updates, with no duplicate Ztcp/Ztls source changes planned. Rx framing obtains unregistered heap backing directly or by ensure on a zero-capacity registered stub; neither path consumes another finite UMEM slot merely to hold a message. Heap failures use ZmHeapFail and do not return nullptr to dependents.

Rx growth of an already attached packet uses alloc(size, registered=false): ensure copies readable bytes into heap backing, returns the old frame through free(..., registered=true), then clears Registered on the same ZiIOBuf object. Future growth/final release uses heap callbacks. Its atomic object reference count remains the lifetime authority through that transition. No extra buffer-lifetime counter or hidden registered-pool exhaustion fallback is introduced.

**Selected recycling mechanism — mandatory for every arena.** Adopt the lock-free MPMC LIFO slist in [ZmHeap.hh](./zm/src/ZmHeap.hh:209), lines 209–233, specifically alloc_()/free_() with the entire `if (ZuLikely(m_info.sharded))` branch excluded. Maintain a separate atomic free head for each per-allocator UMEM arena, including Rx, application Tx and Zutcp control arenas. Overlay each free frame's next pointer on its unused payload backing; do not add a per-frame list-node prefix or a separate return-node allocation. Reuse the existing contention protocol: allocation claims the atomic head using its low-bit marker before reading the next pointer and publishing the new head; free writes the previous head into the returned frame and publishes it by compare-and-exchange, retrying against concurrent operations. Preserve the source algorithm's atomic ordering and alignment requirements. Ignore its sharded fast path, as directed by the author, and do not copy the outer heap-allocation fallback into the fixed UMEM reserve.

The allocator slist is the explicit ownership handoff: final release may call `free_()` from another shard, and `alloc_()` obtains exclusive ownership from the same reserve. No additional cross-shard return queue is needed. This shared allocator operation does not grant non-owner access to RX, FILL, TX, or COMPLETION rings or to mutable protocol state. Only the Rx owner publishes acquired receive frames to FILL; only Tx owns its transmit/completion rings. Overlay the free link only after all application/transport references and any kernel/NIC use have retired. Recover the frame's canonical backing address before recycling; never place the link at an advanced readable offset. Initialize the lists before publication/start and retain their allocator/UMEM lifetime through all outstanding frame releases.

**OQ-3.4 resolved: fixed UMEM backing with no builtin storage.** UMEM-backed Zi::IOBuf instances have no builtin payload storage; the initial backing and capacity come from their registered frame. Reuse the existing compile-time payload-geometry specification without instantiating an unused builtin payload array. Tx uses ZiTxStream's fixed-capacity and cumulative framing limits so jumbo output rolls into additional buffers before any individual buffer would exceed that capacity. Attempting to grow a Tx buffer beyond its initial UMEM-backed allocated capacity is a fatal internal error. It must not trigger heap reallocation, frame replacement, a payload copy, or a recoverable allocation-failure fallback. Enforce this invariant in release builds as well as debug builds, including indirect grow paths through generic buffer helpers.

Rx receives Ethernet packets as-is into UMEM backing sized from the MTU and required link-layer geometry. The UMEM allocation itself never expands. Higher layers such as Ztls may grow the same ZiIOBuf by replacing its backing with ZmVHeap storage, gathering a complete TLS record and decrypting it in place using the current contiguous receive path. This returns the old UMEM slot immediately through registered=true free; the resulting heap-backed buffer is not destined for further Zxdp submission. Zutcp may retain packet references/ranges for reassembly before delivery; upper-layer growth occurs after receive ownership has passed upward, with no kernel use or retained raw ranges depending on the old backing. Concrete UMEM allocator declarations and final-release recycling operations belong in Detailed Implementation; reuse the existing IOBuf metadata rather than designing additional per-buffer bookkeeping. The adapter's architecture and growth policy are settled. Reserve exhaustion is separately handled as bounded backpressure and is not the same condition as a fatal attempt to grow an already allocated frame.

Keep the boundary backend-neutral by using packet references, capacities, queue bindings, and ownership operations rather than exposing UMEM offsets or XSK objects to Zutcp. Supporting another backend later does not require implementing a DPDK abstraction or backend registry now. The choice of static or indirect dispatch at that future boundary is not settled by this proposal.

#### Zero-copy buffer flow and existing layering

**Selected geometry and scheduler dependency.** Use the existing IOBuf compile-time sizing, capacity/alignment specification, and layer headroom/tailroom requirements as the source of payload geometry. UMEM allocation/registration adapts to that geometry; it does not define another application-visible packet geometry. Kernel-required chunk alignment, registration limits, and descriptor offsets remain backend details that must preserve the specified usable capacity. Define the compatible layout and diagnose unsupported configurations rather than silently changing the payload contract.

**Updated pool-count contract.** Applications request each pool's desired number of buffers through `mx->allocator<Type, Base, Size, MaxSize, Align, HeapID>(count)`. Mx forwards count with the requested geometry to `ZiMxPlugin::allocator(type, size, maxSize, align, count)`. The current factory default is `ZiIOBuf_DefltCount` (1024 unless overridden at compile time). Preserve each allocator request's count alongside its geometry, so differently sized application pools can be provisioned independently. Zutcp's separate control allocator also has an explicit pool count. This supersedes the earlier design using ZiMxParams::rxBufSize/txBufSize as user-mode pool counts; those fields retain their kernel socket-buffer meaning. Do not derive a per-allocator count from them or add a parallel application pool-count interface.

**Framing budgets are derived, not configured.** Zxdp contributes the Ethernet framing geometry. Zutcp adds the IP and TCP framing geometry above it. The existing layer machinery deterministically sums the required headroom/tailroom from the actual protocol stack; these budgets are not another operator setting or an architectural choice. Account for supported protocol variants/options in that calculation, reserving the required capacity before application payload construction and using the actual encoded lengths for each packet. For the initial QUIC-derived intermediate milestone, derive its surviving transport framing in the same way; use TCP geometry once the transport is converted. Pass the accumulated geometry to the existing compile-time IOBuf allocation contract without introducing an independent UMEM payload specification.

Both `zxdp` and `zutcp` require an `mx`, even when no kernel UDP/TCP data-path socket is used. `ZiMultiplex` inherits ZmScheduler; use that existing scheduler and lifecycle context rather than creating a second independent scheduler. Kernel resolver/control-plane services can remain available through normal framework facilities. A user-mode Hub still supplies its mx during initialization, and mx must outlive the dependent packet servicing and asynchronous teardown.

The author requires zero-copy transfer of Zi::IOBuf-backed payload storage between the application and packet I/O. For AF_XDP, allocate the packet storage in userspace and register it as UMEM; UMEM registration is not an allocation of application payload storage by the kernel. Allocate application output directly from the registered Tx reserve, with the complete framing budget supplied through the existing ZiRx/ZiRxStream and ZiTx/ZiTxStream layers. Add intermediate QUIC-derived or eventual TCP, IP, and Ethernet headers and any software-required trailers in reserved space. Change buffer ranges/offsets on receive rather than moving payload bytes.

The existing code provides part of this mechanism. H3's `DataStream` in [ZhttpH3.hh](./zhttp/src/ZhttpH3.hh) derives from ZiTxLayer, adds nine bytes of headroom for its own DATA frame header, and prepends that header with `rewind()`. ZiTxLayer accumulates lower-layer headroom/tailroom, and ZiRxLayer similarly accumulates receive geometry. This supports payload-preserving layering into the QUIC stream.

Current Zquic deliberately retains plaintext stream buffers and encrypts gathered input ranges directly into a final packet backing in `sendProtShortPkt_`. H3 buffers are inputs to individual QUIC streams, while QUIC packetization can combine data from several streams into one packet. This separate output backing serves both encryption and packet consolidation; it is appropriate for QUIC and does not imply an avoidable payload-copy stage. Encryption writes the final packet directly rather than first copying plaintext into a staging buffer. Source-to-destination encryption need not impose a meaningful penalty relative to in-place encryption; the relative performance depends on the actual packetization and crypto implementation and is not established by this design discussion. [Zquic's guidelines](./zquic/GUIDELINES.md) explicitly require that architecture while retaining plaintext for recovery. Its receive path already retains slices of the decrypted packet.

The author adopts a different packetization target for Zutcp because encryption and inter-stream consolidation are removed. Preserve the existing layer geometry and retained-buffer machinery, accumulate transport/IP/Ethernet framing space beneath the application, and submit the original application payload backing directly. This is an adaptation to the single-stream unencrypted transport, not a repair of QUIC's encrypted packet construction. Segmentation and retransmission still need explicit range and header-lifetime treatment to maintain this property.

Existing generic helpers also have copy paths: `ZiTxStream::append(buffer)` copies when adoption lacks capacity or framing space, and `ZiRxStream::extract()` can gather/split into new storage. For the admitted zero-copy Zutcp path, provide compatible registered backing and geometry and use retained ranges so these paths do not silently move payloads. Explicit application writes from external memory remain distinct from copying an already constructed buffer inside the transport.

Keep submitted backing stable while the kernel/NIC owns it, including headers: retransmission cannot rewrite a header still in flight. Retain the same application payload backing until transport retirement as well as DMA retirement permit release. Independent descriptor/control metadata may be copied; application payload bytes must not be repacketized through a staging buffer. Specify partial acknowledgments, retransmission ranges, segmentation, variable header sizes, and insufficient-room behavior without assuming all received FIX messages preserve packet boundaries.

**Selected Tx layout: one buffer supplies N packets.** Reserve a table of N complete Ethernet/IP/transport headers in the buffer's headroom, followed by the contiguous upper-layer payload (including TLS record bytes where applicable). Each packet consists of its own header slot and an unchanged payload slice, submitted with scatter/gather descriptors. Small output remains the N=1 case. This author decision supersedes the earlier buffer:packet 1:1 restriction and the overlapping-header proposal. No bulk payload copy or overwrite is required, and independent packets can be queued without waiting for preceding packet completions. The concrete calculation and owner boundary are specified in DP-5.

**Selected byte-range recovery policy: resend bracketing original packets.** TCP ACK/SACK processing remains byte-sequence based. When recovery identifies missing bytes whose boundaries lie inside previously sent packets, select the original packet ranges covering the missing interval and resend their headers plus retained payload slices. Duplicate bytes at the interval's edges are acceptable; do not split or copy payload merely to match the interval exactly. A packet record references its original buffer and payload range; several such records may reference the same buffer. Retain the backing while any packet's bytes still require transport retention or any DMA descriptor references it. Partial acknowledgment or completion of one slice does not release the whole allocation. Retain selectively acknowledged data as required for SACK reneging. Refresh a packet header only after preceding DMA use of that header retires; do not advance the application's skip field to manufacture retransmission packets.

This differs from current Zquic, which can split retained stream-frame ranges into newly encrypted packets. Keep the selected original-packet recovery policy while allowing multiple packet records to share one unchanged backing allocation. The policy remains valid if intermediary processing changes receiver-visible segment boundaries.

Verify backing identity and unchanged payload addresses across layer preparation, submission, receive slicing, and retained retransmission. Test the geometry boundaries that could otherwise trigger generic helper copies. Verify that setup requests zero-copy and that our buffer layout, registration, submission, and configuration do not prevent it when supported. Kernel/driver-side copying is outside the implementation's acceptance policy; veth remains the required functional harness.

| **OQ-3.2.A — Separate Rx/Tx reserves** | Partition registered packet storage into independently sized Rx and Tx frame reserves. Rx owns RX/FILL; Tx owns TX/COMPLETION. Final releases from other shards enqueue returns to the appropriate owner. **OQ-3.2 resolved: Option A.** Partition registered packet storage into separately sized Rx and Tx frame reserves, using each allocator request's count and existing compile-time IOBuf geometry. Rx manages its receive supply and RX/FILL rings; Tx manages its transmit supply and TX/COMPLETION rings. Final releases from another shard return frames directly to their original reserve's contended intrusive free slist, using the selected ZmHeap non-sharded alloc_/free_ protocol. Do not implement a combined Rx/Tx reserve or dynamic capacity borrowing between them. Separate reserves can be logical partitions of the same registered UMEM; they do not require separate registrations. Concrete allocator declarations and the AF_XDP-compatible physical layout will be specified in Detailed Implementation.

**ZO-1 resolution — Separate control-packet storage.** Within the Tx allocation model, Zutcp owns a separate pool of small registered buffers for ACKs, window updates, establishment/close output, and other protocol control messages. Its reserve and intrusive free slist are independent of application-payload pools; any software ring used for that pool has the same explicit owner discipline. Application allocations cannot consume control-packet backing, and control generation does not depend on an application buffer becoming available or on piggybacking. This allocation separation does not require a separate hardware TX/COMPLETION ring: those rings retain their existing per-queue SWSR ownership.

Applications can request multiple allocators with different compile-time buffer geometries tuned to their messages, such as per-table replication buffers in Zdb. Honor the geometry supplied by each allocator factory request; do not impose one application payload size or combine every application allocator and transport control allocation into a single exhaustible free list. Each pool has fixed-capacity backing and its own recycling/accounting, using the existing Zi::IOBuf metadata and selected ZmHeap free-slist protocol. The control pool's small-buffer geometry includes the deterministically required framing and control content. Map these pool geometries to an AF_XDP-compatible registered layout in Detailed Implementation; logical buffer size does not by itself specify the physical UMEM chunk layout.

Tx owns control construction, scheduling, submission, and completion retirement. Reserve isolation protects control backing, but shared descriptor pressure must also permit pending control output to progress as completions arrive; application backlog must not monopolize every subsequent submission opportunity. Keep this bounded and owner-managed. All control backing follows the same in-flight stability and final-release rules as payload backing. Specify the control allocator's count/default, count-to-layout/ring-capacity mapping for each allocator request, descriptor arbitration, and reporting in Detailed Implementation, preserving the Rx/Tx reserve separation and avoiding payload copies or heap fallback.

**design-1-2 resolution — Port receive admission to bounded UMEM capacity.** Reuse Zquic's existing receive byte-credit checks, packet-backed reassembly, delivery and credit-retirement mechanisms. Extend their admission accounting to the fixed registered pool's available frames, including transport/application retention and consumption across connections. Byte credit alone does not establish available packet backing. Preserve enough free/replenishable ingress capacity for incoming ACKs/window updates and for admitting the gap-filling data needed to release an out-of-order suffix.

Perform retention admission before committing the corresponding receive/acknowledgment state. Under pool pressure, refuse and recycle additional out-of-order input that would consume the protected capacity, preserving the current slice's acknowledgment semantics. Retained application buffers remain valid until released; never return their backing to FILL prematurely. In the QUIC-derived slices, do not discard stream data already acknowledged under QUIC's retained-data contract. Account for application-held frames when applying receive backpressure while preserving control ingress. Concrete frame bounds, gap-filling allowance, admission priorities and shared-pool accounting belong in Detailed Implementation, integrated with the existing receive path rather than a second reassembly/flow-control engine.

Verify this adaptation from phase 1 onward: fill reassembly behind a missing segment with small packets and multiple connections, then receive the missing data and progress without externally releasing the queued suffix or timing out the connection. Include reverse-direction ACK/window traffic and retained application slices. Preserve exact data delivery, bounded memory, owner-only ring publication and zero-copy backing throughout.

Size and verify the reserves independently: retained receive slices can exhaust Rx even when Tx has free capacity, and delayed completions can exhaust Tx while Rx remains available. Report each condition separately and apply bounded backpressure. Preserve the descriptor-versus-payload and DMA-versus-transport lifetime rules below.

Verify application-pool exhaustion with held/unsent and unacknowledged payload buffers, including after DMA completion, while the working pair still exchanges ACKs, window updates and close traffic from the control pool. Cover differently sized application allocator requests, independent recycling/accounting, full descriptor rings and subsequent control progress, and teardown with both pool classes in flight. Apply this verification from the first intermediate protocol onward, using that slice's equivalent control messages.

Extra application sending threads dispatch to Tx. Additional NIC queues create additional explicitly owned bindings. Configuration must verify that traffic can actually reach the selected queue; a software XSK map is not a general substitute for NIC queue steering.

#### Proposed scheduler and waiting implementation

**OQ-3.6 resolved: follow mx's plugin integration with configurable `rxQuantum`.** ZiMxParams already supplies `rxQuantum(unsigned)` and its getter, and ZiMultiplex exposes `rxQuantum()`; use them directly. The current default is `ZiMxParams::RxQuantum`, which is 8, and mx startup rejects zero or values greater than INT_MAX. The former epollQuantum naming is historical: the current kernel epoll loop also uses rxQuantum as its maximum event count. For the plugin, it bounds packets read before returning to the scheduler's main loop. Count packets across all descriptor batches in that servicing turn; do not reset it for each batch. Returning when fewer packets are ready is allowed. Continuous readiness must not bypass the configured limit, including in low-latency mode. Ensure pending reception is serviced again through the existing mx scheduler pattern after returning. Do not add another rxQuantum parameter, default, or validation policy.

Bind packet servicing to mx's configured isolated Rx/Tx slots. ZiEventLoop remains the integration reference, but mx already owns the scheduler wake registration: startup installs `wakeFn(rxThread(), ...)` calling `wakeRx()` and queues the first `rx()` invocation. Mx's `rx()` delegates to `plugin->rx()`. Implement that hook rather than installing a second wake owner on mx's Rx slot. Its return permits other scheduler work; budget exhaustion must leave a subsequent servicing turn queued so pending packets are not stranded.

Implement the plugin's wake notification inside its own receive wait/spin mechanism. Mx's `wakeRx()` queues a new mx `rx()` callback while running and calls `wake()`; mx's `wake()` delegates to `plugin->wake()`. That non-Rx-thread hook must interrupt the current plugin `rx()` and make it return, including while blocked, spinning with `ll(true)`, or processing continuous traffic. Preserve notifications across the check-to-wait boundary and repeated wakes so queued callbacks remain serviceable. No new scheduler-wake composition interface is needed for this plugin integration.

In ordinary mode, spin for the configured count, recheck readiness and pending wake state, and wait on AF_XDP readiness together with the scheduler wake source. Use a zero timeout to mean no periodic wait timeout, consistently with ZmRing; scheduler/timer wakeups must still interrupt it. Handle AF_XDP need-wakeup separately from scheduler wakeups, invoking the required driver progress operations rather than assuming a ring spin drives NAPI.

Use each allocator request's IOBuf geometry and count as the pool-sizing inputs; the count is supplied through mx's existing allocator factory rather than through a new backend configuration interface. Specify how those inputs determine valid power-of-two descriptor-ring capacities, including the factory default and handling of zero counts, before implementation. Report effective capacities and diagnose invalid or overflowing requests without adding a conflicting payload-size convention. In the inspected ZmRing implementation, `cpuset` controls memory binding through hwloc; preserve that meaning for packet storage rather than silently treating it as a thread-affinity setting. Configure worker affinity through mx scheduler thread parameters separately.

**OQ-3.7 resolved: request zero-copy and do not obstruct it.** Zxdp and Zutcp must request zero-copy through the kernel interface and preserve backing, registration, descriptors, and configuration that permit it. If the NIC driver supports zero-copy for that setup, our implementation must not prevent it. Whether kernel-side zero-copy actually occurs is the kernel/NIC driver's responsibility and outside this work's scope. Do not impose a separate capability-enforcement, verification gate, or initialization-failure policy merely because hardware zero-copy is unavailable, and do not force copy mode for the veth harness. The earlier requirement to force XDP_ZEROCOPY and fail if unavailable is withdrawn; exact API setup must follow this request-without-obstruction contract rather than treating the flag spelling as an independently accepted policy. Keep the required veth milestone and physical-host measurements. Ring-capacity formulas, zero/default handling, and device/queue configuration are implementation details derived from the accepted contracts, not unresolved architectural alternatives.

The detailed ring comparison and independent test requirements below apply to the selected direct-ABI and separate-reserve architecture. Acceptance requires packet progress, bounded ownership, scheduler/timer progress, and shutdown in both low-latency and ordinary waiting modes before Zutcp integration.

### Zxdp ring buffers and ZmRing comparison

This subsection records the ring-buffer requirements requested by the author. OQ-3.1.B selects direct AF_XDP access and OQ-3.2.A selects separate Rx/Tx reserves; the complete transport architecture is still being drafted. Give [Yasukata's AF_XDP backend](https://github.com/yasukata/iip-af_xdp/blob/master/main.c) primary weight as an implementation precedent for ring servicing, references to packet buffers, completion handling, and driver wakeups. Adapt that precedent to the repository's separate Rx/Tx ownership and scheduler rules.

#### Concurrency and entry representation

Every AF_XDP ring is single-writer/single-reader (SWSR), also called single-producer/single-consumer (SPSC). This applies independently to RX, TX, FILL, and COMPLETION. Sharing packet storage does not change their concurrency contract. [AF_XDP ring specification](https://docs.kernel.org/networking/af_xdp.html#rings).

| Property | ZmRing | AF_XDP rings |
| --- | --- | --- |
| Purpose | Application communication inside a process | Transfer packet-buffer ownership between userspace and the kernel |
| Concurrency | SWSR, MWSR, SWMR, or MWMR | SWSR for every individual ring |
| Entry storage | Fixed- or variable-sized application messages stored in the ring | Fixed-size descriptors referring to separate packet storage in UMEM |
| Capacity unit | Bytes of ring storage | Descriptor entries; ring entry counts must be powers of two |
| Multiple readers | Broadcast to attached readers | One consumer, with no broadcast facility |
| Publication | Reserve/write with `push()`, publish with `push2()` | Reserve slots, populate descriptors, submit |
| Consumption | `shift()`, process, `shift2()` | Peek descriptors, process, release |
| Waiting and termination | Ring spin/block controls, wakeups, and EOF | External waiting and driver wakeups; application-defined stop/drain lifecycle |

ZmRing's multiple-reader behavior is broadcast, not competing workers dividing messages. Its source explicitly recommends sharding writes to multiple MWSR rings for unicast. See [ZmRing.hh](./zm/src/ZmRing.hh). AF_XDP has no native MWSR or multiple-reader mode. A normalized Zxdp API must not imply otherwise.

The ring layout is part of the kernel ABI. Preserve its required publication ordering and barriers, whether using [libxdp's ring helpers](https://github.com/xdp-project/xdp-tools/blob/main/headers/xdp/xsk.h) or a separately selected direct implementation. Do not substitute ZmRing's control block, message headers, or cursor algorithms for the mapped AF_XDP layout.

#### Four rings and their owners

| Ring | Producer | Consumer | Entry contents and meaning | Proposed Zxdp userspace owner |
| --- | --- | --- | --- | --- |
| FILL | Userspace | Kernel | UMEM frame address offered for future reception | Rx shard |
| RX | Kernel | Userspace | Received-packet descriptor with frame address, length, and options | Rx shard |
| TX | Userspace | Kernel | Descriptor identifying packet bytes to transmit | Tx shard |
| COMPLETION | Kernel | Userspace | Address of a frame returned after kernel processing | Tx shard |

Separate Rx and Tx threads can operate these distinct rings without making any ring multi-writer or multi-reader. Multiple application producers dispatch work to the owning Tx shard through framework queues; they do not directly publish to the same AF_XDP TX ring. Returned receive frames similarly reach the owning Rx shard through an explicit recycling path, rather than arbitrary threads writing FILL.

This mapping follows the existing shard rules and selected separate-reserve model. The contended intrusive allocator slist is selected for recycling; concrete allocator declarations and free-list rules are specified in DP-2 through DP-4. Its atomic free operations can run across shards, while each AF_XDP ring remains owner-only. The combined-reserve alternative in [design options](./design_options.md#3-af_xdp-rings-ownership-waiting-and-scheduler-integration) is not selected.

#### Descriptor lifetime versus packet lifetime

Advancing a consumer index releases descriptor slots. It does not necessarily release the packet bytes those descriptors reference.

For reception, copy the small descriptor metadata into the retained buffer representation as necessary, then release the RX slot. Keep its UMEM frame unavailable to FILL while reassembly, the stream parser, or any retained application slice still references those bytes. Final payload release makes the frame eligible for recycling. Refilling FILL early permits incoming packets to overwrite retained data.

For transmission, keep submitted packet backing stable until the kernel returns the frame through COMPLETION. A completion returns ownership; it does not independently prove successful transmission and is not a peer acknowledgment. Transport-retained byte ranges remain live until acknowledgment, cancellation, or connection teardown releases them. If the transport and DMA use the same backing, satisfy both lifetimes before reuse. If they use different backing, retiring the packet frame must not release the separate retransmission source.

Never offer the same frame concurrently for reception and transmission, or to multiple FILL rings. Track the frame's ownership explicitly and keep all pools and pending-return paths bounded. An empty FILL ring, full TX ring, stalled completion path, or application retaining input must have defined backpressure and diagnostics rather than unbounded allocation. [AF_XDP ownership and corruption guidance](https://docs.kernel.org/networking/af_xdp.html).

#### Shared UMEM and sharding

Each AF_XDP socket retains its own RX and TX rings. Sockets sharing UMEM on the same device/queue tuple share a FILL/COMPLETION pair. Sharing UMEM across different device/queue tuples requires a pair per unique tuple. Every shared pair still needs one userspace owner for each ring. Merely creating another socket or process does not authorize concurrent access to that pair. [Shared UMEM specification](https://docs.kernel.org/networking/af_xdp.html#xdp-shared-umem-bind-flag).

Shared UMEM also does not decide which socket receives a packet. That follows the XDP program and device/queue binding. Receive scaling therefore needs an explicit mapping among NIC queues, XSK map entries, sockets, and owning shards. Frame allocation must coordinate storage ownership even where the descriptor rings are separate.

#### Familiar configuration with backend-specific mechanics

Expose the configuration model in [ZmRing_::Params](./zm/src/ZmRing.hh): `size`, `ll`, `cpuset`, `spin`, and `timeout`. Its current defaults are size 0, `ll(false)`, an empty CPU set, 1000 spins, and a 1 millisecond timeout. These are reference defaults, not a selection of AF_XDP capacities or placement policy.

* `size`: distinguish ZmRing byte capacity from AF_XDP descriptor counts and UMEM byte capacity. Define the normalized unit and its mapping before fixing the public API; never silently treat bytes as descriptor entries. RX, TX, FILL, COMPLETION, and packet storage have distinct capacities even if one convenience setting supplies their defaults.
* `ll`: spin on ring readiness in low-latency mode while still servicing scheduler wake requests and shutdown. This configures userspace waiting; it does not guarantee kernel/driver receive progress.
* `spin`: in ordinary mode, bound readiness checks before entering the backend's wait path, following the ZmRing control model.
* `timeout`: preserve millisecond units and document zero/infinite-wait behavior. A wait must remain interruptible by scheduler work and shutdown; it cannot delay transport timers beyond their deadlines.
* `cpuset`: retain the familiar placement control, with its relationship to scheduler thread affinity, UMEM placement, and NIC queue ownership specified explicitly. It is not a native AF_XDP ring flag.

Use [ZiMultiplex.cc](./zi/src/ZiMultiplex.cc)'s plugin rx/wake dispatch and existing scheduler wake registration directly, with [ZiEventLoop.cc](./zi/src/ZiEventLoop.cc) as the integration precedent. Use [ZiLog.cc](./zi/src/ZiLog.cc) for consume/process/retire and draining; its worker is a dedicated ZmThread. AF_XDP has no ZmRing EOF marker, so implement stopping as explicit owner state, removal of further ingress, wakeup of any waiter, and asynchronous draining consistent with [IO.md](./docs/IO.md).

Process bounded packet batches and yield through the scheduler's continuation mechanism to allow queued work and due timer callbacks to execute. Check wake requests under continuous traffic and while spinning on an empty ring. The blocking path needs a race-safe readiness recheck and a wake source integrated with its wait, so enqueued work cannot be stranded between checking readiness and sleeping.

Distinguish userspace spinning from NAPI busy polling and `XDP_USE_NEED_WAKEUP`. With need-wakeup enabled, check the relevant producer-ring flags and invoke the required kernel wakeup operation when needed. Spinning alone can otherwise leave reception or transmission stalled. A syscall-free steady state is a performance aim, not a guarantee of AF_XDP operation. [Driver wakeup contract](https://docs.kernel.org/networking/af_xdp.html#xdp-use-need-wakeup-bind-flag).

### OQ-4: Peer extension profile

Implementation scope remains SACK, timestamps/PAWS, window scaling, DSACK, RACK-TLP, ECN, and TCP Fast Open. The author selected **OQ-4.B**: none of these peer extensions is mandatory for connection establishment. The table retains OQ-4.A as a considered, unselected alternative.

| Mechanism | OQ-4.A: require SACK and timestamps | OQ-4.B: optional peer extensions |
| --- | --- | --- |
| SACK | Advertise permission and require it from the peer; refuse unsupported connections with a specific local diagnostic. | Advertise permission; use SACK when available and cumulative-ACK recovery otherwise. |
| Timestamps/PAWS | Offer timestamps and require negotiation; use PAWS and timestamp RTT handling. | Offer timestamps; if absent, use timestamp-free RTT/retransmission rules and do not assume PAWS protection. |
| Window scaling | Offer and use when negotiated. An absent option means scale zero, not connection refusal. | Same. |
| DSACK | Generate/process duplicate reports under SACK rules; do not require the peer to generate them. | Same when SACK is enabled. |
| RACK-TLP | Local recovery strategy, enabled on every accepted connection because SACK is required. Keep timeout/persist behavior needed for progress. | Use with SACK; implement separate loss recovery for connections without SACK. |
| ECN | Offer/negotiate support and use only when negotiated. Absence does not reject the connection. | Same. |
| TCP Fast Open | Support cookie/data exchange and use when available and requested by the application. Retain ordinary establishment if absent or declined. | Same. |

OQ-4.A eliminates the no-SACK recovery path and makes timestamp protection available on every accepted connection. It narrows interoperability to peers permitting those features; a configured modern peer with either feature disabled cannot connect. This is a supported profile decision, not input rejection solely for syntactic conformance.

OQ-4.B admits peers without those extensions, with additional recovery, RTT ambiguity, and sequence-lifetime paths to implement and verify. Verify fallback recovery, RTT handling, and sequence-lifetime behavior; the implementation must not assume SACK or PAWS when negotiation omits them. Specify and verify timestamp-free high-rate sequence reuse under the selected profile.

RACK-TLP is not separately negotiated with the receiver. It requires SACK and local per-transmission timing, but does not require the wire TCP Timestamp option. DSACK is not a separately negotiated capability bit either. [RFC 8985](https://www.rfc-editor.org/rfc/rfc8985.html#section-4). Window scaling and timestamps have their own handshake rules. [RFC 7323](https://www.rfc-editor.org/rfc/rfc7323.html). TCP permits basic interoperability without these common options, so requiring them must be documented as this implementation's selected peer profile. [RFC 9293](https://www.rfc-editor.org/rfc/rfc9293.html#section-3.2.1).

In both profiles, parse options with bounds sufficient for integrity and safe operation, accept supported encodings without conformance-only policing, and skip unsupported optional options where their wire format permits it. Do not confuse offering an option with successful negotiation. Preserve packet-buffer retransmission and bracketing recovery; selecting a peer profile does not reopen those decisions. Peer extension negotiation starts at the TCP conversion stages, not the first intermediate-protocol milestone.

**OQ-4 resolved: Option B.** Accept absent SACK/timestamps without an extension-based connection refusal. Use SACK and RACK-TLP when available; supply cumulative-ACK loss recovery when SACK is absent. Use timestamp RTT handling and PAWS only when negotiated, with timestamp-free RTT/sequence-lifetime handling otherwise. Window scaling defaults to scale zero; DSACK processing/generation follows SACK availability, and ECN/Fast Open absence uses ordinary operation. Detailed Implementation must specify and verify both negotiated and extension-absent paths, including timeout/persist behavior and Fast Open fallback, without silently assuming an optional feature was enabled.

**Exit evidence:** Inject loss, duplicates, reordering, partial ACKs and ACK loss. Verify exact application delivery, retained-buffer bounds, sequence accounting, RTT behavior, and independent NIC/peer retirement. The unchanged application/telemetry fixtures from phase 2 continue to work.

### DP-1 — ZiConnection plugin close and public state integration

The current ZiMxPlugin declares pure virtual send(ZiConnection *), disconnect(ZiConnection *, bool peer), and close(ZiConnection *, bool peer), all Tx-thread operations. ZiConnection::disconnect and close marshal to Tx; disconnect_1 and close_1 now delegate to the installed plugin and return before the kernel shutdown/close paths. Both preserve the peer argument. This supplies plugin dispatch without kernel shutdown/close. The public up() state still needs the narrowly inventoried owner-state helpers below, because the current delegation returns before clearing ZiConnection private direction flags. Earlier DP-1.A/B scope alternatives are superseded by the supplied API update.

Add public direct-owner helpers ZiConnection::txDown_() and rxDown_(), declared in ZiMultiplex.hh and implemented in ZiMultiplex.cc. txDown_ asserts mx Tx and atomically clears m_txUp; rxDown_ asserts mx Rx and atomically clears m_rxUp. They are idempotent, perform no socket operation, do not notify the application or unregister a connection and never set a closed object up again. New connections use new objects. Do not expose writable atomics or make up() infer lifetime from mutable context pointers.

Zutcp calls txDown_ when it enters closing and stops accepting new application sends, before close/disconnect notification; already admitted data/recovery continues through its own transport state. Rx calls rxDown_ when receive closure becomes effective after preceding ordered data, or during its abort/teardown continuation. Peer-originated closure uses those same owner-directed transitions. Since up() requires both flags, it becomes false when either direction closes and stays false through final notification. A half-close does not itself cancel the other direction's permitted transport work. Keep the existing kernel path unchanged; these helpers are the plugin's explicit route for the public base-state contract.

Existing Ztcp/Ztls link telemetry reads ZiConnection::rxCalls/rxBytes/txCalls/txBytes directly, so separate plugin telemetry objects do not populate those counters. Add public direct-owner helpers countRecv_(unsigned n) and countSend_(unsigned n) in ZiMultiplex.hh/.cc. Each asserts its Rx/Tx owner, increments that direction's call counter once and adds n bytes, with no callback, socket operation or protocol state transition. Zutcp calls countRecv_ once immediately before each receive I/O completion delivering n newly accepted ordered TCP-stream bytes to the current context; do not count pure ACK/control/duplicate bytes or recount buffered bytes on callback rearming. Call countSend_ once for each positive local send-progress result before exposing that result through ZiTxContext. It counts accepted TCP-stream bytes once, not packet headers, DMA completions, probes or retransmissions. TLS counters at this layer count serialized TLS stream bytes, as kernel TCP does, not decrypted application bytes. n==0 produces no plugin progress completion/count. Grouping can differ from kernel syscall boundaries; totals and the documented I/O-completion meaning remain accurate.

Update plugin connection snapshots and unchanged Ztcp/Ztls link telemetry assertions through the same real getters. Keep wire-packet/retransmission/control counters separate in transport telemetry. Existing kernel executedRecv/executedSend counter updates stay unchanged; never call these whole kernel completion functions from Zutcp merely to update counters.

Implement all three hooks in ZutcpMx. Graceful disconnect drains according to the transport's close contract; abrupt close cancels pending application work and retires the transport safely. Keep completion, once-only application notification, connection-registry removal, late timer suppression and original-buffer/NIC retirement consistent with the copied owner-directed lifecycle. Repeated calls must not duplicate notification or retirement. Do not fall through to a kernel shutdown/close operation for a plugin connection.

ZiMultiplex::rx already delegates to the installed plugin. The normal Ztcp path uses the exposed receive context, and the plugin supplies connection telemetry objects. These mechanisms do not require the previously proposed blanket receive/completion/telemetry extension. Use the current interface and verify actual application paths in phase 2.

Exercise public ZiConnection::disconnect and close through both native/plugin-backed endpoint fixtures, including up() before/during/after closure, pending data, outstanding NIC completion, peer close, repeated close and stop. Verify dispatch occurs on mx's Tx thread, the peer value is preserved, callbacks occur once on their owner, and kernel handling remains available on the no-plugin path. Put isolated plugin mapping checks in zutcp/test/ZutcpPluginTest.cc and real endpoint checks in zutcp/itest/zutcpplugintest.cc; no separate Zi source/test target is required solely to implement DP-1.

### DP-2 — Per-allocator pool regions and payload-overlay recycling (adopted)

For each registered Tx/control allocator request, take the requested usable size S, derive the headroom H and tailroom T required by its stack, and record a dedicated pool region with count slots of that adjusted geometry. Zxdp assigns its backing within the owning instance's shared-registration arena at start, as specified in DP-3. Zutcp adds TCP and IP overhead, and Zxdp adds Ethernet overhead. Existing upper-layer reservations, including TLS record overhead where supplied by Ztls, are not added a second time. For phase 1, derive the surviving intermediate/UDP framing instead of inserting TCP headers before the first milestone.

The sizing calculation is W = H + S + T, slotStride = alignUp(W, requiredAlignment), poolBytes = count * slotStride. For Tx, H includes the K-slot header table derived in DP-5, rather than one lower-stack header. Check the addition/multiplication/alignment operations for overflow. Account explicitly for required kernel frame/headroom alignment and page rounding, preserving the requested usable capacity and logical count; page padding does not create more allocatable slots. Framing space is derived from actual supported headers/options and software-required trailers, not an application-selected extra budget. Rx must additionally accommodate the full received Ethernet packet for the configured MTU, as already specified.

Each physical Ingress or registered Tx/control provider owns its adjusted geometry, count, lifetime, reserved region and free head within the shared arena. Application Rx stub providers own no UMEM payload region, as specified in DP-17. Do not enlarge every application's backing to the largest unrelated allocator request. The small control allocator gets its own correspondingly sized region and free head. The earlier DP-2.A/B choice between one common padded layout and compact pools is superseded by this author-specified per-allocator sizing contract and DP-3's deferred shared registration.

**Required free-list algorithm:** use exactly the non-sharded alloc_()/free_() protocol in ZmHeap.hh:209–233. Allocation loads the head, returns null if empty, retries while the low-bit claim marker is set, claims the head with cmpXch, reads the overlaid next pointer only after the claim, and publishes that pointer as the new head. Free waits out the claim marker, writes the observed head into the returned slot's payload, and CAS-publishes the slot, retrying when necessary. Preserve the existing atomic ordering/alignment protocol. Do not substitute the sharded branch, a mutex, an additional ring or return queue, a separately allocated list node, or a different untagged stack algorithm.

The next-pointer storage overlaps unused payload bytes only while the slot is free. A slot enters the free list only after all application/transport references and kernel/NIC use retire. Allocation transfers exclusive slot ownership; final free can execute on another shard. This explicit contended allocator operation does not permit non-owner access to AF_XDP rings or mutable protocol state. Do not copy ZmHeap's outer heap-allocation fallback into these fixed arenas.

**AF_XDP registration boundary:** one Zxdp instance collects its allocator requests and creates a shared-registration arena at start. A physical Ingress or registered Tx/control request defines a reserved pool region, not a separate registration or queue; metadata-only application Rx requests define no payload region. Preserve the request's geometry/count and the kernel-valid frame layout; do not bind a conflicting second UMEM pool to the same device/queue. Instances have independent allocator/provider state and explicitly compatible queue bindings.

The adapter must preserve the distinction between application usable size and the actual backing geometry. Verify initial IOBuf data_/skip/size, layer reservations, full wire range, retransmission origin and canonical free address together: allocating more bytes alone does not reserve headroom in the metadata or prevent an upper layer from writing into it. Preserve the single original backing and existing metadata; record any required geometry propagation in the same file-level inventory rather than adding a hidden staging copy.

### DP-3 — Multiple Zxdp instances and deferred shared registration (adopted)

Zxdp supports multiple instances. Each instance owns its pending allocator list, shared-registration arena, pool-region layout, mapped rings, binding state and lifecycle. Zutcp creates an instance and forwards allocator requests as dependents make them; no request count, total byte size or arrival order needs to be predicted. The previous DP-3.A/B registration alternatives are superseded by this author-selected lifecycle.

An allocator request creates a provider object immediately and appends its requested type, usable size, derived headroom/tailroom, alignment and count to that instance's intrusive pending list. The Zxdp::Allocator base object embeds/inherits its own ZmList linkage using the existing framework intrusive-list pattern; no separate request wrapper, external list node, std::list or copied request queue is permitted. Each Zxdp instance owns its list head. The same provider object carries the pending request and, after successful start, its assigned pool-region metadata. The provider implements the existing Zi::IOBufPlugin interface and remains valid while pending, but it does not yet supply packet backing. Before successful start, registered backing acquisition returns null without substitute storage or I/O-owner blocking. Metadata-only registered Rx stubs and registered=false heap framing remain available under DP-6. The application's factory-created IOBufAllocator can exist during initialization; packet data construction requiring its backing follows successful start.

Include the internal Ingress provider in this pending layout and apply DP-17 to metadata-only application Rx requests, which reserve no UMEM payload region. Zutcp start calls its Zxdp instance's start before publishing endpoints or allowing transport sends. Zxdp traverses the complete intrusive pending list, skips metadata-only Rx stub providers, calculates each physical Ingress/Tx/control pool's adjusted stride and byte requirement, places its region at the next valid aligned offset, sums the regions with checked arithmetic and page-rounds the final allocation. Allocate that one arena, register it as a single UMEM for the instance's binding, initialize each region's independent overlaid slist, and initialize the mapped rings. Retain the provider objects and their embedded linkage through startup/failure/retry; successful activation updates their state rather than copying requests into separately allocated active nodes. Pool offsets follow the recorded list order; correctness cannot depend on a particular order of dependent initialization.

Only after the arena, registration, rings, binding and required steering are ready does the instance publish providers as ready and complete start successfully. Backing addresses become available at that point. If any setup step fails, roll back unpublished resources, leave providers unready, preserve the pending requests for diagnosis/retry, and report failure through the existing asynchronous start result. Do not expose a partially initialized allocator set.

Keep allocator request registration serialized while stopped, consistent with ZiMultiplex::allocator and plugin registration. The per-start set is finalized by entering start. No running-instance arena extension is introduced. Multiple instances may initialize and start independently; they must not share a global pending list, allocator head, arena base or mutable ring cursors. Validate compatible device/queue assignments before publication and report conflicting ownership explicitly. Separate logical instances do not authorize independent kernel pools on an already owned queue.

Shared interface steering resources, where needed for same-NIC coexistence, retain explicit per-instance endpoint/map ownership and attachment lifetime. Stopping one instance must not remove another's map entries, detach a still-used classifier, release its arena, or disturb its traffic. Data-path state remains owner-thread exclusive; setup resource coordination must not introduce shared connection or ring mutation.

Stop uses the adopted ingress/timer prevention and Rx-then-Tx drain. Providers and arena storage remain valid through outstanding backing references and callbacks; allocator objects already retained by mx still survive stop. Re-start/new pending requests must honor that lifetime: do not resize, relocate, unmap or reinterpret live backing. Kernel registration may retire after kernel access ends, independently of retained application references. Implement DP-12.1–12.2 retirement/reuse transitions and verify them with retained references; deferred initial allocation does not permit premature teardown.

Verify different request counts, sizes and arrival orders across at least two independent instances, provider behavior before start, complete region sizing at start, start failure rollback, count-preserving pool isolation, independent stop, and repeated start/stop. Use the exact non-sharded ZmHeap slist in every region. No virtual alias assembly or allocation of a fixed aggregate region before requests arrive is required by this design.

### DP-4 — Intrusive allocator base and Zutcp specialization (adopted)

Define Zxdp::Allocator as the concrete base implementing Zi::IOBufPlugin. The allocator object itself carries the framework intrusive-list node; it is both the pending request record and the active provider. It owns immutable requested geometry/count, its assigned instance/region information, readiness/retirement state, the atomic overlaid free-list head and allocation diagnostics. Do not create a second Pool/request wrapper or separate linkage allocation around it.

Define Zutcp::Allocator as a derivation of Zxdp::Allocator. It computes and retains TCP/IP/current-intermediate framing policy, delegates Ethernet/storage layout to the base, and supplies the payload/wire interpretation needed by the transport. The existing Zi::IOBufPluginAllocator holds the resulting provider through Zi::IOBufPlugin as it does today. Use one Zi::IOBufPlugin base subobject through the inheritance chain; do not add a parallel provider hierarchy or duplicate the free-list implementation.

Construct the derived allocator completely before adding it to the owning Zxdp instance's intrusive pending list. Instance registration takes ownership of the concrete base pointer only after construction succeeds. The base must support destruction of a derived allocator through that owner; lifetime is tied to the instance, mx-retained adapters and outstanding callbacks. Start activates that same allocator object by assigning its region and initializing its free head. Failed start leaves the same object pending for retry; pointers already returned to Zi adapters remain stable.

The base implements registered-frame acquisition/final release with the exact selected non-sharded ZmHeap slist; context-stub construction acquires no frame. Zutcp specialization adds geometry/policy and uses those operations; it does not override reclamation with another ring, lock or heap fallback. Backing acquisition before activation/after it is disabled returns null; metadata-only Rx stub construction does not require active backing. Rx registered=false requests use ZmVHeap with the prescribed alignment and capacity policy; Existing registered Tx growth is rejected before replacement allocation. Route free by the supplied registered flag: true returns UMEM backing to the selected slist, false frees ZmVHeap backing for Rx/framing. Free callbacks for still-live backing remain valid while the provider is retiring. These states and callbacks do not permit early arena unmapping.

Keep instance registration/list mutation on the serialized stopped/startup path. Runtime allocation/free may be called from different shards through the deliberately contended base provider. Ring cursors, connection state and TCP policy remain on their established owners. Verify base-only standalone Zxdp operation before introducing the Zutcp-derived allocator.

### DP-5 — Header table and scatter/gather Tx (adopted)

Zxdp exposes the selected interface MTU to Zutcp before allocator layout is finalized. Size the initial header table from the interface/path configuration then known; peer MSS is not available at allocator-registration time. A Linux interface MTU is the IP-packet budget and excludes Ethernet framing. Interface payload budget P0 = MTU - supported IP/TCP header reservation; actual per-connection P also respects peer MSS and encoded TCP options. Ethernet space is reserved in every header slot, not subtracted twice from the Linux MTU. For intermediate revisions use their surviving framing rather than TCP-specific headers. Reject a configuration/negotiation that leaves no positive payload capacity through its ordinary setup-failure path.

For upper-layer Tx bytes L and current payload budget P, actual packet count N = ceil(L/P), with checked arithmetic. At allocator registration reserve K = max(1, ceil(Lmax/P0)) header slots, where Lmax is the maximum emitted upper-layer byte count allowed by requested capacity and existing layer reservations. Do not add TLS overhead twice. Reserve each slot for the maximum supported Ethernet/IP/transport headers, alignment and software padding; retain the contiguous payload and separate software-required tail reservation. K is a simultaneous-header capacity, not a limit on the total packet count eventually emitted. Small control/empty packets still require a header. A logical approximately 16 KiB allocation spans multiple kernel chunks without becoming one oversized descriptor.

Zutcp populates the header table and determines the actual packet count, each payload offset/length, sequence number, flags and checksum. Zxdp adds the Ethernet portion and submits each packet as the ordered vector of its header plus payload slice. The Tx contract carries the original buffer reference and explicit packet/vector boundaries; N alone does not describe partial final packets or variable header lengths. All fragments reside in the owning instance's registered arena. Split descriptor ranges further as required by UMEM chunk/DMA constraints without copying payload. The header table is protocol data, not a second per-buffer metadata wrapper. Retain transport packet records using the existing sent-packet machinery.

Use AF_XDP multi-buffer Tx with XDP_USE_SG and XDP_PKT_CONTD to express fragments of each individual packet. Ending a descriptor chain marks one packet; a chain containing the entire TLS record would instead describe one oversized Ethernet packet and is not the intended operation. Use the corresponding multi-buffer-capable XDP program and account for kernel/driver fragment limits. Preserve the established zero-copy request policy: scatter/gather submission must not silently coalesce payload into another backing buffer or force copy mode. Actual kernel/driver operation remains outside this work's acceptance policy. Reference: [AF_XDP multi-buffer support](https://docs.kernel.org/networking/af_xdp.html#multi-buffer-support).

Zutcp retains TCP segmentation, congestion/window admission, pacing, per-packet send timing and recovery ownership. Zxdp owns descriptor admission/publication and DMA completion, with bounded partial-batch progress reported at complete-packet boundaries. Reserve descriptor credits for the whole next packet before starting its chain. Keep published headers and payload stable until their descriptor references retire; several independent packet chains may concurrently reference distinct ranges of the same allocation. Recycle the buffer through its existing overlaid slist only after both transport and all DMA retention end. No ACK or completion for one packet can free another live slice. Retrying an in-flight packet must not mutate its existing header.

**Backing lifetime uses ZiIOBuf's existing atomic reference count.** Application ownership, retained transport packet records and outstanding DMA submissions hold ZmRef<ZiIOBuf> references to the same original object. Each published descriptor has an associated retained reference, released by Tx on its completion; packet records release their references when recovery/ACK rules permit retirement. Several descriptors and packet records can therefore retain one large buffer without a separate backing-lifetime counter. The last ZiIOBuf release invokes the existing allocator/provider free callback, which returns the backing to its overlaid slist. Do not independently decide that backing is reusable from packet counts, ACK state or completion totals. Descriptor-to-buffer lookup and protocol byte/range accounting remain necessary for their own operations, but do not replace or duplicate the atomic reference count as the lifetime authority. A reference protects lifetime, not concurrent mutation: in-flight header/payload stability and shard ownership still apply.

**Smaller peer MSS and header-slot reuse.** If actual N exceeds K, submit up to K independent packet headers and continue in bounded batches as header DMA ownership returns. Tx's existing send operation records each header slot's busy/free state; this is header-resource accounting, not another backing-lifetime counter or packet wrapper. Reuse a header slot only after the descriptor(s) referencing that header have completed. Payload bytes remain unchanged throughout. Retained sent-packet records store original sequence/flags and payload ranges, so retransmission rebuilds the same packet in an available header slot without requiring its original header address to remain reserved through peer ACK. If no header slot is free, retain bounded existing send state and resume on completion; do not spin, grow backing, borrow control capacity or gather payload.

Bound the per-buffer outstanding descriptor demand by K times the maximum fragment count for one supported header/payload/padding vector at P0, accounting for chunk splits. Smaller peer MSS can increase the total count of packets sent over time, but not simultaneously reserved headers or descriptor demand. Test an MSS requiring N>K, with completions delayed and arriving in the permitted order, including retransmission after a slot has been reused.

**Path-budget change.** Keep the selected original-packet recovery policy. Before publication/retransmission check that each packet fits the currently effective budget. If a validated smaller path budget would invalidate an already retained original packet, abort the affected connection through its ordinary error/owner-directed close path rather than silently resegmenting retained packets, growing backing or retrying an oversized frame forever. Preserve DMA/application reference retirement. A later connection uses the current budget and header-slot batching. An interface geometry change requiring a different physical Rx slot/arena follows stopped reconfiguration in DP-12; do not reinterpret live receive backing. Test reductions before admission, with queued unsent data and with original packets outstanding, and verify exact failure and release behavior.

### DP-6 — Registered Rx stubs and heap framing (adopted)

Ztcp/Ztls provision a receive-context buffer before recv fills it. For Zutcp/Zxdp, a registered Rx allocation must therefore return a non-null ZiIOBuf-derived stub without backing, rather than dequeueing a frame for a connection whose next incoming packet is not yet known. Require an empty stub request; initialize data_()==nullptr and size==skip==length==0, with no builtin payload. Preserve its application's derived type, owner and allocator identity. Registered Tx allocations still acquire real backing. Physical Rx allocation/FILL servicing remains separate from context-stub construction.

ZiRx framing uses unregistered heap backing through two existing paths: recvMem/recvMemSync request allocBuf(false) directly; network recv may request allocBuf(true) for its next stub and then call ensure(nextLen), which allocates unregistered heap backing from zero capacity before copying a trailing record. Preserve both call patterns; do not require every framing allocBuf call to pass false. Direct allocBuf(false) cannot return null, and the planned registered Rx stub path also returns a real object without taking a UMEM frame. ZmHeapFail handles heap exhaustion internally. When an attached registered buffer is extended, ensure allocates unregistered replacement storage, copies readable bytes, returns its original UMEM backing using the old registered flag, then clears Registered. Final heap release uses registered=false. Preserve alignment and size/failure semantics and do not reuse grown buffers for Zxdp Tx/FILL.

**New heap allocation versus registered-buffer growth.** allocBuf(false) constructs a new heap-backed object for any supported role and does not fail by returning nullptr. Keep that distinct from attempting to grow an existing registered Tx/App buffer. In the inventoried ZiIOBuf.hh changes, reject a replacement allocation before calling the backing allocator when registered()==true and allocator->type() is not an Rx role (RxUDP/RxTCP/RxTLS). Apply the guard consistently to alloc, ensure, realloc and prepend whenever they would exceed current capacity, before moving/freeing bytes; use a fatal internal-error path active in release builds. App/TxStream rollover avoids that path during normal output. Registered Rx growth is allowed to heap, and already unregistered objects grow normally through heap allocation. The provider's unregistered backing callback itself therefore remains the non-null heap allocator; it need not guess whether a call was object construction or growth. No added metadata flag/counter, payload wrapper or new dependent OOM handling is needed.

The current Zi generic adapter source is a prerequisite to verify, not assumed complete merely because the signatures changed: registered Rx stub construction must bypass its ordinary null-backing failure branch and report zero physical capacity; registered=false plugin objects must remain non-builtin so final heap free occurs. Implement/verify this support in the explicitly inventoried zi/src/ZiIOBuf.hh and tests, without another packet wrapper or fake non-null backing pointer. Kernel/no-plugin builtin allocation behavior stays unchanged.

### DP-7 — Tuple lookup, packet attachment and current receive context (adopted)

Zutcp maintains an Rx-owned hash from the live endpoint tuple (including its interface/routing scope) to ZmRef<ZiConnection>. Acceptance/active establishment installs the association before packet delivery; owner-directed close removes it after ingress and queued work have been fenced. The map keeps a live connection reachable for demultiplexing, not a reference from every buffer back to its link. Closed-tuple ring entries remain separate minimal state with no live connection reference. Intermediate packet identifiers may still route their native protocol before TCP conversion; the plugin context association remains the application's connection object.

ZiMxPlugin::recv(cxn) informs Zutcp that the receive context/stub has changed. Execute on mx Rx, inspect cxn->rxContext() immediately and resume any already queued in-order data if its callback is armed and storage/view permits delivery. Do not cache an old stub across callbacks. A reentrant notification during delivery records pending work and returns; process it after the current callback exits rather than recursively invoking it. A context with no callback is not ready, and a fresh empty stub is not readable data.

Zxdp receives the actual Ethernet packet into UMEM before it has a connection association. Zutcp parses headers, verifies actual integrity, finds the live connection, handles ACK/control/sequence admission and retains out-of-order data where necessary. Only data eligible for ordered application delivery is attached to that connection's current stub; unrelated, duplicate and control-only packets do not populate it. Install backing and the actual readable payload view before calling the existing receive callback. Capture the callback result/state and re-read rxContext afterward: Ztcp/Ztls may move the filled object to an application queue and replace it with another stub or a heap-backed framing buffer.

For an exclusively owned admitted packet, transfer its backing into the destination stub while preserving the stub's derived type, application owner and allocator contract. Remove backing ownership from the temporary packet holder before releasing that holder; exactly one final registered free returns the frame. Route that free by canonical arena/region identity to the physical pool that supplied the frame, even if the stub's upper-layer allocator is a different Rx provider of the same instance. Registered=false allocation/free stays with the upper-layer heap provider. Do not return an attached frame to a different logical pool merely because the connection was provisioned by another allocator.

Set runtime size from the actual attached backing extent, never the requested template size. Represent delivered TCP payload without counting Ethernet/IP/TCP bytes in application length. Use a payload-origin view with skip==0 when handing a contiguous TLS record to current Ztls; canonical registered free resolves its true slot from the arena geometry rather than that current pointer. If outstanding shared ranges prevent exclusive backing transfer, or a partial record already occupies the current context, preserve their references and use the permitted heap framing/gathering path. Do not detach backing from a live shared packet or overwrite an application-retained object. Honor the backend's actual decryption alignment; where the packet view cannot satisfy it, normalize through the existing heap framing path rather than inventing scattered-input TLS decryption.

The current Ztls contiguous TLS-record parser/decryptor remains unchanged. Records can span packets and packets can contain multiple records; direct heap framing, zero-capacity stub-to-heap conversion and registered-to-heap growth cover these cases. App-retained records hold their own ZiIOBuf references. Do not invoke an application callback on a backingless stub or pass a stale pointer across replacement/growth. Test initial stub creation with all UMEM frames busy, callback-driven stub replacement, notification without new data, delivery of already queued data after recv, record header/tag boundary splits, coalesced records, out-of-order/duplicate packets, shared backing, heap growth/alignment, connection close with retained buffers and exactly-once frame return.

Current Ztls Tx still requires 16 KiB usable record capacity. Phase-2 fixtures select the existing Ztls::TxBufAlloc<16 * 1024> specialization before allocator creation and reserve the private packet header table in addition. Verify handshake/control/app output stays within that capacity. This is application fixture configuration; no Ztcp/Ztls production source change is part of the plan.

### DP-9 — Kernel-valid arena layout (aligned addressing adopted)

A logical approximately 16 KiB allocation can span several kernel chunks. Registration uses one chunk size C/headroom/flags set for the entire instance, with XDP_UMEM_UNALIGNED_CHUNK_FLAG unset. Linux v6.12 accepts 2048 <= C <= PAGE_SIZE and requires C to be a power of two in aligned mode. Allocate a page-aligned arena and page/chunk-round its registration extent with checked arithmetic. This is backend storage geometry, not a new application payload size. Verify UAPI constraints against the supported implementation baseline. Sources: [UMEM registration](https://raw.githubusercontent.com/torvalds/linux/v6.12/net/xdp/xdp_umem.c), [descriptor validation](https://raw.githubusercontent.com/torvalds/linux/v6.12/net/xdp/xsk_queue.h).

**Correction to the initial alternatives:** Aligned chunk mode does not require chunk-rounding every logical Tx allocation. Its descriptor validation allows a nonzero offset within the chunk, provided offset + length <= C. Consequently, heterogeneous compact Tx slots and small control slots can share a chunk without unaligned mode. Never offer those compact Tx slots to FILL. The earlier DP-9.A proposal to round every Tx slot to C is retired as unnecessary for this design.

Retain the DP-2 formula for compact logical Tx slots: stride = alignUp(H + S + T, requiredAlignment), with H containing the K-slot header table. Align each pool origin to its required alignment; poolBytes = count * stride. Preserve padding around all software-required bytes, including the overlaid free-list link when the slot is unused. The compact layout is static after the complete intrusive pending list is sized at start. It does not change while descriptors are live.

Physical receive slots have a different constraint: a FILL address grants the kernel its full advertised frame-write extent, not just the expected packet length. Reserve and align each physical ingress slot for that entire extent, including kernel XDP headroom and registered headroom. In aligned mode, publish only the canonical C-aligned chunk base; received addr/length identifies the actual packet within it. Ensure the selected C/headroom accommodates the complete configured Ethernet packet for the single-buffer Rx path. Upper-layer Rx destination pools that are never offered to FILL are not physical ingress slots. If the configured MTU requires multi-buffer ingress, implement the bounded DP-18 assembly/cursor and retain original fragment references. Do not represent discontiguous RX fragments as one contiguous ZiIOBuf or silently shorten the MTU.

**DP-9.C adopted — compact Tx with aligned addressing.** Keep ordinary aligned chunk mode. Use the absolute UMEM offset for each Tx fragment and fragmentLength = min(remainingRange, C - (offset mod C)). Continue the packet's chain until its header and payload ranges are exhausted. Physical Rx uses separate C-aligned ingress slots. Compact Tx allocations retain their prescribed alignment and stride; do not round each allocation to C. Keep all descriptor ranges within one chunk, avoiding cross-chunk DMA assumptions.

DP-9.B is retired: unaligned addressing can sometimes avoid C-boundary splits, but adds address encoding/decoding and page/DMA validation with no established benefit for this workload. Do not introduce it as another runtime mode. DP-9.A's chunk-rounded logical Tx slots remain retired as unnecessary. The selected aligned mode preserves compact allocator pools and zero-copy scatter/gather without either alternative.

For each packet, calculate d = sum of fragments needed for its complete header and payload ranges, including any software padding. Apply XDP_PKT_CONTD to all but the final descriptor. Check backing bounds and descriptor arithmetic before publishing; reserve d TX entries plus completion-tracking capacity atomically on the Tx owner. Ring-full admission stops at the preceding complete packet and returns exact admitted payload bytes. Never publish half a packet as a successful complete send. Independent TCP packets remain separate chains even when they reference one buffer.

Derive a bounded per-buffer descriptor demand from its maximum packet/header count and the selected split formula. Sum over the allowed in-flight application and control capacities, then power-of-two round within UAPI bounds. Preserve separate control credits. Ring rounding creates neither additional buffers nor packet headers. Start diagnostics record arena bytes, pool offsets/strides/counts, C/headroom/address mode and descriptor demand. Test zero/small pools, alignment padding, slot and chunk boundaries, final short packets, descriptor-ring wrap/backpressure, invalid geometry and final-release reuse with different allocator request orders.

The selected layout preserves the intrusive list, shared-registration arena, exact slist, header-table Tx and reference-counted lifetime. Record C/headroom and the resulting descriptor demand with the effective startup configuration; address mode is resolved, not a remaining author choice.

### DP-10 — Descriptor completion identity and atomic buffer lifetime

Completion addresses identify submitted ranges, which may be header slots or interior payload slices rather than allocation origins. Use the completed address as the aligned-mode arena offset, find its immutable pool region, then derive slot index = floor((offset - regionStart) / slotStride). Reject impossible offsets as an internal submission/completion error before dereferencing. Descriptor bounds must have been checked against that slot's adjusted backing, not merely the entire arena.

Maintain a bounded active-slot lookup to the original ZiIOBuf object; this is descriptor completion association, not another packet object or copy of length/skip/owner metadata. Before publishing a descriptor, retain its original buffer through the existing atomic reference count and establish the lookup. Completion releases that descriptor's retained reference. Several descriptor addresses and retransmissions can resolve to the same object; none independently returns its storage to a pool. The mapping remains valid through all outstanding uses and is cleared before final release publishes the slot to its free slist. Reuse cannot redirect an old completion to a newly allocated object because the old descriptor's reference prevents final release/reallocation.

Do not add a second per-buffer backing-reference counter. Transport packet records, application owners and DMA holds all use the existing ZiIOBuf reference count. Per-packet ACK/SACK/send-time records and descriptor-ring credits retain their separate meanings. Consuming TX ring entries is not completion; a COMPLETION entry returns descriptor ownership and releases a DMA hold, not a TCP acknowledgment. Refcounting does not authorize mutation of live packet headers or cross-shard state.

On failed admission, release only references acquired for unpublished descriptors; preserve published holds until their actual completion or kernel-ownership retirement. Teardown quiesces submissions, drains or cancels owner work, then retires kernel access before releasing any remaining DMA holds. Application/transport references may still prevent final buffer release. Do not unmap the arena, destroy its provider or reinterpret slot lookup while callbacks can reach it. Rx heap replacement is distinct: free(..., registered=true) returns its old UMEM slot while the same ZiIOBuf object continues on heap backing with Registered cleared.

### DP-11 — Tunable admission and control reserves (adopted)

Expose the following startup-tunable unsigned values through Zutcp::HubParams using the copied parameter/getter/default/initialization style. These are pragmatic initial defaults to adjust using the selected Clang -pg profiling process; they are not performance acceptance targets. They do not override allocator-request counts or mx.rxQuantum.

| Parameter | Default | Unit and operation |
| --- | --- | --- |
| rxRetainFrames | 1024 | Maximum distinct physical ingress frames retained outside active kernel reception/service across the instance, including out-of-order and delivered application-held UMEM backing. Effective capacity also respects R - rxReserveFrames, where R is the actual physical ingress frame count. |
| rxRetainFramesPerCxn | 256 | Maximum distinct physical ingress frames retained for one connection, further bounded by the shared effective limit. Count backing once even when several slices reference it. |
| rxReserveFrames | 64 | Physical ingress frames protected from ordinary retained-data admission for continuing receive service, gap filling and incoming control. This is headroom within the physical Rx reserve, not an additional application allocator or a promise of separate NIC steering. |
| controlBufCount | 256 | Count passed to the separate transport control allocator before instance start. It supplies protocol-sized ACK/window/probe/close backing and does not borrow application payload slots. |
| txControlCredits | 64 | TX-ring descriptor entries unavailable to application admission, reserved for control submission. A descriptor is one address/length/flags ring entry; one scatter/gather packet can require several entries. |

All values are configurable before start and can be changed while stopped for the next start using the existing serialized configuration lifecycle. Changes requiring a different arena or ring capacity follow the registration/restart lifetime rules; no live arena/ring resizing is implied. Do not add cross-shard mutation or a second configuration service. If a later runtime logical-limit update is added, it must dispatch to the relevant Rx/Tx owner and cannot resize physical capacity or revoke existing live references.

Require positive retention limits, rxReserveFrames and controlBufCount. Require R > rxReserveFrames and a positive effective retained capacity. Reject invalid small-pool configurations with the actual R/reserve values rather than silently increasing application-requested counts. The effective instance retention cap is min(rxRetainFrames, R - rxReserveFrames); the connection cap is min(rxRetainFramesPerCxn, effectiveInstanceCap). Both are admission bounds, never instructions to discard already acknowledged data or invalidate application-held references. Reducing a configured cap on a later start does not authorize early retirement of old backing.

Use the existing copied reassembly and byte-credit logic with these frame admission bounds. Before committing receive/ACK evidence for new retained data, check distinct backing demand against both caps and preserve the receive-service allowance. Refuse/recycle excess new out-of-order input before acknowledgment. A gap-filling packet may use the service allowance to retire/deliver an already retained contiguous run; if the application cannot consume it, apply the existing bounded window/backpressure behavior without exhausting the protected service capacity. Parse control independently of payload retention. Application consumption or Rx ensure replacement returns physical backing through its normal provider callback and restores admission capacity; heap-backed record storage no longer consumes a UMEM frame.

Let D be TX descriptor capacity and F the currently free entries. Require D > txControlCredits and enough reserved credits for at least one maximum-fragment control packet under the selected layout. An application packet requiring d descriptors is admitted only if F >= d + txControlCredits. Control admission requires F >= d and available control backing. Account for the entire scatter/gather packet before publication; do not count packets, IOBufs or bytes as descriptor entries. Service pending control before new application admission, coalesce replaceable unsent ACK/window state using the copied machinery and retain bounded queueing. Already published descriptors cannot be preempted; completion/driver progress still must run.

Report configured/effective caps, distinct retained physical frames, admission refusals, free control buffers, free TX entries, reserved credits and control stalls through existing diagnostics/telemetry. Frame admission counters and descriptor credits are resource accounting, not a substitute for ZiIOBuf atomic lifetime counting. Verify default and nondefault values, validation failures, independent application pools, fragmented large Tx buffers, tiny messages, retained Rx data, heap replacement, control submission under application saturation and restored capacity after release. Carry this coverage through the native pair from phase 1 and ZiConnection/Ztls fixtures from phase 2.

### DP-12 — Lifecycle resolutions (adopted; capacity-bounded tuple history)

The three lifetimes are distinct: application/transport references retain ZiIOBuf backing; AF_XDP registration and descriptors permit kernel access to an arena; TCP state protects an endpoint tuple against late packets. Application disconnection does not necessarily end the other two lifetimes. The adopted rules complete their boundaries without another buffer-lifetime counter or additional worker threads.

**DP-12.1 — Stop and restart with retained buffers.** Stop quiesces ingress and submissions, runs the framework's Rx-then-Tx asynchronous drain, cancels/drains protocol work and retires kernel DMA access. Stop may finish while application-held data buffers remain, provided their callbacks/providers and backing remain valid and cannot reference destroyed connection state. A retained buffer keeps its existing object/refcount; it does not keep a link alive through a new owner reference. As required by framework owner lifetime, drain any callback using a raw link back-pointer before link destruction.

Keep the stopped instance's arena mapping, provider identities, assigned pool layout and free slists while backing is live. Restart with unchanged layout re-registers the same arena/bindings and offers only free physical ingress slots to FILL; never rebuild free lists from all slots or reset live IOBufs. New connection objects do not revive old TCP connections. Use existing lifecycle/generation guards on queued operations. Require callback owners/allocators to remain alive through outstanding buffer release; final mx/plugin destruction still requires all such callbacks to have drained.

If stopped reconfiguration adds/removes allocators or changes their physical geometry/count, require all backing from the previous arena to retire before replacing that arena. If a start is attempted earlier, complete start with an explicit retained-buffers/busy failure, leaving the stopped instance and old backing valid. Retry after release; do not wait on an I/O shard, allocate a parallel live arena, grow an active arena or reinterpret old offsets. This keeps one arena per instance and avoids an unbounded chain of retired arenas.

**DP-12.2 — Registration and mapping retirement.** A kernel registration is permission for kernel access; the memory mapping is the storage still used by retained buffers. Stop prevents new queue publication, quiesces/removes XSK map destinations while preserving the selected endpoint discard fence, drains/cancels Rx then Tx work and retires XSK/kernel ownership before releasing DMA-held ZiIOBuf references. Tear down sockets/registration and ring mappings in the order required to end kernel access. Preserve the underlying arena mapping independently until all remaining buffer callbacks have returned its slots. Unregistering need not wait for application-only references once kernel access has ended; unmapping must wait. Do not infer DMA retirement from TX consumer progress or an empty transport queue.

Reuse the same provider objects and addresses on same-layout restart. Rebuild only kernel registration/ring/service state, not live allocation state. Final destruction removes only this instance's maps/attachments/exclusion ownership and releases its arena after its last callback; another active instance must continue unaffected. No periodic GC or forced timeout frees backing. Failure at any startup stage unwinds newly created kernel resources while preserving valid preexisting providers and retained storage.

**DP-12.3 — TCP close and tuple reuse.** A TCP tuple is the local IP/port plus remote IP/port within its interface/routing scope. Ordinary connection close does not close the shared Zxdp instance. Graceful Zi disconnect stops new application sends, drains admitted data, sequences FIN after that data and continues receiving/acknowledging until the appropriate FIN/ACK transitions complete. Preserve independent half-close state; local FIN does not discard peer data. Abrupt close cancels application work, sends RST when meaningful and drops transport references only after owner work is safe; already submitted DMA references remain until retirement. Both paths notify the application exactly once through the existing Zi lifecycle contract.

Represent FIN-WAIT-1, FIN-WAIT-2, CLOSE-WAIT, CLOSING, LAST-ACK and TIME-WAIT with explicit Tx-owned sender/close state and owner-directed Rx publications. Peer FIN is sequenced and delivered after preceding receive bytes; its ACK and notification cannot race ahead of missing data. Bound graceful close with a configurable closeDrainTimeout, default 30 seconds, and orphaned FIN-WAIT-2 with finWaitTimeout, default 60 seconds; expiry aborts protocol work rather than freeing live DMA/application backing. These protocol defaults are configurable, not performance targets.

After application teardown, retain only the minimal closed-tuple state in a fixed-capacity ring owned by Rx. Add HubParams::closedTupleRingSize, default 4096 records, configurable while stopped; validate a positive capacity. Each inline ring record contains the tuple, the sequence/ACK/timestamp information required for late-packet responses and reuse decisions, and any ring/index identity needed to reject stale queued work. It contains no application payload and no raw pointer to a destroyed connection. Keep lookup bounded through an intrusive index over the fixed ring slots; remove the old slot's index entry before overwrite and insert the replacement without per-close heap allocation. This is user-mode transport state, not per-flow BPF state.

Insert records in closure order. When the ring is full, evict the oldest record to admit the next closed tuple. A late packet can update the relevant protocol evidence in its existing record, but does not refresh FIFO insertion order. Expiration is capacity-based: no per-record eviction timer, timeWait duration, expiry scan or elapsed-time removal. This author decision replaces the proposed 60-second TIME-WAIT retention and abort-guard duration. It bounds memory and retained history by record count; it does not promise a minimum wall-clock retention interval.

Rx owns ring/index mutation and late-packet classification. Tx generates responses using bounded immutable snapshots posted by Rx, not pointers into ring slots that can be overwritten. Preserve the ring and its closure order across same-instance stop/start before publishing endpoints. If its configured size changes while stopped, retain the newest min(oldCount, newCapacity) records in order; resizing is an explicit configuration operation, not time-based eviction. Final instance destruction releases the ring; full process restart does not restore connection history. Keep the adopted endpoint exclusion behavior during instance shutdown.

While a tuple record is present, use its sequence/timestamp history to reject stale segments, acknowledge applicable repeated FINs and distinguish eligible new incarnations. Once timestamps/PAWS are ported, apply RFC 6191's SYN reuse checks where applicable. Without sufficient new-incarnation evidence, prefer another available client tuple and report configured port-range exhaustion rather than silently discarding a still-retained matching record merely to retry it. Once capacity eviction removes a record, no history-based guard for that tuple remains; ordinary new-connection initial-sequence and receive-window rules apply. After an abort, insert the same minimal ring record rather than retaining payload or creating a timed quarantine. Owner-generation guards remain necessary for queued work but cannot identify delayed wire packets, which carry no local generation token. Sources for the underlying late-packet/sequence behavior: [TCP close](https://www.rfc-editor.org/rfc/rfc9293.html#section-3.6.1), [timestamp-qualified reuse](https://www.rfc-editor.org/rfc/rfc6191.html). The ring's capacity-based retention is the selected implementation posture, not a claim of timed TIME-WAIT conformance.

### DP-13 — Connection limits, initial sequences and timer mappings (adopted)

**DP-13.1 — Connection admission.** Replace maxStreamsDuplex/maxStreamsSimplex with maxCxns, default 1024, scoped to the Zutcp instance across listeners and active opens. Add maxPendingCxns, default 128, as a subset cap on handshakes in progress rather than an extra connection allowance. Require positive values and maxPendingCxns <= maxCxns. Configure using HubParams while stopped, following the adopted initialization pattern; do not advertise these local limits on the wire. These are pragmatic tunable defaults, not derived from CPU targets or the obsolete simplex/duplex sum.

Rx owns admission and slot accounting. Reserve one slot before constructing a native active-open or passive-open connection; active and passive handshakes both consume pending capacity and total capacity. Establishment releases only the pending charge. Established, half-closed and closing full connection records remain charged to maxCxns. Release the total charge after owner-directed shutdown has removed the full connection, drained its queued work/timers and transferred any minimal history to the fixed closed-tuple ring. Ring records use closedTupleRingSize, not live connection slots; remaining application/DMA references retain their backing independently and do not retain a full connection just to hold memory. Admission failures and setup timeouts release exactly the charges they acquired.

At capacity, fail an application active-open request once through its existing fail callback; refuse a new passive open without allocating a connection or claiming acceptance. Drop excess new SYN/intermediate Initial traffic so a peer can retry, while continuing to process existing connections, ACKs and close/control traffic. Do not evict an established connection or closed-history record to conceal live admission exhaustion. Report pending/live/closing counts, limits and refusals through existing telemetry. An application allocator's buffer count is not multiplied automatically by maxCxns and does not promise one retained buffer for every admitted connection.

**DP-13.2 — Initial sequence policy.** Use a TCP-specific initial sequence number generator with the RFC 6528 structure ISN = M + F(localIP, localPort, remoteIP, remotePort, secret), modulo 2^32. Let M advance from the instance's monotonic clock in 4-microsecond units. Use a keyed PRF over an unambiguous fixed-width encoding of address family/addresses/ports and instance scope; use HMAC-SHA256 truncated to 32 bits, with a 256-bit secret obtained from the operating system's secure random source at initialization. No per-packet hashing or entropy syscall is required. This preserves a small crypto primitive for sequence/cookie integrity; deleting TLS and packet encryption does not require replacing it with a predictable noncryptographic hash. Source: [RFC 6528](https://www.rfc-editor.org/rfc/rfc6528.html#section-3).

Generate/retain the secret and clock origin for the instance lifetime, including same-instance stop/start; do not reseed on every connect or silently fall back to time/process ID if secure initialization fails. Retransmitted SYNs reuse the same chosen ISN. SYN and FIN each consume one sequence position independently of application payload. Deterministic tests may inject a secret/clock through a test fixture; production configuration does not expose a fixed ISN or secret in diagnostics. Use the existing modulo comparisons and wide internal byte ranges, including across wrap. Closed-tuple history and timestamp-qualified reuse rules still apply: a fresh-looking ISN alone does not authorize every incoming SYN or replace PAWS/window checks.

**Timestamp-free operating rule.** Timestamp negotiation remains optional under OQ-4.B. If timestamps are absent, process data/ACKs with ordinary TCP sequence/window checks and wide local stream accounting; use Karn-style RTT sample exclusion for retransmissions. Do not invent an epoch field on the wire, quiet-time wrap delay, automatic connection rotation or throughput limiter. A delayed segment whose sequence aliases the current receive window after a complete 32-bit cycle cannot be distinguished using those headers alone. The timestamp-free profile therefore relies on the ordinary TCP operating assumption that old segments do not survive until their sequence space is reused; it does not claim PAWS protection against that unsupported delayed-duplicate condition. Negotiated timestamps provide the selected PAWS protection for rapid sequence reuse. ISNs and closed-tuple history address connection incarnation, not a hidden same-connection sequence epoch. Reference: [PAWS and sequence reuse](https://www.rfc-editor.org/rfc/rfc7323.html#section-5).

Test ordered stream wrap and outside-window old-segment rejection without timestamps; test PAWS rejection of an older timestamp after full sequence reuse when timestamps are negotiated. Include a controlled sequence-comparison test showing that an exact full-cycle in-window alias without timestamps remains indistinguishable and follows ordinary acceptance checks; do not report that case as protected by internal wide counters. This records the optional-extension profile's actual limitation without adding conformance-only waits or an impossible full-epoch inference requirement.

Place generation/encoding in dedicated ZutcpISN files and retain only the needed existing crypto dependency for this primitive and TFO cookies. Do not copy back Zquic TLS/AEAD/key-schedule code. Use HMAC explicitly to reuse an established implementation rather than writing a new keyed hash. The intermediate first milestone keeps its copied packet-number bootstrap; apply ISNs when connection establishment/byte sequence semantics are ported, not as a prerequisite to the stripped working pair.

**Always-immediate sending and minimal timed behavior.** Hardcode the TCP_NODELAY behavior in Zutcp: delete Nagle's algorithm rather than keeping it behind a default-on/off option. An application send is eligible as soon as its bytes are available, subject to the actual send window, congestion/pacing allowance and backend resources. Do not wait for an outstanding short packet to be acknowledged, an MSS-sized payload, another application message or an aggregation timeout. The ZiMxPlugin path performs no kernel TCP_NODELAY setsockopt; this is the user-mode transport's fixed policy. Existing Ztcp/Ztls production code and the kernel backend need no change.

Batch descriptors and coalesce control state only from work already available in the current servicing turn; do not introduce a timer or wait for more work to improve batch size. Use immediate local ACK scheduling without a delayed-ACK timer. Preserve only time-based mechanisms needed by the selected transport behavior: RTT/send-time evidence, loss recovery, congestion pacing, zero-window probes and explicit connect/user/close policy deadlines. Optional idle/heartbeat behavior stays disabled unless configured. Closed-tuple eviction and memory reclamation remain event/capacity based. This posture removes artificial waits without disabling the already adopted RACK-TLP, PAWS or essential transport timers.

**DP-13.3 — Timer/algorithm mapping.** Retain the copied RTT estimator's first-sample initialization, smoothed RTT weight 1/8 and variation weight 1/4. Remove QUIC peer ACK-delay subtraction because TCP ACKs do not supply that delay. Use unambiguous samples: without timestamp evidence, do not measure RTT from retransmitted bytes. Keep monotonic per-segment send times, separate timer purposes and existing owner-generation/cancellation/drain mechanics. The adopted TCP defaults below are HubParams values unless the row specifies an algorithm; timer deadlines remain on mx Tx, with Rx publishing ACK/window/receive activity.

### DP-19 — Frame-admission charges and off-owner returns

Allocate an Rx-owned slot-charge table of R entries keyed by normalized RxFrameID, and a fixed account-record pool of maxCxns+R entries. Each account record has a stable index/generation, Rx-owned held-frame count and active/retired status. Active connections hold one account token; closed connections with app-held physical backing leave only this small account record, with no raw pointer/reference to the destroyed connection. At most R retired records can still hold charges, because each must account for at least one physical frame. Account records are protocol resource accounting, not an alternate backing-lifetime count: ZiIOBuf atomic references still exclusively control physical release.

When Rx admits a physical frame for retained/application use, write its account token in the slot table once and increment that account/instance charge once, regardless of aliases. Leave the token stable until the physical slot is returned. Registered heap replacement/final release invokes the provider free callback, which returns the frame immediately via the exact selected payload-overlaid slist and wakes Rx on depleted-to-nonempty transition. The off-owner callback does not touch a connection or any Rx-owned account counter and does not enqueue a second frame-return node/queue.

When Rx pops a returned physical slot from the free slist, before any FILL publication, inspect and clear its old charge token. Decrement the identified account and global retained count, reopen applicable live-connection credit through the existing Rx-to-Tx publication, and reclaim a retired account immediately when its final charge is cleared. Then offer the physical frame to FILL with an empty token for its next receive. The slist's publication ordering transfers the slot back before this processing; no off-owner read/write of the token is needed. Initial uncharged slots have token zero and require no account mutation. Final free can occur on an application thread, after heap conversion or after connection destruction, without accessing old connection memory.

FILL capacity is at least R and only this provider supplies it. Therefore every returned free physical slot has publication capacity when the rest of its R slots are accounted for in kernel/FILL/application ownership; do not reserve FILL entries for non-ingress providers. Replenish/reconcile returned slots on wake even if no new packet arrived. These updates may conservatively retain an old admission charge until Rx processes the returned slot, but cannot falsely admit extra backing or require periodic scanning.

During stop, prevent FILL publication and keep slot/account records alive with the preserved arena/provider. Same-layout restart reconciles returned slots on Rx before rearming FILL, preserving tokens on still-held frames. A stopped-instance return can remain on the free slist until restart or final serialized teardown; it never dereferences a retired link. Final destruction after all buffer callbacks have drained may perform one bounded teardown drain of the free slots/account records, without a background collector. Queue/generation guards prevent late work addressing a reused account; a token is reused only after all charged frames have returned and been reconciled. Cover off-shard release, registered-to-heap growth, alias references, connection close before return, same-layout restart, exact one-time charge retirement and immediate physical free-list reuse ordering.

### Integration rules

Implement public Zxdp::Instance/configuration and private helpers in the inventoried files. Keep AF_XDP descriptors/offsets private: the normalized boundary supplies original buffer references, packet vectors, capacities, queue identity, RxFrameID and completion/recycle notification. The binding requires mx, interface/queue identity and the selected ZmRing-style wait parameters. DP-17 is the sole physical ingress count/provider definition; application Rx requests create stubs, while registered Tx/control requests retain their independent prescribed backing counts.

RX/FILL, parsing/reassembly and delivery execute directly on mx Rx. TX/COMPLETION, recovery, pacing and timers execute directly on mx Tx. Capture fixed ACK/window/ECN evidence by value when posting Rx to Tx; retain the original buffer if variable input must survive that handoff. A reference preserves lifetime, not permission to mutate another owner's state. Use existing direct/on-owner paths and mx's wakeFn/rxQuantum; do not add a second scheduler wake owner. When a physical Rx free list changes from empty to nonempty, wake Rx even without new network traffic, then apply DP-19 charge reconciliation before FILL publication.

For Tx, reserve private H/T outside the application's S-byte payload view and return its aligned payload origin so existing Ztcp/Ztls writes at skip==0 preserve their capacity semantics. H contains DP-5's K simultaneous header slots. The application's data_/size/skip/length remain its payload view; ZiTxContext reports admitted application bytes only. Each complete packet vector pairs a currently available header slot with retained payload ranges and software padding. Header addresses remain stable only during DMA; retained recovery records preserve sequence/flags and payload ranges, rebuilding headers in an available slot on resend. Never count lower-stack headers as application bytes or use a changed skip to omit retransmission headers.

The free-storage origin must be aligned for the overlaid ZmAtomic<uintptr_t> and fit that word, even for a tiny logical payload; use existing framing/padding space without exposing extra application capacity. An explicit count=0 physical pool has no backing, but cannot make metadata-only Rx stub creation or registered=false heap framing nullable. Required physical ingress/control capacity is validated before startup under DP-11/17. Do not merge independent Tx/control pool counts or resize old layout while any backing remains live. DP-12 governs registration retirement separately from mapping lifetime.

Use a 32-bit wire sequence type with wide internal retained ranges. Unwrap values relative to current send/receive edges and compare only within the active window below half the sequence space; test wrap, SYN and FIN consumption. Rx owns receive-next/out-of-order/FIN/advertised-window state. Tx owns send-unacknowledged/send-next, peer window, send times, retained data and congestion/recovery. SACK evidence does not release bytes still needed for reneging. Application consumption follows the existing byte-credit path; physical-frame charges retire only through DP-19's Rx-owned free-slot reconciliation, including heap replacement and off-thread release.

Apply the current IP/peer MSS budget and actual option lengths to every emitted packet; Ethernet padding is not sequence data. Compute IP/TCP integrity over the real vectors. Use DP-5 for smaller-MSS header batching and invalidating path changes, DP-18 for bounded multi-frame ingress, DP-13 for TCP timers and DP-14 for TFO cookies. Keep once-only accept/sole-stream/connected/close publication and owner-generation guards throughout the intermediate revisions. Telemetry observes state without executing mutable protocol work from a watching thread.

Use direct AF_XDP/BPF calls and ordinary zero-copy-first bind without XDP_COPY or forced XDP_ZEROCOPY. Driver capability/fallback remains the kernel's decision. Keep need-wakeup handling distinct from scheduler wake: invoke driver progress only when the flags require it. Follow DP-15 interface membership and DP-12 asynchronous teardown before releasing kernel-held references/maps. Report effective mode and pool/ring/admission state through the existing telemetry contract, without imposing a hardware certification gate.

#### Preparatory execution and independent Zxdp gate

1. Record source revision, working-source file manifest, compiler/configuration and existing Zquic test results. Build and independently verify Zxdp before creating Zutcp. Do not edit Zquic to prepare copying.
2. Implement ring views against queried kernel offsets and lengths. Keep RX/FILL on Rx and TX/COMPLETION on Tx. Publication uses acquire/release ordering and never treats descriptor retirement as packet retirement. Validate lengths/offsets needed to protect backing and UAPI integrity.
3. Collect provider records through the existing Zi backing interface in the owning instance's intrusive pending list; at instance start, size/allocate/register the shared arena and initialize each region using its immutable geometry/count request. Each per-allocator region uses the exact non-sharded ZmHeap.hh:209–233 slist, overlaying its next pointer on free payload only. Registered Rx context allocation produces a stub without acquiring a frame; physical frame/Tx reserve exhaustion returns null. Unregistered allocation/free uses ZmVHeap; registered non-Rx growth is rejected at the buffer mutator before replacement allocation in all builds. Implement and verify the DP-2/5/9 registered-layout and descriptor-capacity formulas; geometry must support the requested capacities and MTU, rather than silently changing them.
4. Keep Rx, application Tx and transport-control pool capacities separate. Final free callbacks can run off-owner; mapped ring operations cannot. Hold the original ZiIOBuf through ZmRef for every published descriptor until its kernel completion, relying on the existing atomic reference count and final allocator callback for recycling; preserve backing providers through all final callbacks. Completion lookup storage must retain original buffer references without duplicating the IOBuf's payload/metadata representation.
5. Attach only backend-owned classifier resources. Redirect selected local address/protocol/reserved-port traffic to the configured queue; other traffic passes. During shutdown, owned unavailable endpoints remain excluded. Read existing static neighbor/route information; report actionable setup failures rather than starting dynamic discovery. Handle every partially completed allocation/map/socket/attachment stage in reverse dependency order.
6. Drive Rx using the current scheduler hooks, rxQuantum and ZmRing-style wait controls. Preserve need-wakeup driver progress separately from scheduler wake. Run a bounded Tx completion pump while submissions remain outstanding, permitting other Tx work between turns. Interrupt waits/spins on stop and drain late timer callbacks on their owners.
7. Verify raw Zxdp request/reply over veth without Zutcp or TCP. Exercise ordinary/low-latency wait, full rings, exhaustion/release, wake races, coexistence and outstanding-DMA teardown.
8. After the independent Zxdp gate passes, copy Zquic verbatim to Zutcp, then rename in a separately inspectable change. Preserve byte identity before renaming, including source tests later deleted. Register Zutcp build targets only after its sources exist; Zxdp-only preparation must configure/build independently. Begin phase-1 adaptation only after the copy/rename checkpoint.
