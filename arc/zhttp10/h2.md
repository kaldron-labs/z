# HTTP/2 implementation plan

## Outcome

Add RFC 9113 HTTP/2 to `libZhttp` as another library-owned HTTP profile over
the existing TLS transport.  An application must continue to:

1. configure and `init()` an engine;
2. `start()` it;
3. process application-visible logical links using `connected()`,
   `txStream()`, `process()`, and `disconnected()`;
4. call continuation-bearing `stop(done)` when signalled to exit; and
5. call `final()` only from, or after, the stop completion.

The request/response workload must be the same template for H1, H2, and H3.
Only configuration, concrete profile/link/parser/builder types, and negotiated
metadata may differ.  H2 framing, HPACK, stream IDs, SETTINGS, flow control,
physical TLS-session pooling, GOAWAY, and orderly teardown belong entirely to
`libZhttp`.

The callback order remains normative:

- client: `connect()` -> `connected(link)` -> obtain `txStream()` and begin
  sending -> `process(link, rx)` zero or more times -> `disconnected(link)`;
- server: `connected(link)` -> obtain `txStream()`/install the statically
  composed handler -> `process(link, rx)` for the initial request -> continue
  sending/processing -> `disconnected(link)`.

For H2, the physical TLS handshake, preface, SETTINGS, and session are hidden.
The client callback occurs only after its logical stream is registered and the
local preface/initial SETTINGS are queued.  The server callback occurs before
the retained initial HEADERS bytes are dispatched to the logical link's
`process()` path.

This plan supersedes the earlier assumption that H2 can be added merely by
placing an H2 session beside the existing `TLS` specialization.  The current
code derives HTTP version and multiplexing from the native transport; that
must be corrected first.

Apply root `AGENTS.md` and `GUIDELINES.md` throughout.  The implementation is
not complete if it interoperates but violates shard ownership, adds hidden
copies or allocations, leaves dormant compatibility paths, or completes
`stop()` before all dependent work is drained.

## Phase 0 baseline codebase audit

The following was the implementation baseline for this plan.  Gaps 1-6 were
repaired in Phase 1; the remaining items continue to constrain later phases.

### Facilities to retain and extend

- `Zhttp::Engines` already initializes and starts engines in order, stops and
  finalizes them in reverse order, retains all start/stop continuations, and
  calls `stopAccepting()` before stopping engines.
- `Zhttp::Agent` owns URL routing, discovery, Alt-Svc, redirects, retries,
  replay safety, request timers, result reporting, and H3-to-TLS fallback.
- `Zhttp::Service` owns listener selection, physical-connection admission,
  common request/response workload callbacks, Alt-Svc emission, engine
  lifecycle, and the final Rx drain before stop completion.
- `Zhttp::MessageVersion`, `ClientMessage`, and `ServerSession` already factor
  much of the parser/builder and request/response callback plumbing.
- `ZhttpH3Engine.hh` already demonstrates the required physical/logical split:
  physical QUIC connections and control streams are hidden while each request
  stream is exposed as an application-visible logical link.
- `ZhttpH3Session.hh`, `ZhttpH3.hh`, and `ZhttpQPack.*` provide working H3
  control-stream, request-stream, QPACK, streaming-body, and dynamic-table
  patterns.
- `Zquic::Stream` is the relevant precedent for one logical object containing
  separately owned Rx/Tx subobjects; its QUIC framing, retransmission, and
  transport flow control are not reusable by H2.
- `ZhttpUtil.hh`, the existing header typelists, `ZiRxStream` consumption, and
  `ZiTxLayer`/`ZiIOBuf` headroom are the preferred primitives for parsing,
  callback dispatch, and direct frame output.
- `ZhttpTransportContractTest`, `ZhttpEngineFixture.hh`,
  `ZhttpH1EngineTest`, `ZhttpH3EngineTest`, `ZhttpEngineLifecycleTest`,
  `ZhttpServiceIdleTest`, `ZhttpAgentFallbackTest`, and
  `ZhttpMultiRequestTest` already exercise the normalized contract and
  lifecycle.
- `Ztcp`, `Ztls`, and `Zquic` already implement continuation-bearing engine
  stop and native Rx-to-Tx drain.  H2 must compose those completions rather
  than add a second blocking shutdown mechanism.

### Gaps that must be repaired before H2 integration

1. `ZhttpConfig.hh` defines only `Version::H1` and `Version::H3`.
2. `Transport_::Traits<Protocol>` owns `HTTPVersion` and `Multiplexed`.
   `TLS` is consequently assumed to mean H1/non-multiplexed even though one
   TLS connection may negotiate H1 or H2.
3. `MessageTraits<Protocol>` selects its parser and builder from the native
   transport trait.  HTTP message profile and native transport are therefore
   incorrectly the same template dimension.
4. `ClientPool` uses `Base::Multiplexed` to decide physical-link reuse and
   cleanup.  This works for current H1/H3 but cannot model many H2 logical
   links sharing one TLS connection.
5. `Agent::Attempt` records a transport but not an independent negotiated HTTP
   version.  `event_()` and `result_()` infer H3 from QUIC and H1 otherwise.
6. `Service` instantiates parser, builder, session, engine, and link by native
   `Protocol`; it cannot select an H1 or H2 message session after TLS ALPN.
7. `Transport_::tlsParams()` and the TLS server parameter builder hard-code
   the one-element ALPN list `http/1.1`.
8. `ZhttpHPack.*` is not HPACK.  It is the RFC 7541 Huffman codec in
   `Zhttp::H3::HPack`, used by QPACK.
9. Prefix-integer and string coding is duplicated between `ZhttpH3.hh` and
   `ZhttpQPack.cc`; QPACK static-table lookup and dynamic-table storage are
   useful patterns but not reusable HPACK state machines.
10. H3 decoded-field semantics are embedded in `H3::Parser`.  Pseudo-header
    ordering, `:authority`, forbidden fields, informational responses, and
    CONNECT semantics are not yet a complete wire-neutral component.
11. H3 currently treats some defined push inputs as ignorable extensions:
    `MAX_PUSH_ID` is accepted and a push stream can fall through extension
    handling.  A shared no-push policy must not preserve that gap.
12. Current orderly teardown is a hard-won invariant.  Any H2 design that has
    a no-continuation `stop_` boundary, clears owners before callbacks drain,
    or assumes a posted `run`/`invoke` completed synchronously is a regression.
13. The current GCC release build has measured roughly 9 GiB peak RSS in the
    large `zhttp` and `zhttpd` template translation units.  H2 must put
    non-template protocol machinery in the library `.cc` files and must not
    expand application translation units with duplicated H1/H2/H3 engines.

## Required architecture

### Separate native transport from HTTP profile

Retain `TCP`, `TLS`, and `QUIC` as native transport tags.  Add H2 to
`Version`, and introduce an explicit compile-time composition:

```c++
template <typename Transport_, int Version_>
struct Profile;

using H1TCP = Profile<TCP, Version::H1>;
using H1TLS = Profile<TLS, Version::H1>;
using H2TLS = Profile<TLS, Version::H2>;
using H3QUIC = Profile<QUIC, Version::H3>;
```

Use these aliases in the public profile vocabulary.  The two dimensions and
the four valid compositions are mandatory.  Invalid compositions must fail
with the existing detector/`ZuIfT` style; do not use concepts or `requires`.

After the split:

- `Transport_::Traits<T>` describes only native transport capabilities and
  types: secure/datagram properties, native client/server/link/Rx types,
  parameter construction, and native lifecycle adaptation.
- a profile/message trait describes HTTP version, parser, builder,
  one-message-per-logical-link behavior, close-delimited behavior, and
  multiplexing at the HTTP layer;
- `ConnectedInfo` reports native transport and negotiated HTTP version
  independently;
- `ClientMessage`, `ServerSession`, `ClientPool`, `Agent`, and `Service`
  select message behavior from a profile, never by testing whether transport
  is QUIC;
- physical session reuse/admission is separate from logical request
  admission.

Do not retain aliases that silently map `TLS` to H1 inside new code.  Update
all in-tree dependents; backward compatibility is not a goal.

### One TLS engine, one ALPN decision

H1 and H2 must share one TLS listener and one TLS client connection attempt.
The TLS ALPN list is:

```text
h2, http/1.1
```

subject to explicit prefer/force/disable policy.  Do not start competing H1
and H2 TLS listeners on the same address, perform a second handshake for H1
fallback, or parse application bytes before ALPN dispatch.

Add a library-owned TLS HTTP coordinator, expected in
`ZhttpTLSEngine.hh`.  Its physical `Ztls` link selects exactly one statically
composed H1 or H2 session after `connected(Ztls::Connected)`.  Runtime dispatch
is permitted at the ALPN boundary and at the native-buffer-to-selected-session
boundary.  There must be no virtual or type-erased dispatch per H2 frame,
header field, or body span.

The H1 path should continue to reuse `H1::Parser`, `H1::Builder`, and the
existing message adapters.  The H2 path owns a physical session with many
logical request links.  Both paths feed the same application callback
templates.

### Reuse the existing physical/logical pattern

Follow `H3_::ClientEngine`/`ClientSession`/`ClientStream` and
`H3_::ServerEngine`/`ServerSession`/`ServerStream` where their ownership and
logical-link behavior are wire-neutral:

- a client physical-session pool is keyed by origin/endpoint; after handshake,
  a session records its negotiated profile and is reused only for a compatible
  request;
- pending logical requests wait for handshake and protocol readiness;
- the application receives `connected()` only when its logical request link
  can transmit;
- the server creates an application-visible logical link only when an inbound
  request stream is valid and admitted;
- physical connection/control events remain private;
- physical failure completes every affected logical link exactly once.

Do not derive H2 protocol behavior from QUIC classes.  H2 must use `Ztls`
transport and implement multiplexing, stream IDs, flow control, and scheduling
in `libZhttp`.  Extract small logical-link ownership helpers from
`ZhttpH3Engine.hh` only when they are genuinely independent of QUIC stream
APIs, migration, QPACK, or H3 control streams.

### Layering and source organization

Use this ownership:

- `ZhttpHeader.hh/.cc`: wire-neutral field representation, compile-time header
  callback dispatch, pseudo-header/message semantic validation shared by H2
  and H3, and neutral prefix-integer/string/Huffman primitives.
- `ZhttpHPack.hh/.cc`: actual H2 HPACK static/dynamic tables and codecs.
- `ZhttpQPack.hh/.cc`: QPACK-only instructions, tables, blocked-reference
  policy, and error mapping, using neutral primitives where appropriate.
- `ZhttpH2.hh/.cc`: H2 constants, frame header/parser/writer, SETTINGS, error
  values, and non-template protocol machinery.
- `ZhttpH2Session.hh`: statically composed connection, stream, flow-control,
  and logical-link adapters.
- `ZhttpTLSEngine.hh`: physical TLS ALPN dispatch and H1/H2 client/server
  session ownership.
- existing `ZhttpMessage.hh`, `ZhttpClientPool.hh`, `ZhttpAgent.hh`,
  `ZhttpService.hh`, and `ZhttpConfig.hh`: profile-neutral coordination.

Use `.cc` files for tables, frame validation, HPACK state transitions, and
other code that does not depend on application header typelists.  Headers
should contain only the static boundary needed to call application templates.

### Shard and ownership model

For each H2 physical connection:

- Rx owns input framing, the HPACK decoder, local receive windows, peer
  SETTINGS validation, request semantic state, the Rx stream registry, and
  receive-side GOAWAY/error state.
- Tx owns frame generation, the HPACK encoder, peer receive windows, output
  scheduling, the Tx stream registry, and pending output buffer references.
- fixed setting/window/error metadata crosses shards by value;
- body/header bytes cross shards only in destination-owned or retained pooled
  buffers;
- no lock makes non-owner access acceptable.

An H2 stream should be one heap-identified, intrusively referenced object with
separate Rx- and Tx-owned subobjects/nodes, an immutable stream ID, and a raw
back-pointer to its longer-lived physical session.  The physical session owns
and drains streams; stream/buffer objects must not retain the session and form
cycles.

Creation is not application-visible until Rx creation, Tx registration, and
the return continuation to Rx have completed.  Destruction first prevents
further Rx use and removes the Rx registry entry, then posts Tx removal and
queued-output drain, then returns to Rx for exactly-once application
completion and final release.

### Buffer and allocation model

- Parse directly from the pooled plaintext `Ztls::RxStream`.
- Deliver DATA spans synchronously through the existing body callback.  Return
  flow-control credit when the underlying receive bytes are actually consumed,
  not merely when the frame header is parsed.
- Retain only bounded partial frame/HPACK state across buffers.  Do not
  concatenate a whole header block, DATA frame, or body.
- Use `ZiTxLayer`/`ZiIOBuf` headroom or a purpose-built equivalent so the
  nine-byte H2 frame header is prepended/backpatched in the TLS plaintext
  buffer.  Stream HPACK output into HEADERS/CONTINUATION frames.
- H2 must add no intermediate payload copy above the copy/encryption already
  required by the current TLS Tx path.  “Zero copy” acceptance means no extra
  H2 staging buffer, not an unsupported claim that TLS encrypts arbitrary
  application memory in place.
- All variable storage has an explicit bound and `ZmHeap`/`ZmVHeap`/container
  heap ID.  No unexplained fixed arrays or capacities.
- Control-frame and small-header hot paths must not allocate per frame.

### Error and teardown model

Use one typed error funnel per physical connection:

- connection error: retain the first error, queue at most one GOAWAY, stop new
  streams, best-effort flush, then close the TLS transport;
- stream error: queue one RST_STREAM and complete only that logical link;
- HPACK synchronization failure: connection `COMPRESSION_ERROR`;
- transport failure: fail all logical links without pretending GOAWAY reached
  the peer.

Orderly stop is asynchronous and continuation-bearing:

1. stop listener/request ingress and mark sessions draining;
2. on Rx, cancel/del timers, send or schedule graceful GOAWAY, reject new
   streams, and drain accepted streams according to policy;
3. post an Rx continuation to drain late input/timer callbacks;
4. post Tx work to drain/cancel queued stream output and emit final
   GOAWAY/RST_STREAM frames;
5. from the Tx continuation, post back to Rx and initiate native TLS
   disconnect/engine stop;
6. wait for native `Ztls::stop(done)` and all logical disconnect callbacks;
7. return to Rx for final registry/table assertions and invoke the retained
   H2/TLS stop completion exactly once.

No I/O shard may block.  A synchronous no-argument `stop()` is only a
main-thread wrapper around `stop(done)`.  No composing library call may infer
completion from a posted function or from return of an internal no-argument
`stop_`.  `final()` must assert that timers, streams, physical sessions,
pending callbacks, and output queues are already empty; it must not silently
clear live owners.

## Protocol scope

Required:

- TLS ALPN `h2` with `http/1.1` fallback;
- client and server connection preface;
- DATA, HEADERS, PRIORITY, RST_STREAM, SETTINGS, PUSH_PROMISE, PING, GOAWAY,
  WINDOW_UPDATE, CONTINUATION, and unknown extension frames;
- all mandatory stream states and connection/stream error scopes;
- HPACK static and dynamic decoding; conservative but compliant encoding;
- connection and stream flow control;
- multiplexed requests, trailers, informational responses including 103,
  ordinary CONNECT, graceful drain, cancellation, and safe retry boundaries;
- generic Extended CONNECT substrate needed later by `libZws`.

Not in scope:

- `h2c`, prior-knowledge cleartext H2, or HTTP/1 Upgrade;
- server push production, push caching, or accepted-push delivery;
- RFC 7540 priority-tree scheduling;
- cross-origin connection coalescing;
- WebSocket framing or WebSocket handshake policy;
- a proxy, gateway, or H1/H2/H3 translation application.

Push remains disabled:

- H2 clients send `SETTINGS_ENABLE_PUSH = 0`;
- H2 servers never send PUSH_PROMISE;
- prohibited/role-invalid H2 push produces the exact RFC 9113
  `PROTOCOL_ERROR`;
- H3 clients do not send MAX_PUSH_ID, and defined prohibited push frames or
  streams produce the exact RFC 9114 error rather than extension-ignore
  behavior.

Unknown extensions continue to follow the applicable RFC ignore rules.  Do not
classify a defined push frame/stream as unknown.

## Delivery discipline

Each phase is a buildable, tested slice.  Do not add a dormant parallel H2
stack that is activated only in the last phase.  A phase may start only after
the previous phase's acceptance criteria and concluding
`GUIDELINES.md` audit/repair gate pass.

For every phase:

- add production code, deterministic tests, build/install entries, and
  documentation together;
- build the affected library default target before its tests;
- keep ordinary tests offline and independent of third-party services;
- record compiler, build type, exact commands, and diagnostic tools;
- fix failures instead of weakening assertions or increasing sleeps/timeouts;
- use semaphores/blocks only from main/control test threads, never I/O shards;
- run `git diff --check`.

The known high-RSS GCC translation units must be measured and scheduled
capacity-safely during development.  Before the final required clean parallel
repository build, move or explicitly instantiate enough non-template work in
`libZhttp` that adding H2 cannot reproduce a system-wide memory lockup.

## Phase 1: separate transport, HTTP profile, and logical multiplexing

**Purpose:** remove the architectural assumptions that would otherwise make
H2 a special case throughout the library.

### Slices

1. Add `Version::H2`, the profile composition, and valid-composition detector.
2. Remove `HTTPVersion` and HTTP `Multiplexed` from native transport traits.
   Retain only native secure/datagram/type/configuration facts.
3. Make message traits consume an HTTP profile.  Add an H2 placeholder trait
   containing metadata only; do not add wire behavior yet.
4. Update `ClientMessage`, `ServerSession`, link adapters, and common test
   templates to use profile/message traits.  H1TCP, H1TLS, and H3QUIC behavior
   must remain byte-for-byte unchanged.
5. Store negotiated `httpVersion` independently in `Agent::Attempt`,
   `AgentEvent`, and `Result`.  Remove every `QUIC ? H3 : H1` inference.
6. Split logical request admission from physical-session reuse in
   `ClientPool`.  Preserve current H1/H3 behavior while making concurrency a
   profile/session policy, not a Boolean transport trait.
7. Adapt `Service` parser/builder/session templates to a profile while keeping
   physical admission keyed to native connections.
8. Update all in-tree users and tests directly; delete obsolete transport-to-
   version aliases and branches.

  `Datagram`, or a native `Multiplexed` flag;
- one common fixture instantiates H1TCP, H1TLS, and H3QUIC;

  by the session;
- existing routing, Alt-Svc, fallback, reuse, cancellation, and lifecycle
