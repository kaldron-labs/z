# `ZtlsPK` X25519 implementation plan

Add standalone X25519 key derivation and agreement to `ZtlsPK` for
[`age.md`](age.md) and [`kem2.md`](kem2.md). This is an RFC 7748
key-agreement capability, **not** Ed25519 signing, a generic Weierstrass
`PK_EC` key, TLS key exchange, or an age recipient encoder. The wire and
key-serialization references are [RFC 7748](https://www.rfc-editor.org/rfc/rfc7748)
and [RFC 8410](https://www.rfc-editor.org/rfc/rfc8410).

## Boundary and API

- Define `PK_X25519` and `SK_X25519` in the existing `Ztls::PK`
  namespace and `ZtlsPK.hh`, following nearby `PK_ED25519_` /
  `SK_ED25519_` naming, `Type_<Heap = ZuVoid>`, concrete `ZmHeap`
  aliases, `ZuDerive`, `Secret` values, protected public-key default
  constructor, and the private type's `using PK`, `using PK_`, and
  `using PK_::key`. Do not introduce a `Ztls::X25519` namespace,
  another persistent key owner, or virtual capability methods.
- Both raw private seed and raw public key are exactly 32 bytes. The
  public type imports/exports the raw public key and saves an RFC 8410
  SubjectPublicKeyInfo. The private type accepts a caller-provided raw
  private seed, can generate a new key using the existing `Random &`
  constructor convention, exports raw private seed only to a caller-owned
  mutable span when needed for age identity encoding, exports/derives
  its public key, saves RFC 8410 PKCS#8, and can make an independently
  owned public-only key using `mkPK`. Never log or retain caller spans.
- Expose one private-key `agree(ZuBSpan peerPublic, ZuSpan<uint8_t> secret)`
  operation returning `ZuUnion<void, ZeException>`. It consumes the
  peer's 32-byte raw public key and writes the 32-byte shared secret
  directly to caller storage. The raw-span peer boundary avoids allocating
  a persistent `PK_X25519` for each ephemeral age stanza; backend-owned
  transient OpenSSL key/context objects are still permitted. Do not add
  `sign`, `verify`, or `saveCSR`: X25519 is key agreement, not a
  signature algorithm.
- Keep Bech32 age keys, age stanza wrapping, SSH-Ed25519 conversion,
  hybrid SHAKE/SHA3 composition, and HPKE out of this plan. `kem2.md`
  consumes only raw X25519 public derivation and agreement. Do not
  repurpose `Ztls::Backend::key_exchanges()` or
  `ptls_openssl_x25519` as if their TLS key-exchange interface exposed
  deterministic raw seed import and caller-span agreement.

## Backend and serialization

1. Add narrow `pkey_x25519_*` functions in `ZtlsBackend.hh` and
   `ZtlsOpenSSL.cc` for generation, raw private/public import, raw
   private/public export, and agreement. Match existing `PKey *` /
   `const PKey *` and `ZuBSpan` / `ZuSpan<uint8_t>` conventions;
   backend functions return `bool`, and `ZtlsPK.hh` translates failures
   to `ZeException`. Reuse the existing `Backend::PKey` owner and
   `replace_pkey_` pattern. Build a candidate key, free it on failure,
   and replace the old one only after success.
2. Use OpenSSL's X25519 raw-key import/generation and public export for
   deterministic public derivation from a supplied 32-byte seed. Use
   `EVP_PKEY_derive` with a transient imported peer public key for
   agreement. Check OpenSSL's returned length before declaring success.
   Reject an all-zero shared secret if the provider does not already fail
   for a small-order peer; this is the RFC 7748/age security boundary,
   not gratuitous point validation. On failure, clear any written
   caller secret bytes. Keep OpenSSL includes and API calls in the
   backend, not in `ZtlsPK.hh`, `ZtlsAge.cc`, or `kem2` wrapper code.
3. Add the RFC 8410 X25519 OID `1.3.101.110` to `ZtlsPK_Data.hh`.
   X25519 and Ed25519 use the same SPKI and PKCS#8 ASN.1 *shape* with
   different OIDs and cryptographic operations. Reuse the existing
   `ZfASN1` metadata, factoring the two representations into shared
   accurately named 25519/OKP views if that avoids duplicate structs;
   propagate any rename through Ed25519 dependents rather than adding
   shims. AlgorithmIdentifier parameters are absent; the public BIT
   STRING contains the raw 32 bytes and the private OCTET STRING
   contains the RFC 8410 nested 32-byte private key. Do not hand-code
   DER lengths, OIDs, or PEM.
4. Extend `Load_::keyType`, `LoadPK`, and `LoadSK` for the X25519
   OID, then reuse `savePEM`, `saveFile`, `loadPEM`, and
   `loadFile`. Use `ZfASN1` directly for save/load, following
   `ZtlsPK` patterns. Check only exact format/key extents and backend
   success; do not demand an X25519 public value be in a canonical
   representative form when RFC 7748 agreement can interpret it.
   Clear private export scratch with `ZuClear` on every exit.

## Storage and verification

- Use the existing concrete `ZmHeap` key-object pattern. Keep raw
  32-byte temporary keys/secrets in contract-sized primitive arrays or
  tagged stack-backed scratch; write output directly into caller spans.
  Avoid temporary contiguous copies, zero-before-overwrite, nested
  heap-allocated key wrappers, and additional owning containers. A
  separately owned `mkPK` necessarily imports an exported 32-byte
  public value; no private `EVP_PKEY` is shared into the public object.
- Add focused `ztls/test/ZtlsX25519Test.cc` using `ZuTestUtil`. Cover
  RFC 7748 Alice/Bob public and shared-secret vectors, generated and
  seed-imported keys, public import/export, `mkPK`, exact span sizes,
  small-order peer failure, and independent public/private save→load
  through DER and PEM. Check OpenSSL CLI interoperability in both
  directions for RFC 8410 keys; a self-round-trip is insufficient.
  Confirm private scratch is cleared on failed operations. Do not
  require malformed-but-interpretable public bytes to be rejected.
- Add no new external dependency or separate crypto implementation:
  `libZtls` already links OpenSSL. Use the current configured build,
  batch changes, rebuild `ztls/src` before `ztls/test`, and defer
  dependent rebuilding to the end. Run the focused suite and a sparse
  final Valgrind gate. Do not change other build configurations unless
  separately requested. Review against all applicable
  `GUIDELINES.md` flags, especially direct dependencies, hard tabs,
  concrete heaps, stack scratch, and minimal validation.

Completion requires the standalone `ZtlsPK` raw X25519 agreement and
RFC 8410 key load/save to work without direct OpenSSL use by age or
`kem2`; it does not claim age file-format interoperability.
