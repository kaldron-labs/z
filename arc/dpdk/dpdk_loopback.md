Yes—use a **software poll-mode driver (PMD)**. No physical NIC, VFIO binding, or IOMMU is needed.

**For a simple TX → RX loopback, use `net_ring`.** It exposes an in-memory ring through the normal DPDK Ethernet APIs. DPDK documents this specifically for testing without Ethernet hardware. [Ring PMD documentation](https://doc.dpdk.org/guides/nics/ring.html)

Assuming `dpdk-testpmd` and the ring driver are installed:

```bash
# Replace 0-1 with two CPUs available to your process.
dpdk-testpmd -l 0-1 \
  --no-pci --no-huge --no-shconf -m 256 \
  --vdev=net_ring0 \
  -- -i --nb-cores=1 --total-num-mbufs=4096 \
  --rxq=1 --txq=1 --disable-rss \
  --port-topology=loop --forward-mode=io
```

At its prompt:

```text
start tx_first
show port stats all
stop
quit
```

Wait a few seconds before displaying statistics. `start tx_first` injects the initial packets; forwarding then circulates them through the ring. RX and TX counters should increase. Plain `start` has no initial traffic to circulate. [Testpmd commands](https://doc.dpdk.org/guides/testpmd_app_ug/testpmd_funcs.html)

Here, `--no-pci` disables PCI discovery and `--no-huge` uses ordinary memory, avoiding hugepage setup. This configuration does not support DPDK primary/secondary shared-memory operation. [EAL options](https://doc.dpdk.org/guides/linux_gsg/linux_eal_parameters.html)

**For testing your actual TCP/UDP application, choose the connection you need:**

| Test arrangement | Suitable approach |
|---|---|
| One process, packet loopback | `net_ring` |
| Two endpoints within one process | Two ports created with `rte_eth_from_rings()`, with RX/TX rings cross-connected |
| Linux socket client ↔ DPDK protocol stack | `net_tap` |
| Two independent DPDK processes | Linux `veth` pair, with `net_af_packet` attached to each end |
| Repeatable packet input/output | `net_pcap` with input/output capture files |

These are supported by the [ring](https://doc.dpdk.org/guides/nics/ring.html), [TAP](https://doc.dpdk.org/guides/nics/tap.html), [AF_PACKET](https://doc.dpdk.org/guides/nics/af_packet.html), and [PCAP](https://doc.dpdk.org/guides-24.11/nics/pcap_ring.html) drivers.

For example, launch your protocol-stack application with these **EAL arguments**:

```bash
sudo ./your-app -l 0-1 --no-pci --no-huge \
  --vdev=net_tap0,iface=dtap0 -- <application-options>
```

Then configure the Linux side:

```bash
sudo ip addr add 192.0.2.1/24 dev dtap0
sudo ip link set dtap0 up
```

Configure **192.0.2.2/24 inside your DPDK application’s stack**, and connect from Linux to that address. Do not assign `.2` to Linux as well: local routing would bypass your application. The application must implement the relevant ARP/IP/TCP/UDP handling; DPDK itself supplies packet I/O.

Use these setups for functional testing and software-path measurements. They do not validate physical NIC DMA, hardware offloads, or wire latency.
