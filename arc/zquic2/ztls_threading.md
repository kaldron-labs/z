## Summary

The goal is to decouple Ztls receive processing from transmit processing and
replace the current single dedicated TLS thread with explicit `rxThread` and
`txThread` ownership. Compatibility with existing Ztls callers is a non-goal:
the single `thread` parameter, shared default buffer allocator, and callback
assumptions that make Tx-local calls from Rx callbacks should be removed and
fixed throughout dependent code.

The practical design is not to add another TLS record framing layer. The
existing `parseHdr<RxBufAlloc>()` plus `ZiRx::recv` path already frames complete
TLS records from TCP on the I/O Rx thread and should remain the receive framing
integration. The new work is to split Ztls control-plane state, application Rx,
and application Tx ownership around that framing path.

The recommended final architecture is:

- `rxThread` owns connection lifecycle, handshake and post-handshake picotls
  control state, TLS record Rx, `RxStream`, and application callbacks.
- `txThread` owns application Tx buffers, application record encryption, Tx
  sequence state, and ordered socket-send handoff.
- TLS 1.3 application records use Ztls-owned per-direction record protection so
  KeyUpdate can be handled correctly without concurrent access to one `ptls_t`.
- TLS 1.2 is preserved by validating and then using per-direction imported
  post-handshake picotls contexts for record processing, because TLS 1.2 has no
  KeyUpdate and existing tests already exercise `ptls_build_tls12_export_params`
  plus `ptls_import`.
- Initial handshake remains Rx-owned. Handshake output is generated by the
  Rx-owned picotls control state and handed to the Tx path as serialized records.
  Moving handshake record protection itself to Tx would require a full
  message-layer TLS-over-TCP implementation and should not be part of this
  migration unless it becomes a separate requirement.

This plan keeps the existing Ztls buffer invariants, but it will require a
follow-up rewrite of `ztls/buffers.md` once application-data paths stop using
`ptls_receive()` and `ptls_send()` directly for TLS 1.3 records.

## Architecture Documentation

### New Or Changed Components

`ztls/src/Ztls.hh`

- Replace `EngineParams(mx, thread, alpn)` with
  `EngineParams(mx, rxThread, txThread)` and fluent `.alpn(...)`.
- Replace `Engine::m_thread` with `m_rxThread` and `m_txThread`.
- Replace generic `run()`, `invoke()`, and `invoked()` with
  `rxRun()`, `rxInvoke()`, `rxInvoked()`, `txRun()`, `txInvoke()`, and
  `txInvoked()`.
- Split public/default allocators into direction-specific aliases:

```c++
template <
  unsigned Size = ZiIOBuf_DefltSize,
  unsigned MaxSize = ZiIOBuf_DefltMaxSize,
  ZuString HeapID = "Ztls.RxBuf">
using RxBufAlloc = Ztls_::BufAlloc<Size, MaxSize, HeapID>;

template <
  unsigned Size = ZiIOBuf_DefltSize,
  unsigned MaxSize = ZiIOBuf_DefltMaxSize,
  ZuString HeapID = "Ztls.TxBuf">
using TxBufAlloc = Ztls_::BufAlloc<Size, MaxSize, HeapID>;
```

- Change `CliLink` and `SrvLink` defaults to
  `RxBufAlloc = Ztls::RxBufAlloc<>` and
  `TxBufAlloc = Ztls::TxBufAlloc<>`.
- Remove the public `Ztls::BufAlloc` compatibility alias before completion.
- Add a stable `TlsInfo` snapshot for application/test inspection:

```c++
struct TlsInfo {
  int tlsver = 0;
  uint16_t protocolVersion = 0;
  uint16_t cipherID = 0;
  const char *alpn = nullptr;
  bool psk = false;
};
```

`ztls/src/ZtlsRecord.hh` or `ztls/src/ZtlsProt.hh`

- Add a focused record-protection component, not a receive-framing component.
- It should not replace `parseHdr` or `ZiRx::recv`.
- It should encapsulate:
  - TLS 1.3 traffic secrets.
  - TLS 1.3 AEAD contexts using `Ztls::Pico::AeadCtx`.
  - per-direction sequence numbers.
  - TLS 1.3 record encryption/decryption.
  - TLS 1.3 inner content-type parsing.
  - TLS 1.3 KeyUpdate traffic-secret advancement.
  - TLS 1.2 imported post-handshake `ptls_t` contexts if the validation phase
    confirms this is reliable for per-direction record processing.

`ztls/buffers.md`

- Update after implementation to distinguish:
  - network record framing with `parseHdr` and `ZiRx::recv`;
  - Rx-owned plaintext publication to `RxStream`;
  - Tx-owned plaintext staging and record encryption;
  - TLS 1.3 Ztls-owned protection;
  - TLS 1.2 imported-context protection.

### New Or Changed Processes Or Threads

`rxThread` owns:

- TCP connection lifecycle events posted from `Cxn::connected()` and
  `Cxn::disconnected()`.
- client connect retry and server listen retry scheduling.
- `ptls_t` control state for handshake and post-handshake message handling.
- async certificate-signing resume after `ZiEventLoop` readiness.
- complete inbound TLS records after `ZiRx::recv` framing.
- Rx record decryption and alert/post-handshake processing.
- `m_rxStream` and application `process()`.
- application callbacks `connected()`, `disconnected()`, and `connectFailed()`.

`txThread` owns:

- application Tx buffers produced by `txStream()` and `send()`.
- Tx record-protection state and sequence numbers.
- emission order for control records versus application records.
- serialized record handoff to `ZiConnection::send()`.

The multiplexer I/O Rx and I/O Tx threads remain separate from Ztls logical
`rxThread`/`txThread`. Ztls validation should allow Ztls Rx/Tx to default to
the multiplexer I/O threads only if that remains an intentional supported mode;
for high-throughput deployments the examples/tests should keep dedicated
isolated Ztls Rx/Tx threads distinct from `mx->rxThread()` and
`mx->txThread()`.

### New Or Changed Interfaces

Parameter API:

```c++
struct EngineParams {
  EngineParams(
    ZiMultiplex *mx = nullptr,
    ZuCSpan rxThread = {},
    ZuCSpan txThread = {});

  EngineParams &&alpn(ZuSpan<ZuCSpan>);
  EngineParams &&caPath(ZuCSpan);
  EngineParams &&certPath(ZuCSpan);
  EngineParams &&keyPath(ZuCSpan);
  EngineParams &&asyncThread(ZuCSpan);
  EngineParams &&errorFn(ErrorFn);

  ZiMultiplex *mx = nullptr;
  ParamString rxThread;
  ParamString txThread;
  ParamStrings alpn_;
  ParamString caPath_;
  ParamString certPath_;
  ParamString keyPath_;
  ParamString asyncThread_;
  ErrorFn errorFn_;
};
```

Apply the same constructor and fluent `alpn()` shape to `ClientParams` and
`ServerParams`. Existing old-style calls such as:

```c++
Ztls::ClientParams(&mx, "3", alpn)
```

must become:

```c++
Ztls::ClientParams(&mx, "3", "4").alpn(alpn)
```

Thread-local Link API:

- `txStream_()`, `send_()`, and Tx protection helpers are valid only on
  `txThread`.
- `txStream()`, `send()`, `updateKey()`, and `disconnect()` are public
  cross-thread APIs.
- Application callbacks run on `rxThread`; callbacks should use public Tx APIs
  unless they explicitly post work to `txThread`.
- `updateKey_()` should either be removed from application-visible protected
  surface or asserted as Tx/control internal. A public `updateKey()` should
  schedule the correct control-plane sequence.

### New Or Changed Data Flows

Inbound TLS record:

1. Multiplexer I/O Rx reads bytes into `ZiIOContext`.
2. Existing `ZiRx::recv<parseHdr<RxBufAlloc>, &Impl::recvRecord>(io)` frames a
   complete TLS record into an `RxBufAlloc`.
3. `recvRecord()` posts the framed buffer to Ztls `rxThread` with connection
   generation identity.
4. `rxThread` rejects stale generation/connection events.
5. Before handshake completion, `rxThread` calls the existing picotls handshake
   path.
6. After handshake completion:
   - TLS 1.3 records are decrypted by Ztls-owned Rx protection state.
   - TLS 1.2 records are decrypted by the Rx imported picotls record context.
7. Application data is published by setting `skip`/`length` as today and
   pushing the buffer to `m_rxStream`.
8. `process(m_rxStream)` runs on `rxThread`.

Outbound application data:

1. Application code calls `txStream()` or `send()`.
2. Ztls allocates `TxBufAlloc` and stages plaintext after negotiated headroom.
3. Completed plaintext buffers are posted to `txThread`.
4. `txThread` inserts any pending control records before application data.
5. `txThread` encrypts to serialized TLS records:
   - TLS 1.3 through Ztls-owned Tx protection.
   - TLS 1.2 through the Tx imported picotls record context.
6. Serialized records are passed to `ZiTx::send()`/`ZiConnection::send()`.

Control-plane events:

- The Rx-owned picotls control state produces handshake and post-handshake
  control messages.
- Tx-owned record protection emits those messages in-order as TLS records.
- KeyUpdate is modeled as a control event that carries both the control message
  and the new Tx secret/state transition ordering requirement.

### New Or Changed Event-Driven Or Timer Processing

- `CliLink::connect()` posts to `rxThread`, not a generic TLS thread.
- reconnect timers use `rxRun(...)` because connection setup is Rx-owned.
- `Server::listenFailed()` retry scheduling uses `rxRun(...)`.
- async certificate signing still uses `ZiEventLoop` on `asyncThread`, but
  readiness resumes with `rxRun(...)`.
- Tx control timers are not needed initially. If Tx backpressure metrics are
  added, they should live on `txThread`.

### New Or Changed Network Programming

- Keep `ZiConnection::send()` as the socket Tx entry point. It already posts to
  the multiplexer Tx thread and queues buffers through `ZiTx`.
- Keep `ZiRx::recv` as the TCP framing entry point. It already handles partial
  frames, growth to the framed size, and copying trailing bytes into a new Rx
  buffer because framed messages are queued asynchronously.
- Do not add a parallel TCP parser for TLS records.

### New Or Changed Data Stores

No persistent data stores are introduced. New per-link in-memory state is:

- connection generation counter;
- `TlsInfo` snapshot;
- Rx protection state;
- Tx protection state;
- pending Tx control queue;
- optional TLS 1.2 imported Rx/Tx `ptls_t` contexts;
- diagnostics counters for thread-affinity violations and Rx/Tx heap
  allocations.

## Detailed Design and Implementation Plan

### Phase 1 - API Shape, Validation, And Build-Break Cascade

Focus: make the public threading model explicit and force dependent code to
migrate.

Modify `ztls/src/Ztls.hh`:

- Replace `EngineParams(mx, thread, alpn)` with
  `EngineParams(mx, rxThread, txThread)` plus `.alpn(...)`.
- Add `ClientParams` and `ServerParams` forwarding methods for `.alpn(...)`.
- Replace `m_thread` with `m_rxThread` and `m_txThread`.
- Add `rxThread()`, `txThread()`, `rxRun()`, `rxInvoke()`, `txRun()`,
  `txInvoke()`, `rxInvoked()`, and `txInvoked()`.
- Update validation using the `Zquic::Engine` pattern:
  - `mx` is required.
  - `mx` must be running.
  - unset Rx defaults to `mx->rxThread()`.
  - unset Tx defaults to `mx->txThread()`.
  - Rx and Tx IDs must resolve through `mx->sid(...)`.
  - Rx and Tx must differ.
  - `asyncThread` must differ from Ztls Rx, Ztls Tx, and the multiplexer I/O
    Rx/Tx threads, and must be isolated.
- Add `TlsInfo` but populate it only from the existing single-threaded state in
  this phase.

Dependent code cascade:

- Replace all `Ztls::ClientParams(&mx, "3", alpn)` and
  `Ztls::ServerParams(&mx, "3", alpn)` calls.
- Replace config key `thread` with `rxThread` and `txThread` in wrappers.
- Update tests so old constructors no longer compile.

API behavior validated:

- `ZmScheduler::invoke(sid, fn)` executes synchronously only when already on
  that scheduler thread; otherwise it enqueues and wakes the thread.
- `ZmScheduler::run(sid, fn)` always enqueues asynchronously.
- `ZiMultiplex` exposes `rxRun/rxInvoke` and `txRun/txInvoke`; Ztls should use
  its own logical thread IDs rather than always forwarding to multiplexer I/O
  Rx/Tx.

Phase dependencies:

- This phase does not depend on record-protection work.
- It enables every later phase to use explicit Rx/Tx thread names.

### Phase 2 - Buffer Heap Segregation And Thread-Affinity Assertions

Focus: split role allocation and catch incorrect use while behavior is still
close to the current implementation.

Modify `ztls/src/Ztls.hh`:

- Add public `RxBufAlloc` and `TxBufAlloc` aliases.
- Change `CliLink` and `SrvLink` defaults to use separate aliases.
- Keep the current `Ztls_::IOQueue` intrusive node unless diagnostics prove a
  separate Rx/Tx queue node is needed. Heap identity already comes from
  `Zi::IOBufAlloc<..., HeapID>`.
- Update `TxStream_` so `txStream_()` asserts `app()->txInvoked()`.
- Update Rx-local methods so they assert `app()->rxInvoked()` once dispatch is
  changed.
- Keep a temporary internal `using BufAlloc = RxBufAlloc` only if it is needed
  to stage edits; remove it before acceptance.

Dependent code cascade:

- Tests and examples that currently write `using BufAlloc = Ztls::BufAlloc<>`
  should become either separate aliases or rely on defaults:

```c++
using RxAlloc = Ztls::RxBufAlloc<BufSize, MaxSize>;
using TxAlloc = Ztls::TxBufAlloc<BufSize, MaxSize>;
struct Link : public Ztls::CliLink<App, Link, RxAlloc, TxAlloc> { ... };
```

API behavior validated:

- `ZiRx::recv` allocates `BufAlloc` for framed receive buffers and uses a fresh
  buffer when trailing bytes belong to the next frame. This supports queued Rx
  processing and should not be replaced.
- `ZiTx::send` sets `buf->owner`, queues through `ZiConnection::send()`, and
  runs socket writes on the multiplexer Tx thread.
- `ZiTxStream` assumes each flushed buffer is a protocol frame; this matches
  the one-TLS-record-per-buffer invariant.

Phase dependencies:

- Depends on Phase 1 for `txInvoked()`/`rxInvoked()`.
- Does not require actual Tx encryption to move yet.

### Phase 3 - Lifecycle And Application Callback Dispatch To Rx

Focus: move connection lifecycle and application Rx callbacks to `rxThread`
end-to-end while still allowing the existing picotls record calls to work.

Modify `Link`:

- Rename ownership-visible methods:
  - `connected_1()` -> `rxConnected_()`.
  - `record_()` -> `rxRecord_()`.
  - `handshake_()` -> `rxHandshake_()`.
  - `rcvd_()` -> `rxRcvd_()`.
  - `disconnected_()` -> `rxDisconnected_()`.
- `connected_0()` should post to `app()->rxRun(...)`.
- `recvRecord()` should post to `app()->rxRun(...)`.
- `disconnected_0()` should post to `app()->rxRun(...)`.
- `CliLink::connect()` and reconnect timers should use `rxInvoke/rxRun`.
- `Server::listenFailed()` retry scheduling should use `rxRun`.
- `asyncReady_()` should resume through `rxRun`.
- Add connection generation checks around posted Rx work.

Keep in this phase:

- `ptls_handshake()`, `ptls_receive()`, and `ptls_send()` may still execute on
  `rxThread` as a transitional behavior.
- Public `send()` should post to Tx only after Phase 4.

Phase dependencies:

- Depends on Phase 1 scheduling helpers.
- Benefits from Phase 2 assertions.
- Produces a vertical milestone: callbacks are no longer on a generic TLS
  thread; they are explicitly Rx-owned.

### Phase 4 - Public Tx Facade And Ordered Tx Queue Skeleton

Focus: make all application Tx calls flow through `txThread`, even before final
record-protection ownership is complete.

Modify `Link`:

- `txStream()` allocates `TxBufAlloc` and posts completed buffers to
  `txThread`.
- `send()` posts to `txThread`.
- `txStream_()` remains Tx-local only.
- Add a Tx work queue or simple `txRun` event model for:
  - application plaintext buffers;
  - handshake/control serialized buffers produced by Rx;
  - close requests;
  - key-update requests.
- Add `txReady` state. Before handshake completion, Tx should either queue
  application data or reject with a diagnostic. Prefer queueing only after a
  clear existing caller requires early send; otherwise reject until ready.

Transitional behavior:

- For TLS 1.3 and TLS 1.2, this phase may still bounce encryption back to the
  Rx-owned picotls state behind a temporary gate. This is explicitly
  transitional and must be removed before acceptance.
- The purpose is to update application-facing call sites and ordering, not to
  claim final decoupling.

Dependent code cascade:

- Replace `txStream_()` uses inside Rx callbacks with `txStream()`:
  - `ztls/example/ZtlsClient.cc`
  - `ztls/example/ZtlsServer.cc`
  - `ztls/test/ZtlsBufHookTest.cc`
  - `zhttp/example/zhttpclient.cc`
  - `zws/src/Zws.hh`
- Replace direct `tls()` inspection with `TlsInfo`.

Phase dependencies:

- Depends on Phase 3 callback thread ownership.
- Sets up the ordering mechanism needed by KeyUpdate and close_notify.

### Phase 5 - TLS 1.2 Direction Split With Imported Picotls Contexts

Focus: preserve TLS 1.2 without building a custom TLS 1.2 record layer first.

Validation spike, then implementation:

- After a TLS 1.2 handshake completes, call `ptls_export()` on the Rx-owned
  control `ptls_t`.
- Import the exported parameters twice:
  - `m_rxTLS12` used only on `rxThread` for `ptls_receive()`.
  - `m_txTLS12` used only on `txThread` for `ptls_send()` and
    `ptls_send_alert()`.
- Confirm duplicated imports preserve independent receive/send sequence state.
- Confirm close_notify can be sent by the Tx imported context and received by
  the Rx imported context.

Why this phase comes before TLS 1.3 custom protection:

- TLS 1.2 has no KeyUpdate, so per-direction imported contexts are less risky.
- Existing `ZtlsBufHookTest` already demonstrates imported TLS 1.2 record state
  through `ptls_build_tls12_export_params()` and `ptls_import()`.
- This creates an early true Rx/Tx split for one negotiated protocol version.

Fallback if validation fails:

- Use `ptls_get_traffic_keys()` as the next candidate for TLS 1.2 record
  offload, but treat it as higher risk because the header explicitly calls out
  missing API coverage for key updates and close alerts in offload scenarios.

Phase dependencies:

- Depends on Phase 4 Tx queue and ordering.
- Does not depend on TLS 1.3 custom protection.

### Phase 6 - TLS 1.3 Traffic Secret Capture And Record Protection

Focus: establish Ztls-owned TLS 1.3 application record protection.

Modify context initialization:

- Install `ptls_context_t::update_traffic_key`.
- Capture traffic secrets for epoch >= 3.
- Do not reuse `Zquic::PacketProtection::deriveTrafficSecret()` unchanged:
  that code derives QUIC keys with labels `quic key`, `quic iv`, and
  `quic hp`. TLS stream records need TLS 1.3 record labels `key`, `iv`, and
  `traffic upd` with the `tls13 ` prefix.
- Reuse `Ztls::Pico::AeadCtx` for AEAD allocation and disposal.

Add TLS 1.3 protection state:

```c++
struct TrafficState {
  Ztls::Pico::AeadCtx aead;
  uint8_t secret[64] = {};
  uint8_t key[32] = {};
  uint8_t iv[16] = {};
  unsigned secretLen = 0;
  unsigned keyLen = 0;
  unsigned ivLen = 0;
  unsigned tagLen = 0;
  uint64_t seq = 0;
  ptls_cipher_suite_t *cipher = nullptr;
};
```

Record details to implement and test:

- TLS 1.3 outer record header uses content type application_data and legacy
  version `0x0303`.
- AEAD AAD is the 5-byte record header with encrypted length.
- Plaintext includes payload, optional zero padding, and inner content type.
  Use no padding initially.
- Decrypt strips trailing zero padding and the final inner content type.
- Nonce is derived from static IV and sequence number.
- Sequence numbers are per direction.
- When confidentiality limit approaches, Tx must request a KeyUpdate.

Phase dependencies:

- Depends on Phase 4 for Tx ordering.
- Uses Phase 3 Rx ownership for post-handshake handling.
- Can land with KeyUpdate disabled except for rejection/assertion until Phase 7
  completes.

### Phase 7 - TLS 1.3 Post-Handshake Messages And KeyUpdate

Focus: make TLS 1.3 control-plane behavior correct with split Rx/Tx state.

Rx post-handshake handling:

- When Rx decrypts a TLS 1.3 record with inner content type handshake, feed the
  decrypted handshake message bytes into `ptls_handle_message()` or
  `ptls_client_handle_message()`/`ptls_server_handle_message()` on `rxThread`.
- Honor `ptls_get_read_epoch()` behavior: callers must only feed messages at
  the expected epoch.
- Collect any emitted post-handshake handshake bytes and post them to Tx as
  ordered control records.

KeyUpdate:

- `update_traffic_key` callbacks happen on the thread that drives picotls
  control state. For received KeyUpdate, that is `rxThread`.
- Rx must install the new Rx secret before accepting subsequent records.
- If picotls emits a reciprocal KeyUpdate or a local update is requested, Rx
  posts a Tx control event that includes:
  - the plaintext KeyUpdate handshake bytes;
  - the corresponding new Tx traffic secret;
  - the connection generation and ordering point.
- Tx installs the new Tx secret at the exact point it emits the KeyUpdate
  control record, before subsequent application data.

Public API:

- Replace application-visible `updateKey_(bool)` with `updateKey(bool)` unless
  callers are explicitly on the Tx/control path.
- If a synchronous bool result is still required for tests, implement it with a
  small completion object or keep a test-only hook. Avoid blocking
  `rxThread` waiting on `txThread`.

Phase dependencies:

- Depends on Phase 6 TLS 1.3 protection.
- Depends on Phase 4 ordered Tx controls.

### Phase 8 - Disconnect, Alerts, And Close Ordering

Focus: make close behavior deterministic across Rx and Tx.

Modify disconnect flow:

- public `disconnect()` sets the atomic disconnecting flag and posts control to
  `rxThread`.
- Rx decides whether a close_notify is required.
- Tx emits close_notify in-order using:
  - TLS 1.3 record protection for TLS 1.3;
  - `m_txTLS12` for TLS 1.2.
- After Tx sends or intentionally skips close_notify, request socket close or
  disconnect through `ZiConnection`.
- Application `disconnected()` fires once on `rxThread`.

Preserve current behavior:

- `disconnect_(false)`-style hard close remains available internally for
  protocol errors and async failures.
- Existing `ZiConnection::disconnect()` already crosses Tx then Rx in the
  multiplexer; do not fight that path. Ztls should only ensure TLS alert bytes
  are queued before requesting socket teardown.

Phase dependencies:

- Depends on Phase 4 ordered Tx queue.
- Depends on Phase 5/6 protocol-specific Tx protection.

### Phase 9 - Remove Transitional Paths And Update Documentation

Focus: finish the migration.

Remove:

- any temporary `Ztls::BufAlloc` alias;
- any temporary single-picotls serialization gate for application data;
- old `thread` config handling;
- application-visible `tls()` access unless still needed by internal tests;
- stale comments referring to a single TLS thread.

Update:

- CRTP comments in `Ztls.hh`.
- architecture comments at the top of `Ztls.hh`.
- `ztls/buffers.md`.
- examples and wrapper docs/config samples.

Phase dependencies:

- Depends on Phases 1-8.
- This phase is not complete until old APIs fail to compile and no transitional
  gate remains.

## Acceptance Criteria

- `Ztls::EngineParams`, `ClientParams`, and `ServerParams` no longer accept the
  single-thread constructor.
- `Ztls::Engine` exposes explicit Rx/Tx scheduling helpers and no generic TLS
  thread helper.
- default Ztls Rx and Tx buffers use separate heap IDs.
- application callbacks run on `rxThread`.
- public application sends run encryption on `txThread`.
- no production application-data path serializes `ptls_send()` and
  `ptls_receive()` through one shared `ptls_t`.
- `parseHdr<RxBufAlloc>()` and `ZiRx::recv` remain the TCP record framing path.
- TLS 1.3 app data, KeyUpdate, alerts, and close_notify work across split
  Rx/Tx state.
- TLS 1.2 app data and close_notify continue to work or an explicit follow-up
  decision has removed TLS 1.2 support and its tests.
- direct application `tls()` inspection is replaced with `TlsInfo` or another
  thread-safe snapshot.
- all listed dependent call sites are migrated.
- `ztls/buffers.md` reflects the final implementation.

## Non-goals

- Retaining source compatibility with old Ztls parameter constructors.
- Retaining the `thread` configuration key in dependent wrappers.
- Adding a second TLS record framing path parallel to `parseHdr`/`ZiRx::recv`.
- Moving initial handshake record generation to `txThread` in this migration.
- Rewriting `ZiRx`, `ZiTx`, `ZiConnection`, or `ZiMultiplex`.
- Supporting concurrent calls into a single `ptls_t`.
- Duplicating Zquic QUIC packet protection logic for TLS stream records without
  changing labels, AAD, nonce, and record formatting.

## Options and Open Questions

### Decision: Keep Existing Framing

Keep `parseHdr<RxBufAlloc>()` and `ZiRx::recv` for TLS-over-TCP record framing.
The feedback is correct: adding a small generic record-layer helper for header
parsing would duplicate working code. The new component should be
record-protection/state only.

### Decision: Control `ptls_t` Is Rx-Owned

The one live picotls control state should be driven on `rxThread`. This avoids
concurrent picotls access and matches async handshake resume behavior. Tx
receives ordered secrets and plaintext control messages from Rx rather than
calling picotls directly for TLS 1.3 control-plane mutations.

### Decision: TLS 1.3 Needs Ztls-Owned Record Protection

`ptls_get_traffic_keys()` is not enough for a robust split because the local
header notes missing API coverage for KeyUpdate and close alerts in offload
scenarios. TLS 1.3 KeyUpdate correctness requires Ztls to understand
post-handshake messages and update Tx/Rx secrets in order.

### Decision: Preserve TLS 1.2 With Imported Contexts First

TLS 1.2 should be preserved initially through per-direction imported picotls
post-handshake contexts. This is lower risk than writing a TLS 1.2 record layer
immediately and aligns with existing imported TLS 1.2 tests. Phase 5 must
validate duplicated imports and close_notify behavior before deeper TLS 1.3
work depends on it.

### Contingency: TLS 1.2 Import Split Fails

If Phase 5 shows duplicated `ptls_import()` contexts cannot safely split Rx and
Tx record processing, the implementation owner must choose between:

- implementing TLS 1.2 record protection using `ptls_get_traffic_keys()` plus
  explicit IV/tag handling; or
- dropping TLS 1.2 support and removing/updating the TLS 1.2 tests.

That is the only remaining product-level decision likely to need resolution
during implementation.

### Risk: Local KeyUpdate API Semantics

The current `updateKey_(bool)` returns a synchronous bool and is callable from
callbacks today because callbacks run on the single TLS thread. In the split
model, local KeyUpdate is a control-plane operation that crosses Rx and Tx.
The plan should prefer an async public `updateKey()` API, with a test hook or
completion object only if synchronous tests need it.
