## Summary

The goal is to replace the positional `Ztls` initialization APIs with fluent parameter objects and to make TLS handshakes survive picotls `PTLS_ERROR_ASYNC_OPERATION` by integrating `ZiEventLoop`. The design keeps the existing single-threaded picotls model: all `ptls_t`, `ptls_context_t`, and `ptls_handshake_properties_t` access remains on the configured TLS scheduler thread. `ZiEventLoop` only waits for external async signing completion and then schedules handshake continuation back onto the TLS thread.

What is today:
- `Engine::init`, `Client::init`, and `Server::init` take positional arguments.
- `Link::handshake_()` has a disabled `PTLS_ERROR_ASYNC_OPERATION` block and treats async as fatal.
- `CliLink::connected_()` starts the ClientHello through `handshake__()` but does not use the same result handling as network-input handshakes.
- `ZiEventLoop` already supports external handles/sockets and is explicitly intended for OpenSSL async signing completion.
- `Ztls::Backend::SignCert` hides `ptls_openssl_sign_certificate_t::async`.
- `Server::init` accepts `cacheMax`, but current picotls code ignores it.

What will be after implementation:
- Public initialization uses `Ztls::EngineParams`, `Ztls::ClientParams`, and `Ztls::ServerParams`; old positional overloads are removed.
- `Engine` owns the optional async `ZiEventLoop`, its scheduler id, lifecycle state, and the async error callback.
- `Client` and `Server` enable OpenSSL async signing only when `asyncThread` is configured.
- All `ptls_handshake()` call sites flow through one result handler that flushes generated bytes, completes once, waits for more network input, or registers an fd-backed async job.
- Pending async event-loop registrations are cleaned up on handshake completion, disconnect, reset, and finalization.
- `ServerParams::cacheTimeout` preserves ticket lifetime behavior; `cacheMax` is intentionally absent from the new API.

Research notes:
- Local picotls documents the async contract in `/home/count0/src/picotls/include/picotls.h:772`: after `PTLS_ERROR_ASYNC_OPERATION`, obtain the job via `ptls_get_async_job`, wait on `get_fd` or a completion callback, then call `ptls_handshake` again. The same contract appears in the upstream picotls documentation: https://github.com/h2o/picotls/wiki/Using-picotls.
- Local picotls OpenSSL exposes `ptls_openssl_sign_certificate_t::async` in `/home/count0/src/picotls/include/picotls/openssl.h:193`.
- Comparable H2O/picotls deployments resume async TLS handshakes after an async job signals readiness, commonly through a ready fd for OpenSSL-backed work: https://www.fastly.com/blog/tls-more-secure-always-fast.
- Important constraint: the local picotls core currently passes an async job pointer only for server CertificateVerify (`/home/count0/src/picotls/lib/picotls.c:3233`) and `ptls_get_async_job()` returns `tls->server.async_job` (`/home/count0/src/picotls/lib/picotls.c:5536`). Client mTLS async signing cannot be completed in `Ztls` alone unless picotls is upgraded or patched to support a client async job.

## Architecture Documentation

New or changed components:
- `Ztls::EngineParams`, `Ztls::ClientParams`, and `Ztls::ServerParams` in `ztls/src/Ztls.hh`.
- New common `Engine` async state:
  - `ZiEventLoop m_eventLoop`
  - `unsigned m_asyncThread`
  - flags for event-loop initialized/started state
  - `ZmFn<void(ZeException)> m_errorFn`
  - helpers such as `asyncConfigured()`, `startEventLoop_()`, `stopEventLoop_()`, and `error_(ZeException)`.
- Backend facade additions in `ztls/src/ZtlsBackend.hh` and `ztls/src/ZtlsOpenSSL.cc`:
  - `bool sign_cert_async(SignCert *, bool)` or `SignCert *sign_cert_new(PKey *, bool async)`.
  - Synchronous signing remains the default.
- Per-link async state in `Link`:
  - current `ptls_async_job_t *` identity
  - registered fd/handle value
  - registration kind (`none`, `handle`, optional `socket`)
  - TLS generation counter incremented by `reset_tls_()`
  - async resume scheduled flag
  - cleanup helper safe to call repeatedly.

New or changed processes or threads:
- The TLS scheduler thread remains the only thread that calls picotls APIs.
- The optional async scheduler thread runs `ZiEventLoop` and only observes external job fd readiness.
- Event-loop readiness callbacks deregister the fd on the event-loop thread and schedule a TLS-thread resume with `app()->run()` or `app()->invoke()`.

New or changed interfaces:
- `Engine::init(EngineParams)`, `Client::init(ClientParams)`, and `Server::init(ServerParams)` replace positional overloads.
- `EngineParams` owns required `mx`, `thread`, and `alpn`, plus optional `caPath`, `certPath`, `keyPath`, `asyncThread`, and `errorFn`.
- `ClientParams` derives from `EngineParams` and adds no fields.
- `ServerParams` derives from `EngineParams` and adds `mTLS` and `cacheTimeout`.
- Config-driven wrappers keep existing `thread` and `caPath` config keys and add optional `asyncThread` where async signing is exposed.

New or changed data flows:
- Parameter objects copy input spans/strings before scheduler invocation, so temporaries do not need to survive `init()`.
- Async signing flow:
  1. `ptls_handshake()` returns `PTLS_ERROR_ASYNC_OPERATION` on the TLS thread.
  2. `Link` calls `ptls_get_async_job(tls())`.
  3. `Link` obtains an fd via `job->get_fd(job)`.
  4. Registration is performed on the `ZiEventLoop` scheduler thread with `addHandle`.
  5. Read readiness removes the handle, captures link/generation/fd identity, and schedules TLS-thread resume.
  6. TLS-thread resume validates generation and state before calling `ptls_handshake()` with no new input.

New or changed event-driven or timer processing:
- `Engine::init` starts `ZiEventLoop` synchronously when `asyncThread` is configured, so init can fail if the event loop cannot start.
- `Engine::final` stops the event loop and calls `final()` before common TLS/backend cleanup.
- `Link::asyncCleanup_()` removes any pending event-loop registration during disconnect/reset/handshake completion.

New or changed network programming:
- No network socket model changes.
- The async job fd is treated as an external handle. Use `addHandle` unless backend research proves the returned value is a socket on a platform.

New or changed data stores:
- None.

## Detailed Design and Implementation Plan

### Phase 0: Resolve Picotls Client Async Capability

- Focus: validate or fix the underlying picotls capability required for client mTLS async signing.
- Current feasibility:
  - Server async signing is feasible with the local picotls core.
  - Client mTLS async signing is not feasible in `Ztls` alone because local `send_certificate_verify()` passes `NULL` for the async job pointer when `tls->is_server` is false, and `ptls_get_async_job()` returns only `tls->server.async_job`.
- Required resolution before claiming all requirements met:
  - Preferred: upgrade or patch `/home/count0/src/picotls` so `ptls_t` carries a client async job, client CertificateVerify passes a non-null async job pointer, `ptls_get_async_job()` returns the active side's job, and async job destruction covers both client and server.
  - Alternative: defer client mTLS async support explicitly, but that would not satisfy `requirements.new.md`.
- Verification gate:
  - Add or run a small fake `ptls_sign_certificate_t` probe that returns `PTLS_ERROR_ASYNC_OPERATION` during client CertificateVerify. The test must confirm `ptls_get_async_job(client_tls)` returns the fake job before proceeding with the Ztls client async work.

### Phase 1: Add Parameter Object API

- Focus: replace positional init signatures with owned, fluent parameter objects.
- Add to `ztls/src/Ztls.hh`:

```c++
namespace Ztls {

using ErrorFn = ZmFn<void(ZeException)>;
ZuDerive(ParamString, ZtString<ZtStringHeapID<"Ztls.Param">>);
ZuDerive(ALPNNames, (ZtArray<ParamString, ZtArrayHeapID<"Ztls.Param.ALPN">>));

struct EngineParams {
  EngineParams(ZiMultiplex *mx, ZuCSpan thread, ZuSpan<ZuCSpan> alpn);
  EngineParams &&caPath(ZuCSpan);
  EngineParams &&certPath(ZuCSpan);
  EngineParams &&keyPath(ZuCSpan);
  EngineParams &&asyncThread(ZuCSpan);
  EngineParams &&errorFn(ErrorFn);

  ZiMultiplex *mx = nullptr;
  ParamString thread;
  ALPNNames alpn;
  ParamString caPath_;
  ParamString certPath_;
  ParamString keyPath_;
  ParamString asyncThread_;
  ErrorFn errorFn_;
};

struct ClientParams : public EngineParams {
  using EngineParams::EngineParams;
  ClientParams &&caPath(ZuCSpan);
  ClientParams &&certPath(ZuCSpan);
  ClientParams &&keyPath(ZuCSpan);
  ClientParams &&asyncThread(ZuCSpan);
  ClientParams &&errorFn(ErrorFn);
};

struct ServerParams : public EngineParams {
  using EngineParams::EngineParams;
  ServerParams &&caPath(ZuCSpan);
  ServerParams &&certPath(ZuCSpan);
  ServerParams &&keyPath(ZuCSpan);
  ServerParams &&asyncThread(ZuCSpan);
  ServerParams &&errorFn(ErrorFn);
  ServerParams &&mTLS(bool);
  ServerParams &&cacheTimeout(int);

  bool mTLS_ = false;
  int cacheTimeout_ = -1;
};

} // namespace Ztls
```

- Use derived setters or a small helper to preserve chaining after common setters, e.g. `ServerParams(...).certPath(...).keyPath(...).mTLS(true)`.
- Parameter constructors copy `thread`, every ALPN name, and optional strings into owned `ParamString`/`ALPNNames`.
- Default `errorFn` logs the moved exception with `ZiLogEvent(ZuMv(e))`.
- Remove old public positional overloads immediately.
- Keep any lambda-based common init helper private/protected, not public.

### Phase 2: Rework Engine Init, Validation, and Event-Loop Lifecycle

- Focus: centralize common validation and own the optional event loop in `Engine`.
- Replace the public templated `Engine::init(ZiMultiplex *, ZuCSpan, L)` with a private/protected helper that accepts params and a client/server configuration lambda.
- Public `Engine::init(EngineParams)` validates:
  - null `mx`
  - invalid TLS thread id using the existing `"invalid thread ID"` diagnostic style
  - `mx->running() == false`
  - invalid async thread id with `"invalid async thread ID"`
  - async thread equal to TLS thread
  - async thread not isolated when `mx->params().thread(asyncSid).isolated()` is available.
- Store resolved TLS and async scheduler ids before scheduler invocation.
- On the TLS scheduler thread:
  - run `Random::init()`
  - populate `ptls_context_t` common fields
  - initialize cipher suites
  - copy ALPN into existing `m_alpnData`/`m_alpn` with `init_alpn_()`
  - initialize and start `m_eventLoop` when `asyncThread` is set.
- Start/stop pattern:
  - `m_eventLoop.init(m_mx, m_asyncThread, m_errorFn)`
  - `m_eventLoop.start(...)` wrapped in `ZmBlock<bool>` so `init()` can return `false`
  - if any later init step fails, stop/final the event loop before returning `false`
  - `final()` stops the event loop with a blocking callback if it was started, then calls `m_eventLoop.final()`.
- Route event-loop start/runtime failures through `m_errorFn`; synchronous parameter validation can keep existing `ZiLOG(Error, "Ztls", ...)` style and return `false`.

### Phase 3: Migrate Client and Server Context Setup

- Focus: configure client/server-specific picotls context on the TLS thread using params.
- `Client::init(ClientParams)`:
  - validates client mTLS `certPath`/`keyPath` as all-or-none.
  - loads CA using inherited `caPath`; empty still selects platform defaults.
  - if both `certPath` and `keyPath` are set, load client certificate/key and configure `ctx->sign_certificate`.
  - if mTLS is configured and `asyncThread` is configured, enable async signing on the client signer; this depends on Phase 0 picotls support.
  - if only `asyncThread` is configured and no client certificate/key is configured, keep the client otherwise synchronous.
- `Server::init(ServerParams)`:
  - rejects missing `certPath` or `keyPath` before listening starts.
  - loads server certificate/key and configures `ctx->sign_certificate`.
  - if `asyncThread` is configured, enables async signing on the server signer.
  - sets `ctx->require_client_authentication` from `mTLS`.
  - sets `ctx->ticket_lifetime = cacheTimeout < 0 ? 86400 : cacheTimeout`.
  - keeps `ctx->encrypt_ticket` using the existing backend ticket key.
  - removes `cacheMax` from the public API and documents that old `cacheMax` was unused.
- Backend facade:
  - Add `Backend::sign_cert_async(SignCert *, bool)` returning `false` when unavailable.
  - In OpenSSL implementation, set `sign->impl.async = async ? 1 : 0` under `PTLS_OPENSSL_HAVE_ASYNC`.
  - If async is requested but unsupported, fail init with a clear backend capability diagnostic.

### Phase 4: Centralize Handshake Result Handling

- Focus: make all `ptls_handshake()` paths behave consistently.
- Keep `handshake__()` as the low-level wrapper that:
  - allocates the handshake TX buffer
  - calls `ptls_handshake(m_tls, &pbuf, input, inlen, &m_props)`
  - flushes any generated bytes through `flushTxBuf_()`
  - returns the picotls result.
- Add a single handler:

```c++
void handleHandshakeResult_(int n) {
  if (!n) { finishHandshake_(); return; }
  if (n == PTLS_ERROR_IN_PROGRESS) return;
  if (n == PTLS_ERROR_ASYNC_OPERATION) { asyncHandshake_(n); return; }
  if (isCloseNotify_(n)) { disconnect_(true); return; }
  ZiLOG(Error, "Ztls", ([n](auto &s) {
    s << "ptls_handshake(): " << strerror_(n);
  }));
  disconnect_(false);
}
```

- Use the handler from:
  - `Link::handshake_(ZmRef<ZiIOBuf>)`
  - `CliLink::connected_()` after the initial ClientHello call
  - async resume calls.
- Add `m_handshakeDone` or equivalent so `finishHandshake_()` calls `impl()->connected(...)` exactly once.
- On successful handshake completion:
  - call `asyncCleanup_()`
  - initialize record metadata exactly as `handshook()` does today
  - call the application `connected(...)`.

### Phase 5: Register and Resume FD-Backed Async Jobs

- Focus: implement `PTLS_ERROR_ASYNC_OPERATION` with `ZiEventLoop` while preserving TLS-thread ownership.
- On async result:
  - if no event loop is configured, log/route an explicit diagnostic naming `PTLS_ERROR_ASYNC_OPERATION` and `asyncThread`, then disconnect.
  - call `ptls_get_async_job(tls())`.
  - reject null job.
  - reject missing `job->get_fd` with a callback-only unsupported diagnostic.
  - call `job->get_fd(job)` and reject invalid/null fds.
  - call `asyncCleanup_()` before registering a new job.
  - store job identity, fd, registration kind, TLS pointer, and generation.
  - register the fd with `ZiEventLoop` on the async scheduler thread.
- Registration details:
  - Use `m_eventLoop.run(...)` plus `ZmBlock<bool>` or an equivalent synchronous wrapper to execute `addHandle` on the event-loop thread and report add failure to the TLS thread.
  - Use a no-op send callback.
  - Use a read callback that removes the handle on the event-loop thread and schedules TLS resume.
  - Route add failure through `m_errorFn` and disconnect.
- Readiness callback:
  - captures a safe link reference, generation, TLS pointer, job pointer, and fd.
  - calls `delHandle(fd)` before scheduling resume.
  - schedules `resumeHandshake_(captured...)` onto the TLS thread.
  - does not call picotls from the event-loop thread.
- Resume:
  - checks that the active connection/TLS pointer, generation, job pointer, and fd still match.
  - ignores stale completions with trace/debug logging if available.
  - clears pending registration state before calling `ptls_handshake()` again.
  - calls `handshake__()` with no new network input and dispatches through `handleHandshakeResult_()`.
  - supports another `PTLS_ERROR_ASYNC_OPERATION` by registering the next job.

### Phase 6: Async Cleanup, Reset, and Finalization Safety

- Focus: prevent stale event-loop registrations and stale completions.
- Add per-link helper:

```c++
void asyncCleanup_() {
  if (m_asyncReg == AsyncReg::Handle)
    app()->asyncDelHandle_(m_asyncHandle);
  else if (m_asyncReg == AsyncReg::Socket)
    app()->asyncDelSocket_(m_asyncSocket);
  m_asyncJob = nullptr;
  m_asyncHandle = Zi::nullHandle();
  m_asyncSocket = Zi::nullSocket();
  m_asyncReg = AsyncReg::None;
  m_asyncResumeScheduled = false;
}
```

- The engine delete helpers execute `delHandle`/`delSocket` on the event-loop scheduler thread, not directly from the TLS thread.
- Call cleanup from:
  - handshake completion
  - `disconnect_()`
  - `disconnected_()`
  - `reset_tls_()` before freeing or replacing `ptls_t`
  - link destructor as a defensive best effort when the engine/event loop is still available.
- Increment a generation counter in `reset_tls_()` before freeing/replacing `ptls_t`.
- Do not add a link registry to `Engine` unless implementation reveals an ownership path where links can remain alive past `final()` without receiving disconnect/reset. Current ownership is through client link refs and server connection refs.

## Options and Open Questions

- Blocking dependency question: client mTLS async signing is required, but the local picotls core supports async jobs only on the server side. Should this work include patching/upgrading `/home/count0/src/picotls`, or should client mTLS async be deferred with a documented scope exception? The requirement cannot be fully met in `Ztls` alone.
  - ANSWER: no need for async signing support on client side
- Platform question: picotls/OpenSSL exposes async completion as an integer fd through `get_fd`. On Unix this maps naturally to `Zi::Handle`; Windows behavior should be verified against the actual `ptls_openssl` build before claiming Windows async support.
  - ANSWER: use conditional compilation on `_WIN32` to disable async completion on Windows with a comment concerning `picotls` narrowing to `int`, which is incompatible with `HANDLE` being pointer-sized
- Test hook question: the cleanest deterministic async tests require a fake signer that can wrap a real signer. This can live entirely under `ztls/test`, but if private signer state blocks that approach, add a narrow test-only accessor rather than broadening production API.
  - ANSWER: simulate an async signer using a fake/mock
- Migration note: the old positional `cacheMax` argument was unused in the picotls implementation and should be documented as intentionally removed, not silently retained.
  - ANSWER: ruthlessly prune it if it is no longer relevant
