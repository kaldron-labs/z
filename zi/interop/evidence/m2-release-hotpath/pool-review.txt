Configured fixed I/O pool comparison, 2026-10-08

Retained Clang release build:
  make -C zi/interop -j4 -f Makefile -f /tmp/zffb-release-link.mk /tmp/zifb-release-bench
Only the benchmark changed. Both codecs use identical allocator configuration.
ZIFB_BENCH_POOL configures the existing ZiIOBuf fixed pool through ZmHeapMgr;
production defaults, IDs, object sizes and variable-heap configuration are
unchanged. The default benchmark configuration remains heap fallback.
Four blocks cover the preflight owner, active builder and next fresh owner.

Commands, sequential on CPU 6 after build completion:
  taskset -c 6 /tmp/zifb-release-bench 1000000 64 11
  ZIFB_BENCH_POOL=4 taskset -c 6 /tmp/zifb-release-bench 1000000 64 11
Repeat both with trailing 'wide'. Each run alternates codec order across 11
rounds and completes independent canonical/native correctness preflights.
Values below are medians of per-round mean ns/operation, not message-tail
percentiles. No concurrent build or profiler ran during timing.

Separate debugger traces use trace-growth.py with '3 64 1', with and
without ZIFB_BENCH_POOL=4. In the default run every fixed-pool request sees
an empty freelist (reuse 1, fresh 4, both codecs). With four configured blocks
none sees an empty freelist. This confirms that the two cases actually take
different allocation paths rather than merely requesting different settings.

The narrow fresh-buffer regression disappears with the configured pool;
wide fresh results are close (native +0.9%). This supports heap fallback as
a contributor to the observed fresh-buffer difference. It does not prove why
identical heap request sequences differ in time, or erase the default-run
regressions (narrow +4.6%, wide +7.9%). Keep both allocator regimes in final
acceptance. Reflection/consumer gates and full latency distributions remain
open; these runs are not a complete performance acceptance claim.
