# Zum authorization service and clients

## Overview

`libZum` supplies JWT verification, service authentication, management routes, and shared-signal reception. `zum` is the native management CLI; `zumd` is the persistent authorization daemon, combining browser/passkey and upstream OIDC authentication with application catalogs, scoped roles, administrative delegation, and durable database operations. [Makefile.am](./Makefile.am)

## Interface

- Public [ZumTypes.hh](./ZumTypes.hh) and [ZumURI.hh](./ZumURI.hh) define principals, identifiers, credentials and application-scoped paths. [ZumJWTVerify.hh](./ZumJWTVerify.hh) exposes bounded ES256 verification and unauthenticated header extraction; [ZumLib.hh](./ZumLib.hh) exposes library initialization/version facilities.
- [ZumService.hh](./ZumService.hh) exposes `Service` initialization/start/stop/final, verification, key refresh, catalog publication and SET reception. Callers supply scheduler, credentials, clock and `ServiceHTTPFn`. [ZumMgmt.hh](./ZumMgmt.hh) defines the immutable management-operation registry, catalog and SSF registration models.
- [zum.cc](./zum.cc) implements login and typed management commands. [zumd.cc](./zumd.cc) configures database, Vault key, bootstrap, HTTP, OIDC and optional telemetry; it also exposes one-shot repair/bootstrap and offline rekey modes. Vault adapters and [zum_cli.hh](./zum_cli.hh) are private headers.
- Daemon boundaries are [Daemon](./zumd_daemon.hh), [Server](./zumd_server.hh), [Requests](./zumd_request.hh), authorization/passkey/token/session helpers, and typed tables. [zumd_schema.cc](./zumd_schema.cc) registers 24 tables; [zumd_saga_catalog.cc](./zumd_saga_catalog.cc) registers versioned saga definitions, submitted on shard 0 by [zumd_saga_submit.cc](./zumd_saga_submit.cc).

## Invariants

- `jwtHeader` does not authenticate its result. Full verification checks bounded three-part JWT input, ES256 signature, key/issuer/audience and time claims before publishing a principal; issuer-only verification still requires a nonempty audience. Signing-key selection is bounded and rereads its selected record. [ZumJWTVerify.cc](./ZumJWTVerify.cc), [zumd_discovery.cc](./zumd_discovery.cc), [zumd_key_validation.cc](./zumd_key_validation.cc)
- Service's injected HTTP callback must complete each submitted call exactly once and enforce transport policy; request timeout is passed to that adapter. Keep dependencies alive through stop. Service, daemon, OIDC and request owners seal admission and drain retained callback graphs before finalization; request credits include cancelled nodes awaiting timer-retirement barriers. [ZumService.cc](./ZumService.cc), [zumd_daemon.cc](./zumd_daemon.cc), [zumd_oidc.cc](./zumd_oidc.cc), [zumd_request.cc](./zumd_request.cc)
- Prepare the daemon while stopped with ordinary request admission closed. Startup orders provider, SSF, then HTTP; shutdown drains producers/helpers before SSF and transport. Activation generations reject stale startup completions. Application admission uses active, unowned app/policy snapshots; an already admitted operation may finish after a later app-state change. [zumd.cc](./zumd.cc), [zumd_daemon.cc](./zumd_daemon.cc), [zumd_server.cc](./zumd_server.cc)
- Authorization reloads current principal, policy, assignment, role and action authority, intersecting it with captured grant permissions. Local identity presence shadows external identity. OIDC binds issuer, audience, nonce, authentication time and provider evidence; delegated evidence has bounded age and role mappings. [zumd_authorize.cc](./zumd_authorize.cc), [zumd_db.cc](./zumd_db.cc), [zumd_oidc.cc](./zumd_oidc.cc)
- Browser ceremonies bind to cookie digests and expiration. WebAuthn requires exact origin/challenge/RP bindings, user presence and verification, ES256 keys/signatures and consistent backup flags; registration accepts `none` attestation. Code checks alone do not consume grants: persistence helpers and sagas establish consumption and publication. [zumd_server.cc](./zumd_server.cc), [zumd_webauthn.cc](./zumd_webauthn.cc), [zumd_oauth.cc](./zumd_oauth.cc), [zumd_saga_code_family.cc](./zumd_saga_code_family.cc)
- Token signing precedes code consumption or refresh rotation; successful persistence is followed by a final authority check before release. Failure can leave a code consumed without returning tokens. Refresh reuse revokes the family; revocation of self-contained access JWTs is an accepted no-op. Session use extends idle expiry up to its absolute deadline; later authorization reloads user authority. [zumd_token.cc](./zumd_token.cc), [zumd_session.cc](./zumd_session.cc), [zumd_db_ops.hh](./zumd_db_ops.hh)
- Administrative bearer actions still pass current delegation checks. Conditional edits use ETags; creation PUTs use `If-None-Match: *`. Idempotency identity is actor/operation/key, with a digest of operation, target, conditions and body; conflicting reuse returns 409, pending returns 202, completed replay returns result IDs. [zumd_daemon_admin.cc](./zumd_daemon_admin.cc), [zumd_saga_admin_ops.hh](./zumd_saga_admin_ops.hh), [zumd_request_db.hh](./zumd_request_db.hh)
- Persisted saga type versions, phase definitions, serialized inputs and registration must remain compatible with replay. Business operations use ownership, snapshots, staged publication and compensation; cleanup deletion phases deliberately do not restore rows, so completed deletions can survive later failure. [zumd_saga_catalog.cc](./zumd_saga_catalog.cc), [zumd_saga_catalog_publish.cc](./zumd_saga_catalog_publish.cc), [zumd_saga_grant_cleanup.cc](./zumd_saga_grant_cleanup.cc), [zumd_saga_session_cleanup.cc](./zumd_saga_session_cleanup.cc)
- Rekey is offline: stop other writers and finish before shutting down the store. It persists pending key binding, transforms ciphertext one record at a time, verifies every field with the new key, then publishes the new binding; retries recognize already transformed fields. Durable arguments contain ciphertext, not plaintext keys. [zumd_rekey.hh](./zumd_rekey.hh), [zumd_rekey.cc](./zumd_rekey.cc), [zumd_saga_secret_rekey.cc](./zumd_saga_secret_rekey.cc)

## Side Effects

- The daemon creates/updates identities, credentials, authorization codes, refresh families, sessions, consent, catalogs, delegation and key records. Bootstrap seeds rows resumably, issues an enrollment capability, writes a restricted capability file, then advances its phase; these steps are not one all-or-nothing transaction. [zumd_bootstrap.cc](./zumd_bootstrap.cc), [zumd_schema.cc](./zumd_schema.cc)
- HTTP endpoints perform discovery, login/consent/logout, passkey/OIDC callbacks, token operations, UserInfo and management. Cookies use Secure/HttpOnly/SameSite=Lax; logout checks a cookie-derived CSRF value. Outbound OIDC uses HTTPS, bounded origins/responses and retained asynchronous calls. [zumd_http.hh](./zumd_http.hh), [zumd_server.cc](./zumd_server.cc), [zumd_oidc.cc](./zumd_oidc.cc)
- SSF transmission persists an outbox before HTTP delivery, rechecks receiver revision/lease, removes successful deliveries and schedules bounded-backoff retries. Service receives and deduplicates signed SETs, renews registration, refreshes keys and publishes catalogs through its adapter. [zumd_revoke.cc](./zumd_revoke.cc), [ZumService.cc](./ZumService.cc)
- Secrets use AES-256-GCM envelopes bound to issuer, record type/ID and field. CLI/daemon Vault operations persist credentials/database keys; login can launch `xdg-open`. Mutable secret buffers have explicit clearing paths. Management audits, readiness/listener messages and maintenance counters reach logging/output; timers drive expiry and cleanup. [zumd_secret.cc](./zumd_secret.cc), [ZumVaultClient.hh](./ZumVaultClient.hh), [zum.cc](./zum.cc), [zumd.cc](./zumd.cc), [zumd_admin.cc](./zumd_admin.cc)
